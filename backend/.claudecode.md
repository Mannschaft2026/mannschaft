## 1. バックエンド (Java / Spring Boot)

- `src/main/java/com/mannschaft/app/` 配下は「技術レイヤー」ではなく「機能（ドメイン）」ごとにパッケージを分離すること。
- `com.mannschaft.app.controller` のような全機能共通のレイヤーパッケージは作成しない（禁止）。
- ファイル移動・作成時は、ディレクトリ構造に合わせた `package` 宣言を正しく記述すること。
- 複数機能で共有するモデルや基底クラスは `com.mannschaft.app.common` に配置すること。
- Spring の設定クラス（Security, WebSocket, Valkey/Redis, CORS, Swagger 等）は `com.mannschaft.app.config` に配置する。`common` とは分離し、アプリケーション設定専用とする。
- 異なる機能間のサービスを呼び出す場合は、Repository を直接呼ばず Service 経由で呼び出すこと。
- 機能が肥大化する場合は、役割ごとに Service / Controller を同一 feature パッケージ内で分割すること。
- `@PreAuthorize` で書けない認可（名簿・日付・メンバー資格など）は、Controller → Facade（`@Transactional` なし）→ `XxxAccessPolicy` → `AccessControlService` の順で行い、業務 Service は Policy を呼ばない。

詳細・コード例・経緯: [docs/conventions/backend/01-backend-java.md](../docs/conventions/backend/01-backend-java.md)

## 2. フロントエンド (TypeScript / Nuxt.js)

> ディレクトリ構成・命名規則・API通信・セキュリティの詳細は **`FRONTEND_CODING_CONVENTION.md`** に定義する。ここでは原則のみ記載する。

- Nuxt 3 の標準ディレクトリ構成をベースに、機能別でファイルを整理する
- **SSR と認証の制約**: JWT は `localStorage` に保存するため、SSR 時にはアクセス不可。SSR は公開ページ（SEO目的）のみ、認証ページは SPA モード
- **API通信**: フロントエンド → Spring Boot API に直接通信。BFF（`server/api/`）はAPIキー秘匿等の例外時のみ
- **自動生成型**: `types/generated/` は直接編集禁止。openapi-typescript で生成（`cd frontend && npm run generate:types`）
- **`docs/openapi.json` の再生成**: `cd backend && ./gradlew generateOpenApiDocs`（手編集は禁止。エスケープが壊れる）。
  タイムアウトした場合の診断手順（無音ログ・`:8082` の孤児プロセス）は
  [`docs/development/openapi_json_regeneration.md`](../docs/development/openapi_json_regeneration.md) を参照

## 3. エラーハンドリングとAPIレスポンス設計

- HTTP ステータスで成功/失敗を判断し、`success` フィールドは持たない。成功時は常に `data` でラップし、すべてのコントローラーは `ApiResponse<T>` または `PagedResponse<T>` を返す。エラーは `ErrorResponse`（`error.code` / `message` / `fieldErrors?`）。
- バリデーションメッセージは `messages.properties` に集約し、`GlobalExceptionHandler` でフィールド名＋メッセージに変換する。
- `com.mannschaft.app.common` に共通インターフェース `ErrorCode` を置き、各機能パッケージに `[Feature]ErrorCode` Enum（`ErrorCode` 実装）を作る。`ErrorCode` は HTTP ステータスに依存させず、紐付けは `GlobalExceptionHandler` で行う（個別マッピング＋`Severity` 既定の2層）。
- 【必須】`Severity.ERROR` は「既定で HTTP 500」と同義。サーバ側の障害（外部連携失敗・生成/直列化失敗・データ不整合・想定外の状態）にのみ付ける。クライアント起因のエラーに `Severity.ERROR` を付けてはならない（WARN=400 / INFO=200 が既定）。
- クライアント起因エラーの是正は、まず `Severity` を `WARN` に正す。既定の 400 で粗すぎる場合（404・409・402・429 等）に限り `ERROR_CODE_STATUS_MAP` へ明示登録する。`Severity.ERROR` のまま `ERROR_CODE_STATUS_MAP` に 4xx を足すだけの直し方は禁止。既知の例外（`CHAT_015` / `CHAT_019` / `RECRUITMENT_204` / `RECRUITMENT_207`）は負債であり新規に増やさない。
- 「上限超過」は 409 ではなく 400 が本則（既定のまま上書き不要）。不在・越境の存在秘匿は 404、重複・状態競合・楽観ロック競合は 409、支払い必要は 402、レート制限は 429。
- 【必須】ステータスを決める・変えるときは、同一概念の兄弟コードがドメイン横断で別ステータスになっていないか、enum 定数名と日本語メッセージの両方で全 `*ErrorCode.java` を grep して確認する。新規エラーコード追加時にクライアント起因なのに 500 を返す状態にしない（回帰固定は `GlobalExceptionHandlerTest` の `ClientErrorMustNotBe500`）。
- エラーコードは `{機能プレフィックス}_{連番3桁}`。新機能追加時は先にプレフィックスを定義してからエラーコードを作る。
- メッセージはハイブリッド方式: BE は Enum にデフォルトメッセージを持ちレスポンスに含める。FE は `code` をキーに文言を制御してよい。
- `com.mannschaft.app.common` に `BusinessException`（`ErrorCode` を保持し Service 層から投げる）と `GlobalExceptionHandler`（`@RestControllerAdvice`）を置く。Bean Validation 失敗・不正 JSON・型不一致・必須パラメータ欠落は `COMMON_001`（400）、楽観ロック競合は `COMMON_003`（409、§22）、その他未定義例外は `COMMON_999`（500）。
- FE は `composables/useErrorHandler.ts` にエラーコード→表示メッセージ変換を集約し、共通インターセプター（`useApi.ts`）で 401 / 5xx を自動処理し、`fieldErrors` は VeeValidate と連携して項目別に表示する。

詳細・コード例・経緯: [docs/conventions/backend/03-error-handling.md](../docs/conventions/backend/03-error-handling.md)

## 4. APIバージョニング
- **方式**: URLパスベースのバージョニング（`/api/v1/...`）を採用する。
- **バージョンアップ基準**: 破壊的変更が必要な場合のみメジャーバージョン（v2, v3...）を上げる。フィールドの追加など後方互換のある変更は同一バージョン内で対応する。
- **並行稼働**: 新バージョンリリース後も、旧バージョンは最低3ヶ月間は並行稼働させる。

## 5. リソーススコープ（取得範囲）の命名規約
- **個人スコープ**: ログインユーザー自身のデータを取得する場合は `/resources/me`（例: `/todos/me`）というパスを使用する。
- **所属組織スコープ**: チームや組織に紐づくデータを取得する場合は、`/teams/{teamId}/resources` のように、親リソースのIDをパスに含めることを原則とする。
- **一貫性の保持**: `GET /todos` のようにスコープが曖昧なエンドポイントは避け、必ず「誰の・何の」範囲であるかをパス構造で定義する。
- **例外**: 検索APIなどで動的に範囲を切り替える場合は、`scope=mine|team|all` といったクエリパラメータを標準化して使用する。
- **README.md との関係**: README.md の API 設計セクションは機能一覧としての概要表記であり、スコープを省略した短縮形で記載されている。実装時は本規約に準拠し、すべてのエンドポイントに明示的なスコープ（`/me`, `/teams/{teamId}/...` 等）を付与すること。

## 6. イベント駆動設計

- 機能間の連携は Service 間の直接呼び出しで密結合させず、`DomainEventPublisher` インターフェース経由で発行する（初期実装は Spring の `ApplicationEvent` + `@TransactionalEventListener`）。
- `com.mannschaft.app.common.event/` には `DomainEvent`（マーカー）と基底クラスのみ置く。機能固有のイベントクラスは発行元の feature パッケージ内に置き、`DomainEvent` を実装する。
- 同一機能内の処理は Service 直接呼び出し、異なる機能間の非同期連携にイベントを使う。
- イベントリスナーは `@TransactionalEventListener(phase = AFTER_COMMIT)` を使い、発行元のコミット後にのみ実行されるようにする。
- `DomainEvent#occurredAt()` は `LocalDateTime`（§20 準拠。`Instant` は使用しない）。
- 非同期（`@Async`）リスナーの失敗時は、ERROR ログ＋監査ログ記録を必須とする。即時リトライはせず運用監視で検知する。リトライ機構を導入するときは本節を更新する。
- 【必須】業務 TX 内の直接呼び出しを `AFTER_COMMIT` リスナーへ移設するときは、(1) 移設した通知種別・イベントを観測している既存テストをテスト木全体から洗う（`notification_type` の値で検索）、(2) 見つかったテストが実効的に `@Transactional` か確認する（「0 件であること」を検証するテストは偽の緑になる。継承・`@DataJpaTest` でも実効的に TX になる）、(3) 配送まで検証するなら `@Transactional` を外して `TransactionTemplate` で明示コミットするか、`@RecordApplicationEvents` で publish までを検証する形に直す、(4) 直したテストが直す前の本番コードで赤くなることを実測する。
- 番人 `TransactionalTestNotificationObservationGuardTest` が「実効的に `@Transactional` なテストが通知の配送結果を表明している」形を拒否する。例外は同クラスの `ALLOWED` に理由付きで列挙し、無条件の baseline 化はしない。

詳細・コード例・経緯: [docs/conventions/backend/06-event-driven.md](../docs/conventions/backend/06-event-driven.md)

## 7. 新モジュール追加ガイドライン
選択式モジュールを新規追加する際の手順:

1. **エラーコードプレフィックス**を定義する（例: `RESERVE`）
2. **Flyway マイグレーション**で `module_definitions` テーブルにレコード追加
3. **`module_level_availability`** でレベル別適用（組織/チーム/個人）を設定
4. **feature パッケージ**を新規作成（本ファイルの構成イメージに従う）
5. **テンプレートプリセット**への追加（必要に応じて `template_modules` を更新）
6. **ユニットテスト・統合テストの作成**
    - 新しいモジュール（Service, Controller等）を作成した際は、必ず対応するテストコードをセットで作成すること。
    - **テスト範囲**: ユニットテスト（境界値や例外系を含むビジネスロジックの検証）、統合テスト（DBアクセスや依存コンポーネントとの連携検証）。
    - **完了定義**: テストがすべてパスし、プロジェクトで規定されたカバレッジ基準を満たしていることを確認して完了とする。
7. **フロントエンド**: `pages/`, `components/`, `composables/` に対応するファイルを追加

## 8. データ保持・削除規約
- **個人情報の取り扱い**: 退会申請後 **30日間** を猶予期間（論理削除状態）とし、その後個人を特定できる情報（氏名、メールアドレス等）を物理削除する。
- **法的強制力のあるデータ**: 決済履歴や領収書データ等は、税法等の法令遵守のため、退会後も **7年間** 保持する。
- **データの匿名化**: 投稿内容や行動ログを統計的に利用する場合は、個人との紐付けを完全に遮断（アノニマイズ）した状態で保持する。
- **アカウント凍結時**: 規約違反等による凍結時は、再登録防止や法的対応のため、凍結解除または一定期間が経過するまで情報を保持し続ける。

## 9. サブスクリプション設計指針
- **DB構造の柔軟化**: `subscription_plans` テーブルに `plan_type` カラム（`FLAT` / `METERED`）を定義し、定額・従量の両方に対応可能なスキーマ設計を Phase 1 から検討する。
- **ビジネスロジックの分離**: 料金計算ロジックは将来の「従量課金」導入を見据え、特定の計算式に依存しないよう `BillingStrategy` 等で抽象化して実装する。
- **決定時期**: 具体的な課金ロジックの実装は Phase 8 までに確定させるが、DBマイグレーションのコストを最小化するため、器（テーブル構造）の準備は現段階で行う。

## 10. データベース命名規約
- **テーブル名**: 小文字の `snake_case` かつ **複数形** とする（例: `task_groups`）。
- **カラム名**: 小文字の `snake_case` とする（例: `due_date`）。
- **主キー**: 原則として `id`（Long/UUID）とする。
- **論理値 (Boolean)**: `is_` または `has_` で始める命名とする（例: `is_completed`）。
- **日時 (Timestamp)**: `created_at`, `updated_at`, `deleted_at` 等、`_at` を末尾に付与する。
- **日付 (Date)**: 日時を含まない場合は `_on` を末尾に付与する（例: `birthday_on`）。
- **外部キー**: `[相手先テーブルの単数形]_id` とする（例: `user_id`）。

### 10.1 E-R 図の自動生成

既存テーブルの構造・ドメイン間の参照は、[`docs/architecture/er/README.md`](../docs/architecture/er/README.md) から辿れる E-R 図で確認する。**テーブル設計・ドメイン境界の判断・既存テーブルの把握の前に、まずこれを見ること**。

- **位置づけ**: `docs/features` 配下の手描き `erDiagram` は設計時点の意図、`docs/architecture/er/` は現実のスキーマ。食い違えば `er/` が現状である。
- **生成の仕組み**: Flyway を全適用した MySQL（Testcontainers）の `information_schema` から、ドメイン単位の `<domain>.md`（mermaid `erDiagram` ＋全列定義表）、全体の `README.md`、ドメイン未解決の `_unmapped.md` を出力する。生成器は `backend/src/test/java/com/mannschaft/app/common/erdiagram/`。
- **ドメイン解決**: `@Entity` の `@Table(name)`（および `@SecondaryTable` / `@CollectionTable` / `@JoinTable`）を `com.mannschaft.app` 直下のパッケージ名へ対応づける（ArchUnit の `TableDomainResolver` と同じ規則）。Entity の無いテーブルは `_unmapped.md` に載る。
- **関係線の凡例**: 実線は実 FK（他ドメインへの実 FK も実線）。図中の `FK` マーカーは実 FK 列だけに付き、ID参照の列には付かない。点線は「ID参照(FKなし)」で、`user_id` / `*_user_id` / `*_by` は `users`、`<x>_id` は `x` の複数形テーブルへ、列の型が参照先の主キーと一致する場合だけ推定する。多態参照（`<p>_type` と `<p>_id` の組）・推定不能参照は線を引かず表に列挙する。他ドメインへの参照は列を持たないスタブ実体で描く。図に描くのはキー列のみで、全列は表を見る。
- **自己参照**: mermaid は同一テーブルの自己参照を複数描けず1本に畳むため、自己参照は各ドメインページの「自己参照」表を正とする（図に線が欠けても表に全件ある）。
- **被参照の見方**: 各ドメインページの「被参照（他ドメインから）」節は、そのドメインのテーブルを参照している**他ドメイン側**の逆引き索引（実 FK と ID参照のみ。多態参照・推定不能参照は載らない。`_unmapped` は通常のドメインと同じく参照元にも参照先にもなる）。あるテーブルを参照している側を探すときは、そのテーブルが属するドメインのページでこの節を見る。
- **再生成（必須）**: migration や Entity を変更したら `cd backend && ./gradlew generateErDiagrams` を実行し、差分をコミットする。`./gradlew checkErDiagrams` でコミット済みとの照合のみ行える。CI の `ER Diagram Drift Check`（`.github/workflows/er-diagram-drift-check.yml`）が再生成漏れを検出する。`docs/architecture/er/` は手で編集しない。
- **Docker 不在時**: 生成・照合は Docker（Testcontainers）が必須。ローカルで Docker が使えないときは skip され、CI（`-Der.requireDocker=true`）では失敗する。ローカルで再生成できない場合は PR にその旨を書き、CI の検出結果に従って Docker のある環境で再生成する。

## 11. エンティティ共通基底規約

### BaseEntity
すべての主要エンティティが継承する `@MappedSuperclass` を `com.mannschaft.app.common` に配置する。

```java
@MappedSuperclass
@Getter
public abstract class BaseEntity {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, updatable = false)
    private LocalDateTime createdAt;

    @Column(nullable = false)
    private LocalDateTime updatedAt;

    // 論理削除対象エンティティのみ deletedAt を追加（§14 参照）
    // BaseEntity には含めず、SoftDeletableEntity 等のサブクラスで拡張する

    @PrePersist
    protected void onCreate() {
        this.createdAt = LocalDateTime.now();
        this.updatedAt = this.createdAt;
    }

    @PreUpdate
    protected void onUpdate() {
        this.updatedAt = LocalDateTime.now();
    }
}
```

- ログ系テーブル（`audit_logs`, `notifications` 等）や中間テーブルは `BaseEntity` を継承せず、個別に定義してよい。
- 論理削除が必要なエンティティは `deletedAt` フィールドを個別に追加する（本ファイル §14 参照）。

## 12. ページネーション規約
- **標準方式**: オフセットベース。クエリパラメータは `?page=0&size=20&sort=createdAt,desc` を標準とする。
    - `page`: 0始まりのページ番号
    - `size`: 1ページあたりの件数（デフォルト20、最大100）
    - `sort`: ソート対象カラムと方向（カンマ区切り）
- **カーソル方式**: チャットメッセージやタイムラインなど、リアルタイムにデータが追加されるリストにはカーソルベースを使用する。`?cursor={lastId}&limit=20` の形式。
- **レスポンス**:
    - オフセットベース: `PagedResponse<T>` の `meta` フィールドで返す（§3.1 参照）。
    - カーソルベース: `CursorPagedResponse<T>` を使用する。

```java
// com.mannschaft.app.common.CursorPagedResponse<T>
// フィールド: data (List<T>), meta (CursorMeta)
// CursorMeta: nextCursor (String, nullable), hasNext (boolean), limit (int)
CursorPagedResponse<ChatMessageResponse> → {
    "data": [...],
    "meta": { "nextCursor": "msg_12345", "hasNext": true, "limit": 20 }
}
```

## 13. APIフィルタリング規約
- **基本形式**: フィルタリング条件は、対象フィールド名をそのままクエリパラメータのキーとして使用する（例: `?status=active`）。
- **範囲指定の命名**: 日付や数値の範囲検索には、フィールド名に接頭辞/接尾辞を付与する。
    - 開始: `_from` または `_min`（例: `?price_min=1000`）
    - 終了: `_to` または `_max`（例: `?price_max=5000`）
- **複数値（IN句）の指定**: 同一キーの複数指定（`?tags=java&tags=spring`）またはカンマ区切りを許容するよう実装を統一する。
- **部分一致（LIKE検索）**: 文字列検索で部分一致をサポートする場合は、パラメータ名に `_like` を付与する（例: `?title_like=keyword`）。

## 14. 論理削除規約
- **実装方式**: 論理削除が必要なテーブルには `deleted_at DATETIME NULL` カラムを追加する。`NULL` = 有効、値あり = 削除済み。`is_deleted` フラグ方式は使用しない。
- **適用テーブル**: 主要エンティティ（`users`, `teams`, `organizations`, `blog_posts`, `chat_messages` 等）に適用する。ログ系テーブル（`audit_logs`, `notifications`）や中間テーブルには原則適用しない。
- **自動フィルタリング**: Hibernate 6.4+ の `@SQLRestriction` を Entity に付与し、デフォルトクエリに `WHERE deleted_at IS NULL` を自動適用する。手動で毎クエリに条件を追加する方式は漏れやすいため禁止する:
```java
@Entity
@SQLRestriction("deleted_at IS NULL")
public class UserEntity extends BaseEntity {
    private LocalDateTime deletedAt;
    // ...
}
```
- **削除済みデータの取得**: 管理者機能で削除済みデータを含む検索が必要な場合は、`@SQLRestriction` を無効化するカスタムクエリ（ネイティブ SQL または `@Query` に `deleted_at` 条件を明示）を使用する。
- **物理削除**: 本ファイル §8「データ保持・削除規約」に定める猶予期間経過後に、バッチ処理で物理削除を実行する。

## 15. 非同期ジョブ実行規約
- **Virtual Threads（Java 21）**: Spring Boot 3.2+ の `spring.threads.virtual.enabled=true` を `application.yml` に設定し、Tomcat のリクエスト処理に Virtual Threads を使用する。これにより、大量の同時接続を少ないOSスレッドで効率的に処理できる。
- **基本方式**: `@Async` アノテーションを使用した Spring Boot 標準の非同期実行を採用する。`@EnableAsync` を `com.mannschaft.app.config.AsyncConfig` に付与してプール定義と合わせて管理する。
- **スレッドプール管理**: `ThreadPoolTaskExecutor` を適切に構成し、APIリクエスト用のスレッドを圧迫しないよう専用のプールを割り当てる。用途ごとにプールを分離し、長時間ジョブ（データエクスポート等）がイベントリスナー（通知送信等、§6 参照）を圧迫しないようにする。
    - **イベント用プール**: 軽量・短時間処理向け（例: `event-pool`）
    - **ジョブ用プール**: 重量・長時間処理向け（例: `job-pool`）
    - `@Async("event-pool")`, `@Async("job-pool")` のように明示的にプール名を指定すること。
- **プールを無指定にしてはならない（Issue #2953）**: `@Async` を executor 無指定で使うと `@Primary` の `event-pool` に載る。`event-pool` 上で動くリスナーの中から無指定 `@Async` を呼ぶと**自分と同じプールへの自己投入**になり、容易に自己飽和する。飽和は既定 `AbortPolicy` の `RejectedExecutionException` として同期で呼び出し元に返るため、呼び出し元が `REQUIRES_NEW` の中だと**そのトランザクションごとロールバックしてデータが消える**（実際に通知行が消えうる欠陥として発現した）。
- **エグゼキュータの使い分けと拒否方針**（すべて `config/AsyncConfig`）:

| プール | 用途 | サイズ (core/max/queue) | 拒否方針 |
|---|---|---|---|
| `event-pool`（`@Primary`） | 汎用イベントリスナー（監査ログ・通知配送リスナー等） | 2/5/100 | Abort（例外送出）＋ ERROR ログ |
| `notification-dispatch-pool` | 通知の**単発**配信 `NotificationDispatchService#dispatch` | 4/8/500 | CallerRuns ＋ ERROR ログ |
| `notification-fanout-pool` | 通知の**一括**配信 `dispatchBatch`（チャンク単位） | 4/8/500 | CallerRuns ＋ Micrometer 可視化 |
| `withdrawal-pool` | 退会即時匿名化リスナー | 2/10/100 | Abort（既定） |
| `purge-pool` | 退会物理削除リスナー | 2/10/500 | Abort（既定） |
| `page-view-pool` | 計測ビーコン（欠損許容） | 2/8/500 | Discard ＋ Micrometer 可視化 |
| `job-pool` | 重量・長時間バッチ | 2/4/50 | Abort（既定） |

- **拒否は silent drop にしてはならない**: `@Async` の投入拒否はリスナー本体の `try/catch` では捕捉できない（拒否は投入時＝呼び出し元スレッドで起きる）。拒否方針は必ず `AsyncConfig` 側で明示し、少なくとも構造化 ERROR ログ（`event=async_task_rejected`）を残すこと。
- **欠損させてよいかで方針を選ぶ**: 通知・監査など欠損不可のものは `CallerRuns`（捨てず・例外も投げず、呼び出し元で実行して背圧をかける）。計測ビーコンのような欠損許容のものだけ `Discard`。無制限キュー（`queueCapacity` 無指定相当の巨大値）は OOM の入口になるため採らない。
- **状態管理**: ジョブの進捗状況（ステータス、完了率、生成ファイルURL等）は、`Valkey` または DB のジョブ管理テーブルで保持する。
- **拡張性**: 処理の肥大化や分散処理が必要になった段階で、Spring Batch や外部メッセージキュー（RabbitMQ/Kafka）への移行を検討する。

## 17. 開発フローの制約

- 【必須・AI向け】新機能の実装前に、(1) 要件確認（機能詳細とテーブル定義 DDL 案を提示し承認を得る）、(2) 設計案の提示（クラス構成・API インターフェース案）、(3) 承認（Go サイン）後に初めてコーディング、の順を踏む。
- 人間の開発者は、軽微なバグ修正・リファクタリング・ドキュメント更新は事前の設計承認なしで実装・コミットしてよい。大規模な機能追加や既存のスキーマ・アーキテクチャに影響する変更は設計案の合意を経てから進める。
- コードは実務経験3〜5年のプログラマが無理なく読めるレベルを基準とする（AI・人間共通）。
- 原則1: 標準 API・定番パターンを優先する。Stream・ラムダ式は積極的に使ってよいが、`reduce` の多重ネストや `Collectors.teeing` のような低頻度メソッドは避ける。TypeScript では高度な型パズルを避ける。
- 原則2: 変数名・メソッド名・クラス名・Enum 値名を仕様書の用語と一致させる。略語は業界標準（`id`, `url`, `dto` 等）に限り、プロジェクト固有の略語は作らない。Boolean を返すメソッドは `is〜` / `has〜` / `can〜` で始める。
- 原則3: ビジネスルールの分岐（Why）、複数テーブルを跨ぐクエリ・集計、パフォーマンス上直感的でない書き方、外部サービス連携の前提・制約には必ず日本語コメントを書く。コードを読めば自明なことにはコメントを付けない。
- 原則4: メソッドは「バリデーション → データ取得 → ビジネスロジック → 結果返却」の流れを一貫させ、1メソッド1仕事とし、途中で目的が変わるなら分割する。
- 原則5: 付随通知は業務コミット後に起動する。業務サービスから通知 Runner（`REQUIRES_NEW`）を直接呼ばない。正規形は「業務 TX でイベント publish → `AFTER_COMMIT` + `@Async("event-pool")` の配送リスナー → `NotificationDeliveryRunner#sendOne()`（1件ごと `REQUIRES_NEW`）」。複数受信者はリスナーから Runner を1件ずつ呼ぶ。
- 原則5: 配送リスナーは `@Async("event-pool")`、`NotificationDispatchService#dispatch` は `@Async("notification-dispatch-pool")` に固定する（executor 無指定にしない）。visibility deny（`createNotification` が `null`）は WARN、例外は ERROR とログを分ける。Runner の内部で例外を catch して監査ログを書かない（境界は非 TX の Async リスナー側の try/catch）。削除済み行を参照するソースで `AFTER_COMMIT` 通知を発火しないよう、`ContentVisibilityChecker` の Resolver 実在を確認してから使う。
- 原則5-1: 付随通知は業務 TX 内では「イベント発行だけ」を行い、実通知は明示的な `AFTER_COMMIT` 境界の後、または項目 TX 完了を待つ非トランザクションのバッチオーケストレータからのみ実行する。`@Async` / `REQUIRES_NEW` / `NOT_SUPPORTED` 単独は `AFTER_COMMIT` の代用とみなさない。`@Async` メソッドの同一クラス内自己呼び出しは失効するので別 Bean へ切り出す。
- 原則5-1: 監査済み例外（クラス粒度・自身のみ対象外・メソッド粒度の各リスト）は本文のリストに限る。免除はクラス単位にしてはならず、前提条件つきの許可（`AUDITED_EXCEPTION_METHODS` のメソッドは `NOT_SUPPORTED` / `NEVER` / `@Async` の宣言が必須。`REQUIRES_NEW` は不可）。
- 原則5-1: 番人 `NotificationTransactionBoundaryGuardTest` は許可された入口のホワイトリスト構造で判定し、既存の負債を `notification_tx_boundary_freeze.txt` に凍結する（増加は常に CI fail、減少は該当実装差分と同じ PR のみ）。検出件数は実態の下限（別 Bean への委譲追跡は1ホップ限定）であり、0 件でも負債が無いとは読まない。baseline を減らすときは、偽陽性なら `# REMOVED:` 台帳行を足し、実際に是正したなら同じ PR で `# CENSUS_FLOOR` を下げる。
- 原則5-2: 通知 API は必ず引数（宛先・種別など）を取り、引数ゼロの通知 API を作らない。通知をメソッド参照（`notificationHelper::notify` 等）で遅延させない。配送層に新しい `createNotification*` API を足したら番人の語彙 `NOTIFY_METHOD_VOCABULARY` にも足す（語彙を開いた正規表現にしない）。
- 判定不能（曖昧）も是正対象として凍結ファイルの `# AMBIGUOUS:` 行に載せ、総数を `# CENSUS_FLOOR` に算入する。凍結エントリの影響区分（`ROLLBACK_COUPLED` / `ORDERING_ONLY`）はソースの実注釈と機械照合され、一度付けた分類は `# CLASSIFIED_FLOOR` で外せない（増やしたら同じ PR で下限も上げる）。

## 18. Flyway マイグレーション SQL スタイル規約

- migration を追加・変更したら E-R 図を再生成してコミットする（`cd backend && ./gradlew generateErDiagrams`。CI の ER Diagram Drift Check が検出）。
- ファイル名は `V{major}.{yyyyMMddHHmmss}__{説明}.sql`。major は「origin/main 全体の最大 major + 1」を使い、PR 作成前に最大 major を確認して他 PR と被ればリネームする。同一 major 内の並行 PR 衝突は minor（タイムスタンプ）で回避する。連番 minor は禁止。
- タイムスタンプは `date -u '+%Y%m%d%H%M%S'`（bash / WSL2）または `Get-Date -Format 'yyyyMMddHHmmss'`（PowerShell）で取得する。Flyway は major と minor を数値で別々に比較するため、小さい major に大きな minor を付けても後には実行されない。
- 既存の `V{phase}.{連番}__*.sql` は変更しない。`FlywayLegacyMigrationBaseline` の凍結リストへの追記は禁止。番人 `FlywayTimestampNamingGuardTest` が新規ファイルの連番 minor とバージョン重複を拒否する。新規 migration 追加後は `FlywayFromScratchMigrationTest` が CI で通ることを確認する。
- SQL キーワードは大文字、テーブル名・カラム名は小文字 snake_case（§10）。1ファイル＝1つの論理的変更。
- テーブル作成時は冒頭に作成意図のコメントを書く。DELETE / DROP / `ALTER TABLE ... DROP COLUMN` を含む破壊的 migration はファイル冒頭に警告コメントを書く。
- 制約・インデックスの命名: 外部キー `fk_{テーブル名}_{参照先テーブル名}`、インデックス `idx_{テーブル名}_{カラム名}`、ユニーク制約 `uq_{テーブル名}_{カラム名}`。
- `IF NOT EXISTS` と `IF EXISTS`（DROP 時）は付けない（禁止）。
- Entity に列を足したら migration も必ず足す。`FlywayFromScratchMigrationTest` の番人（全 Entity のマッピング列が Flyway 実スキーマに存在すること）に、Flyway 実スキーマを要する番人は相乗りさせ、新クラスを作らない。`KNOWN_UNPAID_DRIFT` は空を維持し、赤になったら台帳へ追記せず migration（`ALTER TABLE ... ADD COLUMN`、既存データ環境向けは冪等）で返済する。新規テーブルでは `created_at` / `updated_at` を必ず作る。`s3Key` / `positionX` のように命名戦略で `s3_key` / `position_x` にならないフィールドは `@Column(name = "...")` を明示する。
- 【必須】migration の DML で「今」を書くときは UTC 系関数を使う: `UTC_TIMESTAMP()`（`NOW()` / `SYSDATE()` / `CURRENT_TIMESTAMP` / `LOCALTIMESTAMP` は禁止）、`UTC_DATE()`（`CURDATE()` / `CURRENT_DATE` は禁止）、`UTC_TIME()`（`CURTIME()` / `CURRENT_TIME` / `LOCALTIME` は禁止）。番人 `FlywayMigrationTimeFunctionGuardTest` が新規追加を拒否し、凍結台帳 `session_tz_time_function_freeze.txt` への追記は禁止。列 DEFAULT / ON UPDATE の `CURRENT_TIMESTAMP` は対象外。既存 migration は書き換えない（チェックサム不一致のため）。

詳細・コード例・経緯: [docs/conventions/backend/18-flyway-sql-style.md](../docs/conventions/backend/18-flyway-sql-style.md)

## 19. DTO 粒度ルール

### Request（リクエスト）
- **Create と Update は原則として分ける**:
    - `Create[Feature]Request` → 作成時の必須フィールドのみ（例: email, password, name）
    - `Update[Feature]Request` → 変更可能フィールドのみ（例: name, displayName）
- **理由**: バリデーションルールが異なるため、共用すると `@NotBlank` と nullable が混在して複雑になる

### Response（レスポンス）
- **一覧用と詳細用を分ける**:
    - `[Feature]SummaryResponse` → 一覧表示に必要な最小限（id, name, avatarUrl 等）
    - `[Feature]DetailResponse` → 詳細画面用（全フィールド + リレーション情報）
    - `[Feature]Response` → 上記の区別が不要な場合（小さいエンティティ）

### 共通ルール
- DTO は feature パッケージ内の `dto/` サブパッケージに配置する
- **エンティティを直接レスポンスに返すことは禁止**（必ず DTO に変換する）
- DTO のフィールドは不変（`final` + `@Getter`、`@Setter` なし）とする（`BACKEND_CODING_CONVENTION.md` §1 Lombok 規約と統一）
- ネストが必要な場合は Inner class ではなく別ファイルに切り出す

## 20. 日時の扱い統一

- DB の日時カラムは `DATETIME`（`TIMESTAMP` は使わない）、日付のみは `DATE`。DB に格納する値は UTC 壁時計で統一する（`spring.jpa.properties.hibernate.jdbc.time_zone: UTC`）。
- 二層モデル: アプリ層（`LocalDateTime`）は JST（JVM 既定 TZ を `TimeZoneConfig` が `Asia/Tokyo` に固定）、DB 格納値は UTC。両者を混同しない。Hibernate 経由の読み書きは往復無損失で、API・FE の契約（JST 前提の ISO 8601 文字列）は変わらない。
- Hibernate を通さず DB を直接触る経路（ネイティブクエリの `NOW()` / `CURRENT_TIMESTAMP` / `CURDATE()`、`CONVERT_TZ()` の変換元、テスト・seed の文字列リテラル INSERT）は必ず UTC 基準で書く。
- 日時文字列を解釈するコードは必ず `UserZoneLocalDateTimeParser` を使う（規則のコピペ実装は禁止）。`@RequestParam LocalDateTime` は `WebMvcConfig#addFormatters` の `addFormatterForFieldType` 登録で扱い、`addFormatterForFieldAnnotation` は使わない。解釈不能入力は 400 とし、握り潰しも無音フォールバックもしない。
- 受信側の解釈規則: オフセット付きは瞬間として解釈して Asia/Tokyo の壁時計へ変換、オフセット無しでユーザー TZ が解決済み（`TimezoneContextHolder.isResolved()`）ならその TZ の壁時計、未解決なら Asia/Tokyo の壁時計（恒等変換）。`setResolved(zone)` は `users.timezone` を実際に引き当てたときだけ使う。
- java.time 型のシリアライザだけを足さない。カスタムしたら対になるデシリアライザも同じ `SimpleModule` に登録する（`JacksonTimeTypeSymmetryGuardTest` が拒否）。`TimeZoneConfig` を変えるならシリアライザ（`ZoneId.systemDefault()`）とデシリアライザ（定数 `SERVER_ZONE`）の両方を同時に変える。
- 環境側の TZ 設定を UTC に揃える（ローカル `docker-compose.yml` は `--default-time-zone=+00:00`、`application-local.yml` / `application-ci.yml` は `serverTimezone=UTC`、本番は RDS `time_zone=UTC` ＋ JDBC `serverTimezone=UTC`）。番人 `TimeZoneStorageBasisGuardTest` が固定している。
- Java: 裁可済みの日時方針（`docs/architecture/datetime_policy_utc_instant_vs_wallclock.md`）に従い、新規の「起きた瞬間」は `Instant` / `OffsetDateTime` で UTC 保持する。土地の約束（壁時計）は `LocalDate` / `LocalTime` ＋店・チームの TZ で保持し、壁時計そのものを UTC 化しない。新規コードで瞬間と壁時計を混同する型として `LocalDateTime` を追加せず、既存フィールドの一括変更はしない。
- JVM のデフォルト TZ は起動時に `Asia/Tokyo` に設定する（`com.mannschaft.app.config` の `TimeZoneConfig`）。JST 固定を外すと API の日時表現まで変わるため、格納基準とは独立に扱う。
- Jackson は `spring.jackson.serialization.write-dates-as-timestamps: false` を `application.yml` に必ず設定し、`LocalDateTime` を配列ではなく ISO 8601 文字列で出す。
- FE: API レスポンスの日時は ISO 8601 文字列で受け取り、表示フォーマットは dayjs に統一する。

詳細・コード例・経緯: [docs/conventions/backend/20-datetime.md](../docs/conventions/backend/20-datetime.md)

## 22. 楽観的ロック（Optimistic Locking）

複数ユーザーが同時に同じデータを編集する可能性がある主要エンティティには、楽観的ロックを適用する。

### 実装方式
- JPA の `@Version` アノテーションを使用する。対象エンティティに `version` カラムを追加する:
```java
@Version
private Long version;
```
- DB 側のカラム定義:
```sql
version BIGINT NOT NULL DEFAULT 0
```

### 適用対象
以下のように「複数ユーザーが同時編集しうるデータ」に適用する:
- **適用する**: `schedules`, `bulletin_threads`, `bulletin_replies`, `blog_posts`, `teams`, `organizations`, `user_profiles`, `service_records` 等の主要業務データ
- **適用しない**: `audit_logs`, `notifications`, `login_histories` 等のログ系テーブル、`user_roles` 等の中間テーブル、カウンタ系カラム（`member_count` 等、アトミック更新で制御するもの）

### 競合時のハンドリング
- Spring Data JPA が `ObjectOptimisticLockingFailureException`（JPA の `OptimisticLockException` をラップした Spring 例外）をスローするので、`GlobalExceptionHandler` でキャッチして **409 Conflict** を返す:
```java
// GlobalExceptionHandler に追加
@ExceptionHandler(ObjectOptimisticLockingFailureException.class)
public ResponseEntity<ErrorResponse> handleOptimisticLock(ObjectOptimisticLockingFailureException ex) {
    ErrorResponse error = ErrorResponse.of(CommonErrorCode.COMMON_003);
    return ResponseEntity.status(HttpStatus.CONFLICT).body(error);
}
```
- エラーコード: `COMMON_003`（「他のユーザーがデータを更新しました。最新の内容を確認して再度お試しください」）
- フロントエンドは 409 を受け取った場合、最新データを再取得してユーザーに差分を提示する

### API での version の受け渡し
- **Response**: 全ての詳細レスポンスに `version` フィールドを含める
- **Request**: Update 系リクエストに `version` フィールドを必須とする
```java
public class UpdateBulletinThreadRequest {
    @NotNull
    private Long version;  // 取得時の version をそのまま返す
    // ... 他のフィールド
}
```

## 23. Enum の DB 保存方式

### ルール
- **`@Enumerated(EnumType.STRING)` を必須とする**。`ORDINAL`（数値保存）は禁止する
```java
@Enumerated(EnumType.STRING)
@Column(nullable = false)
private RoleType roleType;  // DB には "ADMIN", "MEMBER" 等の文字列で保存
```

### 理由
- `ORDINAL` は Enum の定義順序に依存するため、途中に値を追加すると既存データの意味が変わる致命的バグになる
- `STRING` なら Enum の順序変更で既存値の意味は変わらない。DB を直接見たときも値が分かりやすい
- **定数追加は旧バイナリとの読取り互換性を壊し得る**。定数だけを全タスクへ配布し、新定数を書かない第1段階 → 旧タスク退場を確認 → 新定数を書き始める第2段階、の順に展開する。書込み開始後のrollback下限は第1段階とする
- 詳細とPR／リリース記録の作法は [`docs/development/persisted_enum_deployment.md`](../docs/development/persisted_enum_deployment.md)。番人 `PersistedEnumCompatibilityArchTest` がSTRING永続化enumの定数追加・削除を互換性台帳との比較で検知する（CIの緑は二段階展開の実施証明ではない）

### DB 側のカラム定義
- MySQL の `ENUM` 型は使わない。**`VARCHAR`** で定義する:
```sql
role_type VARCHAR(30) NOT NULL  -- "ADMIN", "MEMBER", "GUEST" 等
```
- 理由: MySQL の `ENUM` 型は値の追加に `ALTER TABLE` が必要で、Flyway マイグレーションが煩雑になる。`VARCHAR` は列長・CHECK制約が許す限り値追加で列型の変更を要しない。ただし、定数の追加と書込み開始は上記の二段階で展開する

### CHECK 制約（任意）
- 値の整合性を DB 側でも担保したい場合は CHECK 制約を付与する:
```sql
role_type VARCHAR(30) NOT NULL,
CONSTRAINT chk_user_roles_role_type
    CHECK (role_type IN ('SYSTEM_ADMIN', 'ADMIN', 'DEPUTY_ADMIN', 'MEMBER', 'SUPPORTER', 'GUEST'))
```

## 24. Valkey キー命名規約・TTL 方針

### キー命名フォーマット
```
mannschaft:{用途}:{スコープ}:{識別子}
```

| 用途 | キーパターン | 例 | TTL |
|------|-------------|-----|-----|
| JWTブラックリスト | `mannschaft:auth:blacklist:{jti}` | `mannschaft:auth:blacklist:abc123` | Access Token の残存有効期限 |
| Refresh Token | `mannschaft:auth:refresh:{userId}:{deviceId}` | `mannschaft:auth:refresh:42:mobile` | 7日 |
| レートリミット | `mannschaft:rate:{endpoint}:{ip}` | `mannschaft:rate:login:192.168.1.1` | 1分 or 1日（エンドポイントによる） |
| キャッシュ（ユーザー） | `mannschaft:cache:user:{userId}` | `mannschaft:cache:user:42` | 30分 |
| キャッシュ（チーム） | `mannschaft:cache:team:{teamId}` | `mannschaft:cache:team:7` | 30分 |
| キャッシュ（モジュール定義） | `mannschaft:cache:modules` | — | 1時間（更新頻度が低い） |
| WebSocket セッション | `mannschaft:ws:session:{sessionId}` | `mannschaft:ws:session:sess_xyz` | 接続中のみ（切断時に削除） |
| 非同期ジョブ進捗 | `mannschaft:job:{jobType}:{jobId}` | `mannschaft:job:export:job_456` | 24時間 |

### ルール
- キーの区切りは **コロン（`:`）** を使う（Redis 互換の慣例、`valkey-cli` でのキースペース分析に対応）
- **全て小文字**で統一する
- TTL は必ず設定する（TTL なしのキーが蓄積するとメモリリークになる）
- キャッシュの無効化はデータ更新時に明示的に `DELETE` する（TTL 切れに頼らない）。Service の CUD メソッド内で対応するキャッシュを削除すること

### Spring Boot での設定
```java
// RedisConfig.java に TTL のデフォルト値を定義
@Bean
public RedisCacheConfiguration cacheConfiguration() {
    return RedisCacheConfiguration.defaultCacheConfig()
        .entryTtl(Duration.ofMinutes(30))  // デフォルト TTL
        .serializeValuesWith(
            SerializationPair.fromSerializer(new GenericJackson2JsonRedisSerializer())
        );
}
```

## 25. API の HTTP ステータスコード使い分け

### 成功系

| ステータス | 使用場面 | 例 |
|-----------|---------|-----|
| **200 OK** | データの取得・更新が成功 | `GET /users/me`, `PATCH /users/me` |
| **201 Created** | 新しいリソースの作成が成功 | `POST /teams` |
| **204 No Content** | 削除が成功（レスポンスボディなし） | `DELETE /teams/{id}` |

### エラー系

| ステータス | 使用場面 | エラーコード例 |
|-----------|---------|--------------|
| **400 Bad Request** | バリデーションエラー、リクエスト形式不正 | `COMMON_001` |
| **401 Unauthorized** | 認証失敗、トークン無効・期限切れ | `AUTH_001`, `AUTH_002` |
| **403 Forbidden** | 認証済みだが権限不足 | `COMMON_002` |
| **404 Not Found** | 指定リソースが存在しない | `{FEATURE}_001` 等 |
| **409 Conflict** | 楽観的ロック競合、一意制約違反 | `COMMON_003` |
| **429 Too Many Requests** | レートリミット超過 | — （`Retry-After` ヘッダーを付与） |
| **500 Internal Server Error** | 予期しないシステムエラー | `COMMON_999` |
| **503 Service Unavailable** | 未実装機能へのアクセス（フィーチャーフラグ OFF） | — |

### ルール
- **更新（PATCH/PUT）は 200** + 更新後のリソースをレスポンスボディに含める
- **作成（POST）は 201** + 作成されたリソースをレスポンスボディに含め、`Location` ヘッダーに新リソースの URI を設定する
- **削除（DELETE）は 204** + レスポンスボディは空。ただし**論理削除**の場合は **200 OK** + `deleted_at` 等の情報をレスポンスボディに含めてよい（クライアント側で削除日時の確認・表示に利用するため）
- **一覧取得で結果が0件の場合は 200** + 空配列（404 にしない）

## 26. ファイルアップロードフロー（Pre-signed URL）

フロントエンド → バックエンド → S3 の3者間のシーケンスを以下に統一する。

### アップロードフロー（3ステップ）
```
1. [Frontend] → POST /api/v1/{feature}/upload-url
   Request:  { "fileName": "report.pdf", "contentType": "application/pdf", "fileSize": 2048000 }
   Response: { "data": { "uploadUrl": "https://s3...", "fileKey": "uploads/teams/7/abc123.pdf", "expiresIn": 600 } }

2. [Frontend] → PUT {uploadUrl}  (S3に直接アップロード)
   Headers:  Content-Type: application/pdf
   Body:     <ファイルバイナリ>

3. [Frontend] → POST /api/v1/{feature}  or  PATCH /api/v1/{feature}/{id}
   Request:  { "title": "月次報告", "attachmentKey": "uploads/teams/7/abc123.pdf", ... }
   ※ バックエンドは fileKey の存在を S3 に確認してからDBに保存する
```

### バックエンド側の処理
- **ステップ1（URL発行）**:
    - `contentType` のホワイトリスト検証（許可: `image/jpeg`, `image/png`, `image/webp`, `application/pdf` 等。機能ごとに定義）
    - `fileSize` の上限チェック（機能ごとの上限。例: 掲示板添付は 6MB）
    - `fileKey` はUUIDベースで生成し、推測不可能にする: `uploads/{feature}/{scopeId}/{uuid}.{ext}`
    - Pre-signed URL の有効期限は **10分**（§ストレージ規約の5〜15分に準拠）
- **ステップ3（リソース登録）**:
    - `fileKey` が S3 に実在するかを `HeadObject` で確認する（偽のキーでの登録を防止）
    - 確認後に DB にレコードを保存する

### ダウンロードフロー
```
1. [Frontend] → GET /api/v1/{feature}/{id}/download-url
   Response: { "data": { "downloadUrl": "https://s3...", "expiresIn": 300 } }

2. [Frontend] → GET {downloadUrl}  (S3から直接ダウンロード)
```
- ダウンロード用 Pre-signed URL の有効期限は **5分**
- アクセス権限チェックはステップ1でバックエンドが行う（S3 は URL を知っていれば誰でもアクセス可能なため）

### 未使用ファイルの清掃
- ステップ1で URL を発行したがステップ3が行われなかったファイル（孤立ファイル）は、日次バッチで `uploads/` 配下を走査し、DBに紐付かないファイルを削除する
- バッチ対象: アップロードから **24時間** 経過 かつ DB 未登録のファイル

## 27. 構造化ログフォーマット

- 本番環境は JSON 形式、開発環境は人間が読みやすいテキスト形式で出力する。
- Logback の `logstash-logback-encoder` を使い、`logback-spring.xml` では appender と `<root>` を必ずセットで定義する（appender だけでは出力されない）。`prod`（JSON・INFO）・`local`（テキスト・DEBUG）・`test`（テキスト・WARN）の各 `springProfile` を持つ。
- 全リクエストで `requestId` / `userId` / `traceId` を MDC に設定してログへ自動付与する（JSON は `includeMdcKeyName` で出力）。
- `requestId` はリクエストごとに UUID を生成（`X-Request-Id` ヘッダーがあればそれを使用）し、`OncePerRequestFilter`（`RequestLoggingFilter`、`com.mannschaft.app.config`）で設定する。`traceId` は現時点では `requestId` と同値でよい。
- `userId` は Spring Security の認証処理完了後に、認証フィルター内（`SecurityContextHolder` から取得）で別途設定する（未認証時は `anonymous`）。`RequestLoggingFilter` では設定しない。

## 28. チーム運用規約（マスター・殿様・家老・足軽モデル）

- 報告は時代劇口調で統一する。四層（マスター＝ユーザー／殿様＝メイン Claude／家老＝`Plan`・`Explore`／足軽＝`Agent(worktree)`）で進める。
- 禁止事項: 殿様はマスターの承認なきコミット・プッシュ、家老は殿様の許可なき設計変更、足軽は設計判断と他の足軽の担当領域への変更。
- 殿様が独断で決めてよいのは、軍議指示・タスク分解の承認、足軽の起動順・並列度、軽微なコーディング判断、軽微な問題の修正指示、差し戻し・再実装の指示。
- マスターへ上奏するのは、フェーズ着手の承認、仕様の矛盾・曖昧さ、設計方針の重大な分岐、進軍不能なエラー、成果物のコミット・プッシュ（最終御裁可）、`.claudecode.md` や仕様書の変更が必要な場合。
- ワークフロー: 軍議（`/軍議`・設計）→ 試練（`/試練`・受け入れ条件から失敗するテストを実装より先に作成。詳細は CLAUDE.md『大名システム活用ルール』）→ 出陣（`/出陣`・実装。各足軽は担当範囲のみ実装し越権禁止）→ 検分（`/検分`・家老が検分、合格なら殿様が戦果上奏、御裁可後にコミット）。
- 品質ゲート（検分基準）: コンパイルエラーなし、規約準拠、対応するテストが存在し全パス、家老の陣立て書どおり（設計逸脱なし）、OWASP Top 10 の穴なし、仕様書との矛盾なし。
- worktree 運用: 各足軽は `isolation: "worktree"` で起動する。足軽間に依存があれば家老が順次起動する。コンフリクトは家老が調停し、足軽同士で直接やり取りしない。メインブランチへの取り込みは殿様がマスターの御裁可を得た後。
- エスカレーション: 足軽→家老→殿様→マスターの順。仕様の矛盾や `.claudecode.md`・仕様書の変更は殿様がマスターに上奏する。
- Dynamic Workflows（Workflow ツールが提供される環境のみ。オプトイン）: 軍議・早馬は対話のまま、承認ゲートは Workflow の外に置く、モデル/effort はスクリプトで固定（機械的な足軽は sonnet/haiku・low、難所は opus・medium、詰まったら high、`max` 不使用）、足軽は `isolation:'worktree'` 必須、コミット/マージは Workflow 内禁止（御裁可後に殿が `gh` で行う）。

詳細・コード例・経緯: [docs/conventions/backend/28-team-operations.md](../docs/conventions/backend/28-team-operations.md)

## 30. アーキテクチャ番人テスト（ArchUnit FreezingArchRule）

- `com.mannschaft.app.common.architecture` の ArchUnit 番人テスト（認可・D-1 クロスドメイン Entity 参照・D-3 越境 `@Transactional`・D-2b `UuidV7Entity` 継承・D-5 越境 Repository 依存・D-6 Controller の Entity レスポンス・D-7 リクエスト DTO の実体生成可否）と、ソース走査型の番人（`ErrorCodeHttpStatusDeclarationGuardTest` / `IntentionallyPublicMatcherGuardTest` / `BatchMarkerAnnotationGuardTest` / `FlywayTimestampNamingGuardTest` / `ArchUnitFreezeStoreIntegrityTest` ほか）が機械的に強制している。D-6 / D-7 を除き `FreezingArchRule`（`freeze.refreeze=false`）で、既存違反は `backend/src/test/resources/archunit_store/` に凍結し新規違反のみ fail させる。D-6 / D-7 は凍結を持たず違反 1 件で即 fail する。
- ErrorCode: `ERROR_CODE_STATUS_MAP` に未登録のコードは `Severity` 既定（WARN=400 / ERROR=500）へフォールバックする。Javadoc 等で宣言した HTTP ステータスと実挙動を一致させ、存在秘匿（`IDOR` / `BOLA` を含む宣言）は 404 または 403 に解決させる。例外は `DECLARATION_EXCEPTIONS` に集約し各エントリに理由を必須とする。
- `@IntentionallyPublic` は行番号ではなく `SecurityConfig` の matcher 式（例 `@IntentionallyPublic("/api/v1/public/stats")`）で引用する。公開してよいと判断した理由の Javadoc は必ず残す。
- D-7: リクエスト DTO は採用可能な creator が一意でなければならない（コンストラクタ 2 本以上＋引数無しコンストラクタ無しは常時 500）。是正は `chat/dto/SendMessageRequest` を金型に、完全コンストラクタへ `@JsonCreator` ＋各引数 `@JsonProperty("...")` を付ける（独自の工夫をしない）。コンストラクタ 1 本の DTO は不要（2 本目を足すと壊れる）。フォーム経路（`@ModelAttribute`）では `@JsonCreator` は効かない。
- §30.1 バッチ（`@Scheduled`）の規約（`ScheduledBatchGuardTest` が強制）: (1) `@SchedulerLock` 必須（例外は `@PodLocalScheduled` のみ）、(2) `lockAtMostFor` 明示必須、(3) `@BatchEndpoint` 必須（例外は `@BatchEndpointExempt` のみ）、(4) 起動間隔 1 時間以下の短周期バッチは `lockAtMostFor` > 起動間隔（同値も不可。算出できない `${prop}` は落ちるので既定値付きで書く）、(5) `@SchedulerLock` 付きメソッドはプリミティブ戻り値禁止（`void` か参照型にする）。例外マーカー 2 種は `value()` の理由リテラル＋対象メソッドの Javadoc が必須で、免除リストは無い。凍結ストアは使わない。
- `lockAtMostFor` の決め方: 短周期バッチは間隔の 3 倍を基本（15 分〜1 時間は 2 倍）、日次・週次・月次は最悪ケースの処理時間の見積もりを根拠コメントとして日本語で残す。`name` は `shedlock` テーブルの主キーなので全バッチで一意（付与前に grep で確認）。使用量・カウンタの read-modify-write は条件付き DELETE の戻り値（実削除行数）で引く（claim-then-act）。
- 認可番人の監査済マーカー 4 種（`@SelfScopedEndpoint` / `@AuthorizedInService` / `@AuthorizedByPathConfig` / `@IntentionallyPublic`）は主張ごとに分離されており、実態と異なるマーカーを貼ってはならない。`@SelfScopedEndpoint` はメソッドのみに付け、`@AuthorizedInService` を流用せず、`value()` にその場で読める文字列リテラルの根拠を書き、他ユーザーから到達できないことを固定する契約テスト（Javadoc または `@DisplayName` に `<Controller 単純名>#<メソッド名>` を明記）を用意する。要件を満たせないなら貼らない（免除リストは無い）。
- 本番全体（`com.mannschaft.app`）の ArchUnit 取り込みは `ProductionClasses.get()` だけを使う。一部が要るときもホルダから引いてルール側で絞る（`importPath` / `importClasspath` は禁止）。テストクラスの `JavaClasses` 型 static フィールドは禁止（番人 `ProductionClassImportGuardTest`）。
- ArchUnit（`com.tngtech.archunit.*`）または `ProductionClasses` を参照するテストクラスはタグ必須（Jupiter は `@Tag(ArchUnitTestTag.ARCHUNIT)`、`@AnalyzeClasses` は `@ArchTag(ArchUnitTestTag.ARCHUNIT)`）。タグ付きテストは Spring のテストコンテキストを使わず、`shard-weights.properties` に載せない（番人 `ArchUnitTestTagGuardTest`）。Jupiter 側は専用タスク `archTest`（別 JVM）、`@AnalyzeClasses` 側は `archUnitTest` で走る。ローカル確認は `./scripts/gradle-turnstile.sh ./gradlew archTest --tests "<完全修飾名>"`（`@AnalyzeClasses` のクラスを `archTest --tests` に指定しない。そちらは `archUnitTest`）。
- Spring テストコンテキストキャッシュ上限は 10（`spring.test.context.cache.maxSize`。応急の上限で、番人 `SpringTestContextCacheMaxSizeGuardTest`）。
- ⚠️ ArchUnit 番人テストを含むテストクラスを `--tests` で絞り込んではならない（凍結ストアから「今回検出されなかった違反」が誤って削除される）。確認はフルの `./gradlew test` か `compileTestJava` に留め、実行は CI に委ねる。`ArchUnitFreezeStoreIntegrityTest` が凍結ストアの行数を `EXPECTED_LINES_*`（上限）と照合する。返済 PR は定数を変更せず減少行と返済内容を本文で照合し、上限の引き下げは締めレーンが履歴（`docs/architecture/archunit_freeze_history.md`）とともに行う。`backend/src/test/resources/archunit_store/` は CODEOWNERS でオーナーレビュー必須。
- 新 rule の導入は、設計・初回違反の裁可・UUID/store/guard 登録を同じ変更で検分し、`allowStoreCreation=false` / `refreeze=false` を維持する（常時 creation/refreeze を有効にして新違反を無断凍結しない）。D-1 / D-3 / D-5 は依存ごとに `[occurrence=N]` を付けて全行を一意にする。D3 / D3T は `@Transactional` 注釈入口のみ検出し、programmatic `TransactionTemplate` は網羅しない（新規変更は実境界・caller・裁可を検分する）。診断原本（CI の XML artifact）と store 更新は分離し、未実行 store の未変化を実解析成功へ転用しない。

詳細・コード例・経緯: [docs/conventions/backend/30-arch-guard-tests.md](../docs/conventions/backend/30-arch-guard-tests.md)

## §XX ローカルアバター/画像保存 — MinIO（profile `storage`）

ローカル開発環境では Cloudflare R2 が使えないため、S3互換の MinIO を使ってアバター・バナー画像の
presigned URL フロー（`/api/v1/*/profile-media` EP）を動作確認できる。

### 起動手順

1. MinIO を起動（通常の `docker compose up -d` には含まれない）:
   ```bash
   docker compose --profile storage up -d
   ```
   - API ポート: `9000`
   - Console UI: http://localhost:9001（ユーザー: `minioadmin` / パスワード: `minioadmin`）
   - バケット `mannschaft-storage` は `minio-init` コンテナが自動作成する

2. `backend/src/main/resources/application-local.yml` に以下が設定されていることを確認:
   ```yaml
   mannschaft:
     storage:
       endpoint: http://localhost:9000
       access-key: minioadmin
       secret-key: minioadmin
       bucket: mannschaft-storage
   ```
   既定値として設定済みのため、環境変数の上書きなしで MinIO に接続できる。

3. Spring Boot を再起動（ローカルプロファイル）:
   ```bash
   cd backend && ./gradlew bootRun
   ```

4. `/settings/profile` でアバター画像を選択し、アップロードが成功することを確認する。

### 注意事項

- MinIO はローカル開発専用。本番は Cloudflare R2（`MANNSCHAFT_R2_*` 環境変数）を使用。
- ブラウザからの presigned PUT に必要な CORS（`http://localhost:3000`/`3001`）は
  `MINIO_API_CORS_ALLOW_ORIGIN` で許可済み。
- MinIO Console でバケット内容を確認できる（http://localhost:9001）。

## 31. CI テストシャードの重み付け振り分け

- 6 shard の matrix で分割し、`shard-weights.properties`（クラス単位の実測秒数）があれば貪欲法（LPT）でトップレベルクラスを割り付け、載っていないクラス（新規テスト等）は完全修飾クラス名の安定ハッシュへフォールバックする。重み表ファイルが無ければ全クラスがハッシュ方式。
- 貪欲法は「実際にその CI 実行で走るクラス集合」に対して行う（`-PexcludeMigrationTests=true` の場合は migration+Flyway クラスを事前に除外してから均等化する）。
- 割り付け・判定ロジックは `build-logic` の `ShardAssignment` に一本化し、実際のテスト実行時の `Test.exclude { }` と `verifyShardCoverage` の両方が同じ述語（`shouldExcludeForShard()` / `shouldExcludeMigrationReplay()`）を呼ぶ。呼び出し側で別実装の再計算や外側での `!` 反転をしない。
- 検証は `cd backend && ./gradlew verifyShardCoverage -Pshard.total=6`（各クラスがちょうど 1 shard、migration 除外時に migration+Flyway クラスが非実行、ネストクラスが同じ shard、を 4 プロファイルで assert）。CI では `shard-coverage-guard` ジョブが 1 回だけ実行し `gate` の needs に含まれる。
- 実時間の採取は `scripts/run-ci-tests-with-observability.sh` を共用する。重みの一次入力は通常 `:test` の class suite 開始/終了間の実時間（ミリ秒）で、JUnit XML の `testsuite.time` や MFA 内部計測値とは同一視しない。未実行・timeout・terminal 欠損は `completed=false` / `testStepExitCode=null` とし、採取欠損を green や高速化の証拠にしない。
- 重み表の再生成は、テストクラス数が数十クラス規模で増減したとき、または特定 shard が恒常的に偏るときに行う。数クラス程度の増減は不要。手順は `cd backend && ./scripts/regen-shard-weights.sh`（`gh` CLI 必須。既定で `backend-nightly-full.yml` の直近成功 run の runtime artifact から再構築。`backend-ci` は拒否）。不正・欠損時は出力を変えず、XML へ fallback しない。生成後は 4 profile の coverage guard を実行し、回帰検証は `python3 -m unittest scripts/test_regen_shard_weights.py`。

詳細・コード例・経緯: [docs/conventions/backend/31-ci-shard-weighting.md](../docs/conventions/backend/31-ci-shard-weighting.md)

## 32. CI の OOM 調査用証跡（ヒープダンプ・テスト結果XML・JVM実効ヒープログ）

`build.gradle.kts` の Test タスクは `-XX:HeapDumpOnOutOfMemoryError` を指定しており、OOM
発生時に `backend/build/heap-dumps/java_pid<PID>.hprof` へワーカーごとに個別のダンプを書き出す
（固定ファイル名だと複数ワーカーの同時書き込みで巨大な偽ファイルになるため、ディレクトリ指定で
ワーカーごとに分離している）。

- `backend-ci.yml`（PR 側 6-shard）: shard ごとに `if: failure()` でヒープダンプ
  （`heap-dump-pr-<PR番号>-shard-<i>`、保持3日、`if-no-files-found: ignore`）と、
  `if: always()` でテスト結果 XML（`test-results-xml-pr-<PR番号>-shard-<i>`、保持7日）を
  アーティファクトとしてアップロードする。
- `backend-deploy.yml`（main への push）: 2026-10 まで `path: build/reports/tests/`
  （`backend/` を省略した誤ったパス）を指定していたため、`defaults.run.working-directory:
  ./backend` の影響を受けず常に「見つからない」扱いとなり、main 側では一度もテスト結果が
  アップロードされていなかった（CMP-261002-1606 の証跡整備で発覚・修正）。`backend-ci.yml` と
  同じ方式（`heap-dump-main-<run_id>-shard-<i>` / `test-results-xml-main-<run_id>-shard-<i>` /
  `path: backend/build/...`）に揃え、main 側でも PR 側と同等の証跡が残るようにした。
- 各テストワーカー JVM の実効最大ヒープ（`Runtime.getRuntime().maxMemory()`）は、
  `com.mannschaft.app.common.testing.TestJvmHeapLoggingLauncherSessionListener`
  （`org.junit.platform.launcher.LauncherSessionListener` を実装し
  `META-INF/services/org.junit.platform.launcher.LauncherSessionListener` 経由で ServiceLoader
  登録）が CI ログへ `[test-jvm-heap] pid=... maxMemory=...MB` の形式で1行出力する。
  Gradle の `addTestListener`（[test-jvm] 計測器、本ファイル §31 の直前にある build.gradle.kts
  のコメント参照）はビルド側プロセスで動くためワーカー JVM 自身のヒープ設定値を読めないが、
  本リスナーはワーカー JVM の中で起動直後に実行されるため、Gradle 側からは見えない「ワーカーが
  実際に確保した maxMemory」を測れる。CI ログを `[test-jvm-heap]` で grep すれば全ワーカー分を
  一覧できる。

**必ず backend-nightly-full.yml の run を使うこと（backend-ci.yml の通常 PR run は不可）。**
通常の backend-ci.yml PR run は db/migration/** 無変更なら `-PexcludeMigrationTests=true` で
走り、Flyway マイグレーション再生テスト（約70クラス・全実行時間の約8割を占める最重量級テスト群）
が丸ごと除外される。この状態の run から重み表を作ると、最も均等化効果が大きいはずのクラス群が
安定ハッシュ任せに戻ってしまう。backend-nightly-full.yml は毎晩フル実行するため、常に migration
系込みの実測値が揃う。生成後は重み表ヘッダーの「migration+Flyway クラス数」が 0 でないことを
確認したうえでコミットすること。
