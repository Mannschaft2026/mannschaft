# CMP-261103-0823 実機検証記録（友達チームへの投稿転送の存在オラクル是正）

- 修正: PR #4589。`POST /api/v1/teams/{id}/friend-feed/{postId}/forward` で、許可されない転送元（不在・論理削除済み・非フレンド・自チーム・スコープ越境・非共有・下書き・非表示）は、すべて「不在と同じ」`404 SOCIAL_122`（status・エラーコード・本文まで一致）。許可された転送は従来どおり成功し、二重転送は冪等（409 SOCIAL_121）。管理者フィード `GET /api/v1/teams/{teamId}/friend-feed` は TEAM スコープの共有・公開済み投稿だけを出す。仕様は `docs/features/F01.5_team_friend_relationships.md`。試験の写し元は `FriendContentForwardExistenceOracleContractIT`。
- 実施日: 2026-11-18（JST、前日 2026-11-17 夜からの連続作業）。手段: 実 BE への HTTP 実測（契約）と Playwright（Chromium、実ブラウザ・モックなし）による画面操作。
- 環境: BE は **origin/main `51deace6fb`（#4589 を含む）から WSL native で bootJar を新規ビルド**（共通入口 `scripts/verification-run.mjs`、`--no-daemon`）して 8081 で起動。実 MySQL・実 Valkey。CORS は OPTIONS で FE のオリジンが 200 になることを実測。FE は同コミットの作業木（`npm ci`）の dev サーバー。
- 前提データは自前（メール・組織・チーム・投稿に `e2e-og-r30-` / `r30` / `R30` の接頭辞）。投稿の「友達共有」フラグ・状態・スコープは公開 API に変更手段が無いため、**自分が作成した投稿 ID を厳密指定した UPDATE** だけで準備した（ワイルドカードなし）。
- スクリーンショット: `docs/evidence/screenshots/CMP-261103-0823/`

## 登場ロール（ラベルで表す）

| ラベル | 立場 |
|---|---|
| ta | 転送する側のチーム A の代表（ADMIN。転送権限あり） |
| tm | チーム A の一般会員（転送権限なし） |
| fa | チーム A とフレンド関係にあるチーム F の代表（チーム A の権限なし） |
| fm | チーム F の一般会員 |
| oa | 別組織の管理者（チーム A の権限なし） |
| om | oa の組織の一般会員 |
| ob | 他テナントの管理者（チーム C の代表） |
| unauth | 未ログイン |

チーム A と F は相互フォローでフレンド成立。チーム C は A とフレンドではない。転送元の投稿は F の共有・公開済み 3 件（正当）、F の非共有・下書き・非表示・論理削除済み、C の共有、A 自身の共有、組織スコープ（scope_id を F のチーム ID に一致させたもの）の計 10 件を用意。

## 結果（API 契約）

| tm・fa・ob が A のフィードを取得 | 403 SOCIAL_105 |

## 観測（欠陥ではない・記録のみ）

- 共有が取り消された投稿への転送で 404 を受けても、転送モーダルは開いたままで、一覧のカードも古いまま（409 のときは一覧を更新する）。操作者は再度「転送する」を押しても同じ 404 になる。軽微な UX（`CMP-261103-0823-exploratory.md` に記録）。

## 判定

**passed**（許可されない転送元がすべて不在と同じ 404 SOCIAL_122、許可された転送は成功し二重転送は 409、フィードは TEAM スコープの共有・公開済みのみ、権限なし・他テナント・未ログインは画面も API も弾かれる）。
