# CMP-261012-0911 実機E2E・アリシゼーション記録

OAuth ログインが 2FA を迂回する不具合の是正（PR #4677、merge commit e626d31528）について、実機E2E とアリシゼーションの実施記録。個別のユーザー ID・トークン・認証コード・個人情報は記載しない。IP は文書用の 203.0.113.x 等のみ。凡例の「目視」はスクリーンショット画像を実際に開いて確認したもの、「テキスト/API のみ」は画面テキスト・HTTP ステータス・DOM 寸法だけで画像は未確認のもの。

## 実機E2E（2026-11-21・E1〜E6 合格）

- 条件: #4677 のマージコミットから bootJar を作成した検証 BE（本陣 8080 とは別ポート。8080 は終了時も無傷）と、同 commit の FE（Nuxt dev）。Google は偽プロバイダ（ローカル）で代替し、ブラウザ（Playwright・Chrome headless）で「Google でログイン」ボタンを実際にクリックした。EMAIL 方式は既定で無効のため、検証 BE にだけ有効化の設定を付けた。
- 目視したのは E1・E2（TOTP / EMAIL）・E3・E4 の一部のスクリーンショット。他は本文テキストと API ステータスで確認した（テキスト/API のみ）。
- E1（AC-17）: 2FA 無効ユーザーが /login から Google ログインし、POST /api/v1/auth/oauth/google が `?code=` 付き（クエリ送信）で 200、/dashboard へ到達。LOGIN_SUCCESS と refresh_tokens が各 1 件増えた。ダッシュボードのメイン領域は dev 初回コンパイルの loading のままだった（dev 固有）。
- E2（AC-9）: TOTP ユーザーは callback 後 /2fa-verify（primary=TOTP、methods=TOTP,BACKUP_CODE,EMAIL）へ。この時点でトークン保存なし・LOGIN_SUCCESS 増えず。TOTP 入力後に /dashboard。LOGIN_SUCCESS は ip・UA・session_hash が正しく、metadata に method=OAUTH_GOOGLE・mfa=true・mfa_factor=TOTP。EMAIL ユーザーは primary=EMAIL・methods=EMAIL,BACKUP_CODE（TOTP は出ない＝仕様どおり）で完走し mfa_factor=EMAIL。2FA 前に別タブで /dashboard を直打ちすると /login?redirect=/dashboard。
- E3（AC-10）: クエリ無しの /2fa-verify は /login へ。偽セッションでの送信は AUTH_073 で画面は「認証の有効期限が切れました」、トークン保存なし。消費済みセッションの再利用も AUTH_073（単回消費）。
- AC-5（試行上限）: 誤 TOTP を連続すると 1〜4 回目は 400 AUTH_074、5 回目で 429 AUTH_075 となり画面が「試行回数が上限に達しました」に切り替わる。上限はセッションあたり 5 回で、これとは別にユーザー単位で 30 分 10 回の失敗合算でロックされる 2 段構えが設計どおり（回帰テスト OAuthMfaLoginIT で担保）。上限到達後に新しいセッションで再ログインして正しいコードで通ったのは、セッション単位の上限の仕様どおりでアカウントロックは 10 回側で掛かる。
- E4（AC-11）: 所属チーム A のユーザーは自チームの画面・メンバー・監査ログが 200、チーム B の同 URL は API が 403（画面は「情報を取得できませんでした」）。チーム B 所属の EMAIL ユーザーは対称。チーム無しのユーザーは /dashboard のみ表示でチーム URL は 403。/teams の一覧は自チームのみ。
- E5: 未認証で /users/me・/me/teams・チームのメンバー・/auth/2fa/status は 401。MFA セッショントークンを Bearer に使っても、偽 Bearer でも 401。A のセッション＋B の TOTP、B のセッション＋A の TOTP はどちらも AUTH_074 で成立せず、本人は同セッションで成功した。
- E6: パスワード＋TOTP でも 2FA 前は LOGIN_SUCCESS が増えず、完走後は method=PASSWORD・mfa_factor=TOTP で ip・UA・session_hash・refresh_tokens の jti が入る。

### 実機で見つけた点（本 PR の範囲外）

- /teams/<他チーム>/audit-logs は API が 403 なのに画面は「ログがありません」と空表示にする（権限は守られているが誤解を招く。OAuth/2FA とは無関係の既存事象）。
- 1280px 幅で /2fa-verify の 3 要素切替のラベルが折り返す（見た目のみ）。
- TOTP を 30 秒窓の境界付近で入力すると 400 になる事象が 3 回あった（残り 10 秒未満を避けると再現しない。許容窓は現在窓のみの可能性）。

## アリシゼーション（2026-11-21・実機後）

- 住民 2 体: 一般利用者（ja・360px・Google、2FA 未設定から設定画面で有効化して再ログインで 2FA、バックアップコード）と、英語話者（en・360px・Google）。到達できたか、読めるか、詰まらないかを観測した。
- 到達可否: ログイン、ダッシュボード、メニューの「設定」、「アカウント設定」で 2FA セットアップ（QR・シークレット・6 桁）、バックアップコード表示、有効化まで到達できた。「個別設定一覧」から「セキュリティ」へも到達できた。再ログインで /2fa-verify が必ず出て、誤コード、タブを閉じて同 URL を開き直し、バックアップコード（ハイフン可）、ペースト入力のすべてで通過または適切に拒否された。
- 問題なし（確認済み）: 2FA 後のセッション維持（Cookie 発行・リロードで /dashboard 維持）、バックアップコード消費で残数が減る、再生成は再認証を要求する、別タブでの /2fa-verify 再開、ブラウザの戻るで code が再送されない。

| 観測 | 重大度 | 確認方法 |

## 後始末

作成した検証用ユーザーと関連行は、主キー・ユーザー ID 指定で削除し、ユーザー系・チーム系の全列を走査して残件 0 を確認した。共有の既存ユーザーには触れていない。Valkey は自作ユーザー ID を含むキーだけを個別削除し、所有を特定できないセッション系キーは触れずに自然失効に任せた。検証 BE・偽プロバイダ・検証 FE は停止して listener の消滅を確認し、検証コピー・一時ファイル・認証情報を含む一時ファイルも撤去した。
