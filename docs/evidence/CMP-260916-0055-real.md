## 手順
1. バッチの起動方法をコードから確認した。`PointCardRematchBatchService#execute` は `@Scheduled(cron="${pointcard.rematch-batch.cron}")` で動く。管理 API（`/api/v1/system-admin/batch/pointcard-rematch/trigger`）は SYSTEM_ADMIN が要るため使わず、起動時の環境変数で `pointcard.rematch-batch.cron`（5分毎）と `chunk-size=3` を上書きして、スケジューラ経路をそのまま踏んだ。
2. 起動直後（シード前）の tick で、既存の未マッチ4件（他テスト由来）が total=4 / matched=0 になることと、その4件の provider_id・updated_at が不変であることを確認した（ベースライン）。
3. テストユーザー（自作・使い捨て）で、ウォレットを有効化し、実 API（POST /api/v1/point-cards）でカードを2枚作った。表示名 "rakuten"（提携先コードに一致）と "zzz-nomatch-4881"（一致しない）。表示名・バーコードは DB 上で暗号化列なので、この2枚の暗号文を複製して SQL で20行を追加した。
   - ID は `00000000-…`, `00ffffff-…`, `01000000-…`, `01a212ae-…`, `1a2b3c4d-…`, `3fffffff-…`, `7f000101-…`, `8e444444-…`, `b1777777-…`, `e3999999-…`, `ffffffff-…` など先頭 `00000000`（最小値の直後）から `ffffffff` まで散らした。
   - 一致する行と一致しない行を、ID 順で 2:1 の割合で交互に並べた。
   - シード後の provider_id IS NULL は 26 件（自作22件＋他者の既存4件）。chunk-size=3 なので 9 チャンクになる。
4. 次の 21:35:00 の tick を待ち、ログと DB を確認した。
