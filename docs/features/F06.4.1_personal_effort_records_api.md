## 1. 共通契約

以下のpathは `/api/v1` 配下。認証必須、認証方法とCookie/refreshは既存基盤を使用し変更しない。JSONはcamelCase、queryはsnake_case、enumはUPPER_SNAKE_CASE。IDは新規UUIDをハイフン付き小文字文字列、既存user/team/organization/templateのBIGINTを既存契約どおりJSON整数で扱う。ownerUserIdは入力させず認証主体から決定。未知のfield key、重複field key、未知enum、値の型不一致は400。

成功は `ApiResponse<T>={"data":T}`、一覧は `CursorPagedResponse<T>={"data":[T],"meta":{"nextCursor":null,"hasNext":false,"limit":20}}`。削除/取消も200 `{"data":{"id":"UUID","version":2,"state":"REVOKED"}}` とし、204やsuccessフラグを混在させない。エラーは `{"error":{"code":"COMMON_001","message":"...","fieldErrors":[{"field":"values.duration","message":"..."}]}}`。fieldErrorsは検証失敗だけの任意項目。

nullableは明記した項目だけnullを許可する。レスポンスではnullable項目も省略せずnull、配列は空配列。書込は全置換PUTであり、任意値削除は明示null、required項目省略不可。日時はInstant由来のISO8601 UTC `2026-11-08T03:00:00Z`、日付は `YYYY-MM-DD`、TZはIANA文字列。数値入力・出力は固定小数の10進文字列（例 `"30.00"`）、ID/version/countは整数。FEは表示前のchart描画だけNumberへ変換し、集計や永続値は再計算しない。

一覧queryは `date_from` / `date_to`（両端包含、対で指定）、`definition_uuid`（任意UUID）、`cursor`（任意）、`limit`（既定20、1〜100）。未指定期間は全期間の履歴をcursorで読む。未知queryは400。順序はrecordedOn DESC, createdAt DESC, id DESC。cursorはこの組＋filter hash＋認証scopeをAES-GCMで暗号化・認証したopaque文字列（scope/filterもAADへ束縛）、最大2048字。有効期限24時間、改竄/別filter/別scope/期限切れは400。次ページにも同じfilterを送る。スナップショット一覧ではないため途中編集の重複はUUIDでFEが排除し、再読込で最新へ戻す。

## 2. 型

```ts
// UUID/Date/Instant/Decimalは上記形式のstring。
type FieldValue = { fieldKey: string; value: string | null }
type FieldDefinition = {
  fieldKey: string; label: string; labelKey: string | null;
  type: 'NUMBER' | 'TEXT' | 'SELECT' | 'DATE' | 'DATETIME' | 'CHECKBOX'; required: boolean;
  semantic: 'DURATION' | 'WEIGHT' | 'INTENSITY' | 'SUBJECT' | 'MENU' | 'NUMBER' | 'TEXT' | 'DATE' | 'DATETIME' | 'CHECKBOX';
  unit: string; aggregation: 'SUM' | 'LATEST' | 'NONE'; scale: number; min: string | null; max: string | null;
  options: { key: string; label: string; labelKey: string | null }[];
}
type DefinitionSnapshot = {
  definitionUuid: string; revision: number;
  source: 'PRESET' | 'TEAM'; presetCode: string | null;
  teamTemplateId: number | null; templateName: string;
  durationFieldKey: string | null; subjectFieldKey: string | null;
  fields: FieldDefinition[];
}
type OwnerShare = {
  id: string; teamId: number; state: 'PENDING' | 'VISIBLE' | 'FAILED' | 'REVOKED' | 'MODERATED';
  version: number; sourceVersion: number; grantMembershipId: number; selectedFieldKeys: string[];
  lastErrorCode: string | null; updatedAt: string;
}
type OwnerRecord = {
  id: string; version: number; contentRevision: number; recordedOn: string; recordTimezone: string;
  definition: DefinitionSnapshot; values: FieldValue[]; privateNote: string | null;
  share: OwnerShare | null; createdAt: string; updatedAt: string;
}
type SharedRecord = {
  id: string; version: number; teamId: number;
  author: { userId: number; displayName: string; avatarUrl: string | null };
  recordedOn: string; recordTimezone: string;
  definitionUuid: string; templateName: string;
  fields: { fieldKey: string; label: string; type: 'NUMBER' | 'TEXT' | 'SELECT' | 'DATE' | 'DATETIME' | 'CHECKBOX';
    semantic: string; unit: string; value: string | null; displayValue: string | null }[];
  createdAt: string; updatedAt: string;
  interactions: { canLike: false; canMitayo: false; canComment: false;
    canReply: false; canQuote: false; canRepost: false };
}
```

文字列は文字数上限を親設計で定め、fieldKeyは `[a-z][a-z0-9_]{0,63}`、unitは最大32字。SELECTのvalueはoption key、NUMBERは小数2桁以内（整数semanticは小数部0のみ）、TEXTは文字列。labelKeyは標準プリセットのみ非null。SharedRecord.fieldsはallowlistの定義順だけ、私的IDやnoteを含まない。共有authorは既存プロフィール可視性を適用し、非公開情報を足さない。既存profileが非表示なら許可された匿名表示を使う。

## 3. 個人API

| Method / path | 入力・成功 | 認可 |
|---|---|---|
| GET `/effort-records/me/presets` | queryなし。200 data: DefinitionSnapshot[]（標準3種） | 認証本人、所属不要 |
| POST `/effort-records/me/definition-snapshots` | `{teamId:number,teamTemplateId:number}`。200 `{definition:DefinitionSnapshot,definitionToken:string,expiresAt:string}` | 現在所属＋TEAM templateのscopeId一致。廃止は409 EFFORT_002。非所属は403（template存否で変えない）、template不在・別チーム・TEAM以外のscopeは404 EFFORT_001。親組織は判定に使わない |
| POST `/effort-records/me` | 下記Create。201 OwnerRecord | 本人。TEAM定義なら現在所属・同チーム定義を再検証 |
| GET `/effort-records/me` | 共通一覧query。200 cursor OwnerRecord[] | owner束縛 |
| GET `/effort-records/me/{id}` | queryなし。200 OwnerRecord | owner束縛、不在/他人404 |
| PUT `/effort-records/me/{id}` | 下記Update。200 OwnerRecord | owner束縛、version一致 |
| DELETE `/effort-records/me/{id}` | 必須query `version` 非負整数。200 `{id,version,state:'DELETED'}` | owner束縛 |
| GET `/effort-records/me/stats` | §5 query。200 Stats | owner束縛 |

Createは `{recordedOn,recordTimezone,definitionUuid,definitionRevision,definitionToken,values,privateNote}`。definitionTokenはPRESETのみnull可。TEAMではsnapshot APIの10分有効署名tokenを必須とし、teamId/definitionUuid/revision/hash/本人IDを束縛する（organizationIdは束縛しない。チームは親組織0件・複数件があり得るため）。token欠落・改竄・期限切れ・束縛不一致（他人・別チーム・別定義・版不一致）は400 COMMON_001とし、fieldErrors[].field=`definitionToken` を返す。serverはtoken検証後に指定team shardのServiceを1回呼び、総当たり検索しない。privateNoteはnull可、他は必須。snapshot自体やowner IDをクライアントから受け取らない。serverがdefinitionUuid/revisionを取得し同一snapshotを保存する。definition-snapshots APIはチーム定義の不変revisionを登録・返すための操作で、原本を作らず個人一覧にも出ない。標準はpresets応答をそのまま指定する。

Updateは `{version,recordedOn,values,privateNote}`。definition/recordTimezoneの変更不可。versionは非負整数、成功時1以上増加。snapshotに存在する全fieldをvaluesへ渡し、任意未入力はnull。削除済みは404。共有済み原本の更新は、現在の共有先所属者なら既存allowlistで同期要求を新versionへ更新し202ではなく200 OwnerRecord（share.state=PENDING）を返す。共有資格喪失または保存加入期間ID不一致ならprivate更新だけ成功し、旧共有をREVOKEDとして扱い再同期しない。再加入後のprivate訂正でも旧共有を再開せず、新previewによる再共有を要求する。

`@SelfScopedEndpoint` はscope IDを受け取らない本人一覧/詳細/保存/集計だけ候補とし、Controller#methodを名指す契約ITを付ける。teamId/templateIdを受け取るsnapshot/共有APIへ流用しない。

## 4. 共有API・チームAPI

previewは永続済み原本のUUIDを必須とする。初回画面の「保存して共有内容を確認」は、明示的な個人保存POST成功後に返却UUID/versionでpreview POSTを呼ぶ。最終previewの「この内容を共有」で初めて共有PUTを呼ぶ。previewを閉じる/期限切れ/取得失敗でも保存済み原本は残り、共有は発生しない。既存原本は同じUUIDへのPUT（変更がある場合だけ）→preview→共有PUTとし、原本を複製しない。具体的なボタンとAPI呼順は[親設計§2.1](F06.4.1_personal_effort_records.md#21-初回保存と共有確認のapi順序)に従う。

| Method / path | 入力・成功 |
|---|---|
| POST `/effort-records/me/{id}/team-share/preview` | `{version,teamId,definitionToken,mappings,selectedFieldKeys}` →200 `{previewToken,expiresAt,recordVersion,contentRevision,definitionRevision,projection:SharedRecord}`。previewのidは予約share UUID、version0 |
| PUT `/effort-records/me/{id}/team-share` | `{version,previewToken,mappings,selectedFieldKeys}` →202 OwnerRecord（PENDING）。mappings・selectedFieldKeysはpreviewで送ったものを送り直す（上限はpreviewと同じ15項目）。同じshareを再利用 |
| POST `/effort-records/me/{id}/team-share/retry` | `{version,shareVersion}` →202 OwnerRecord。FAILEDまたは60秒超PENDINGのみ。同一desired commandを再実行し、定義token/previewTokenは不要。内容変更不可 |
| DELETE `/effort-records/me/{id}/team-share` | query `version`, `share_version` 必須 →200 OwnerRecord（REVOKED） |
| GET `/teams/{teamId}/effort-records` | 共通一覧query＋`user_id`（任意既存ID）→200 cursor SharedRecord[] |
| GET `/teams/{teamId}/effort-records/{shareId}` | queryなし →200 SharedRecord |
| DELETE `/teams/{teamId}/effort-records/{shareId}` | query `version` 必須 →200 `{id,version,state:'MODERATED'}` |

新規共有・取消後の再共有、および既存共有への項目追加・allowlist/mapping/共有定義変更のpreview/共有PUTは本人原本ownerを確認し、現在の所属、TEAM templateの所属一致、共有先TEAM定義tokenのteam一致、現行有効revisionを検証する。これらは新たな共有許可またはその変更としてlive定義・現行revision・10分有効token・本人のpreview再確認を必須とする。単なる原本値の訂正とは区別する。原本定義と共有定義は異なってよい。原本1件から選んだTEAM定義へ共有専用mappingを行い、原本や個人集計の行を増やさない。mappingsは `{targetFieldKey:string,sourceFieldKey:string|null,valueOverride:string|null}[]`。同一semantic/unit/typeのsourceだけ候補として値を引き継ぎ、本人が確認する。sourceFieldKeyとvalueOverrideの同時指定は拒否し、単位変換や未知の意味の推測はしない。target必須の不足は共有画面でvalueOverrideとして入力し共有設定だけへ保存する。任意不足はnull。selectedFieldKeysはtarget keyのallowlist。target必須値は未選択でも入力検証するが、非選択値をprojectionへ含めない（必須の判定はmapping適用後の値で行い、mappingの省略・nullへ正規化される値は不足として400 COMMON_001、fieldErrors[].field=`mappings.<targetFieldKey>`）。valueOverrideは原本の値と同じ型・定義制約（NUMBERのscale/min/max、DATEの暦日、DATETIMEのオフセット付きISO8601、SELECTの選択肢、TEXTの文字数）で検証し、DATETIMEはUTCへ正規化して保存する。元の私的noteはmapping元にできない。既に別teamの有効shareがあれば409。

既存の有効許可に基づく原本訂正と同一desired commandのretryは、owner・現在の共有先所属・有効な共有許可・current share ID・TEAM側の現在共有資格ありかつgrantMembershipId一致・contentRevision/shareVersion・desired hash一致・teamが非MODERATEDであることを検証する。原本訂正は凍結した共有定義snapshot/mapping/allowlistから新contentRevisionのdesired projection/hashを確定し、retryはその保存済みcommandが現在版と一致することをserverが検証して再実行する。live定義token・previewToken・10分expiry・現行revision・retired判定を再要求しない。したがって管理者が定義を変更/廃止しても、既に許可された同一定義の訂正とその部分失敗からのretryは継続できる。取消/削除/別shareへの切替/管理者非表示後の復活、mapping/allowlistの拡張はこの経路で許可しない。

previewTokenは10分有効の署名opaque、owner/record/contentRevision/team/grantMembershipId/共有definition revision/mapping/allowlist/projection hash/share UUIDを束縛する。mapping/allowlist（valueOverrideの値を含む）はtokenへ値ごと詰めず、正規化したcommandのcanonical hashで束縛する（tokenの長さは入力の大きさに依らず一定。15項目×2000字のvalueOverrideでも共有PUTの上限16,384字に収まる）。共有PUTは本文で送り直されたmappings/selectedFieldKeysをpreviewと同じ規則で検証・正規化し、command hashとprojection hashがtokenと一致しなければ409 COMMON_003（再preview）。（2026-11-24 PR-3b 検分指摘で追記）previewはDBへ共有を作らず、通常再表示も公開しない。投稿までに原本contentRevision/共有定義/所属加入期間IDが変化したら409・再preview。定義revisionの比較は同一TEAMテンプレートの変更検知に使い、既存recordのsnapshotを書換えない。共有値はserverが許可項目だけから確定する。tokenをquery/log/localStorageに保存しない。

本人取消は脱退後でもowner照合で許可し、現在所属を必須にしない。チーム一覧/詳細はteamの現在所属とF00を両方確認。非所属403、別team share UUIDは404（親組織は判定に使わない）。user_idが他teamの人でも存在を推測する検証エラーを返さず該当なし。管理者非表示は既存のチーム管理者権限判定を使用（ADMIN、既存テンプレート管理権限を正規に委任されたDEPUTY_ADMIN）。MEMBERは他人のshareを削除不可。SYSTEM_ADMINもチーム可視性をバイパスしない。

チーム履歴のテンプレート候補は既存有効TEAM templateに、履歴内に存在する廃止済みdefinitionを追加して選べるようにする。候補専用API `GET /teams/{teamId}/effort-records/definitions` は200 data:`{definitionUuid,templateName,isRetired:boolean}[]`、現在所属認可、当該teamでVISIBLEな履歴が1件以上あるものだけ返す。PENDING・REVOKED・MODERATEDの履歴しかない定義は、候補として返さない（存在や状態を一覧の絞り込みから推測させない）。これは一覧/{shareId}より先にroute解決する。

### 4.1 冪等性と応答消失

POST create、PUT share、POST retry、DELETE owner/share/moderationに `Idempotency-Key` UUID必須。scopeは認証主体＋HTTP method＋path、request hashにbody/query/versionを含める。同じkey/同じhashは24時間、同じstatus/bodyを返す（完了後の再送でも重複書込なし）。同じkey/異なるhashは409 COMMON_003。進行中同keyは409で `Retry-After: 1`、FEは自動別keyへ変更しない。owner UUID/versionを含むためteam境界でkeyが衝突しない。

原本PUTはversionによる重複検知とする。応答消失後に同じversionで再送すると409、GETで保存結果を比較してUIを回復する。共有202後はGET ownerを手動更新または最大5秒間隔・画面可視時のみ取得し、30秒で自動取得を止め「確認」を表示する。60秒未満PENDINGのretryは409、60秒経過後PENDINGまたはFAILEDでは明示再試行ボタンを表示する。FAILEDは明示retryだけ、ネットワーククライアントの無条件POST再送をしない。DELETE取消は許可失効をowner TXで確定してから200を返すため、team後処理を待たない。

## 5. 集計API

必須query `date_from`,`date_to`,`definition_uuid`,`field_key`,`chart`（BAR/LINE/PIE）。任意`grain` DAY/MONTH（省略時親設計の期間規則。DAYは62日以下、MONTHは366日以下）。chartとsemanticが不適合なら400。PIEは対応durationFieldKey指定が必須で、SUBJECT対応がない定義は400。filter値をレスポンスへechoし、rangeの端数月は指定期間内だけ集計する。

```ts
type Stats = {
  definitionUuid: string; fieldKey: string; unit: string; semantic: string;
  chart: 'BAR' | 'LINE' | 'PIE'; grain: 'DAY' | 'MONTH';
  dateFrom: string; dateTo: string; totalSampleCount: number;
  buckets: { startOn: string; endOn: string; value: string | null; sampleCount: number }[];
  categories: { key: string; label: string; value: string; sampleCount: number }[];
  total: string | null; emptyReason: 'NO_DATA' | 'ZERO_TOTAL' | null;
}
```

BAR/LINEはbucketsを空白bucket含め昇順に返しcategories=[]。PIEはbuckets=[]、categoriesを値降順/key昇順、null数値は分母に含めない。BAR totalはSUM、LINE totalはnull、PIE totalはduration SUM。全データなしはtotal=null/NO_DATA。BAR/PIEの0記録ありだけtotal="0.00"/ZERO_TOTAL、LINEは値が0でもtotal=null/emptyReason=null。sampleCountは数値が非nullの記録件数。SELECT未指定はreserved subject keyで集約する。

## 6. エラー割当

EFFORT_001〜005 は PR-1 で実装済み（`EffortErrorCode`）。新規採番は「現在の最大＋1で予約、確定はマージ時に再確認」とし、実装時に全ErrorCode prefix重複を再検索する。COMMONのHTTP割当もGlobalExceptionHandlerへ明示登録する。エラー文言は、日本語を enum の既定メッセージに持ち、de・en・es・ko・zh の5言語を `messages_{lang}.properties` の `error.effort.NNN` に置く（`messages_ja.properties` と `messages.properties` には `error.effort` を置かない）。

| code | HTTP / Severity | 条件 |
|---|---|---|
| COMMON_001 | 400 / WARN | 型/範囲/桁/上限/空allowlist/不正cursor/非対応chart |
| COMMON_002 | 403 / WARN | チーム非所属/管理権限なし |
| COMMON_003 | 409 / WARN | version/preview失効/key不一致/別team共有/状態競合 |
| EFFORT_001 | 404 / WARN | 原本不在/他人/共有不在/別tenant（区別しない） |
| EFFORT_002 | 409 / WARN | template廃止・revision変更で新規共有不可 |
| EFFORT_003 | 403 / WARN | 努力由来sourceへの通常操作すべて（like/mitayo/comment/reply/quote/repost/通常本文更新/通常のdeletePost/pin/bookmark/フレンドチーム転送/公開化）。操作別にコードを分けず、応答は共通のエラー形で fieldErrors なし。既定文言は「この投稿には操作できません。共有をやめるときは、記録の『共有を取り消す』から行ってください」（全操作に通じる形）。deletePost で拒否されたときの案内は FE が effort.json（`effort.share.deleteGuide`）で出す。誘導先の取消 API は本人取消 `DELETE /effort-records/me/{id}/team-share`、管理者の非表示は `DELETE /teams/{teamId}/effort-records/{shareId}`。許可・禁止の全体表は[データ設計§7.2](F06.4.1_personal_effort_records_data.md#72-努力由来投稿に許す操作と禁止する操作) |
| EFFORT_004 | 503 / ERROR | F00/source照会障害。詳細・一覧とも取得失敗とし、障害を空一覧に置換しない |
| EFFORT_005 | 503 / ERROR | 共有処理インフラ障害で要求を保存できない（保存済み原本は残る） |

無認証は既存認証基盤の401。タイムライン・共有一覧ではdeny対象を件数/previewで漏らさず、hasNext/nextCursorは走査継続位置を返す（非表示行だけの空pageでも次cursorを返せる）。1回の走査上限は1000行。全てdenyでも暗号化した継続位置で空page＋hasNext=trueを返し、次の有限走査へ進める。すなわち、1000行で打ち切って続きがあるときは「空、hasNext=true、nextCursorあり」、走査が終わったときは「空、hasNext=false、nextCursor=null」とする。非表示IDや値をtokenから推測できない。F00障害を「0件」として成功表示することはしない。

全体検索（検索基盤 #4647、タイムライン投稿の検索 #4661、SQL を統一した #4700）は、F00 の個別判定ではなくSQLで努力由来の投稿を常に除外する。timeline の検索の共通 SQL の WHERE に `NOT EXISTS (SELECT 1 FROM timeline_effort_sources s WHERE s.timeline_post_id = timeline_posts.id)` を足し、件数（count）・ページ境界（cursor・offset）・並び替えも同じ条件で絞る。そのため件数や次ページの有無から努力由来の投稿の存在が漏れない。努力由来の投稿は閲覧権限があっても検索結果に出さない（閲覧は活動履歴・タイムラインから行う）。

## 7. 管理者の指標設定と既存型互換

既存activity templateへsemantic等が存在すると仮定しない。チームテンプレート編集画面へ「個人の頑張り記録の指標」セクションを追加し、既存fieldごとにsemantic/unit/aggregationを設定する。duration↔subject対応は各1項目だけ選択する。設定しないテンプレートも共有に使えるが、数値はNUMBER/NONEとして個人集計対象外とする。個人の独自定義作成や式エディタは追加しない。

`GET /teams/{teamId}/effort-records/template-settings/{templateId}` →200 `{version,definition:DefinitionSnapshot}`。`PUT` 同path、body `{version,fields:[{fieldKey,semantic,unit,aggregation}],durationFieldKey:string|null,subjectFieldKey:string|null}` →200 同型。両方、既存TEAMテンプレート管理権限＋templateのscope一致。MEMBER・非所属は403、pathのteamに属さないtemplate（別チーム・TEAM以外のscope・不在）は404 EFFORT_001。親組織の有無・一致は判定に使わない。PUTは全field設定を要求し、未知key/重複/互換しないsemantic（TEXTへWEIGHT等）/対応の二重指定は400、version競合409。semantic・unit・型の変更はいずれも新しいfieldKeyを発番し旧seriesと混ぜない（label変更だけは同じkey）。設定保存先はeffort_definition_revisions.definition_jsonで、activityテンプレートの既存列へ勝手に属性を追加しない。min/max/scaleはsemanticの固定規則からserverが決定し、管理者の任意設定にしない。

NUMBER→NUMBER、TEXT/TEXTAREA→TEXT、SELECT→SELECT、DATE→DATE、DATETIME→DATETIME、CHECKBOX→CHECKBOX。型がない/未知型/複合値は400（COMMON_001、該当fieldKey付き）。DATE/DATETIME/CHECKBOXと自由TEXTはaggregation=NONE。SUBJECTはSELECTまたはTEXT、DURATION/WEIGHT/INTENSITYはNUMBERだけ。MENUはTEXTだけ。NUMBERは管理者が明示SUMを選んだ場合だけ合計可、unitは空不可（無単位はNONE）。共有値の型を適合させられない場合は保存前にエラーを示す。

snapshot APIは毎回activity ServiceからTEAM template全定義を取得し、field ID/key/type/label/options/required/順序をcanonical JSON hashに含め、effort指標設定と合わせたhashを現在revisionと比較する。異なれば同じdefinitionの新revisionを同一effort TXで発行する。activity更新イベントがあればretired/changedを先行反映するが、イベントに依存せず新規共有・取消後再共有・既存共有許可変更のpreview投稿時にactivity Serviceの現在hashを再検証し、定義変更の取りこぼしを防ぐ。廃止はその確認で新規共有不可。既存snapshotの編集/個人集計、および既存許可の同一定義訂正・同一desired commandのretryはactivity照会に依存させない。

### 7.1 テンプレート編集の fieldKey 契約（ALIC-1）

**適用範囲**: 既存の活動テンプレート更新 API（`PUT /activity-templates/{id}`。実装は `ActivityTemplateService#updateTemplate`）はスコープ共通なので、この契約も TEAM に限らず全スコープ共通で適用する（TEAM 以外では effort の系列に影響しないが、同じ検証を課して挙動を分けない）。作成（POST）・複製・プリセット取込の契約は変えない。ここでの `fieldKey` は activity の項目キー（`activity_template_fields.field_key`、最大50字）であり、指標設定 API（§7 前半）の `fieldKey`（effort の series key。`f{activity field ID}_...`）とは別物である。後者は前者の field ID から導かれる。

**根因（2026-11-22 時点の実コード）**: 編集保存が 500（Duplicate key null）になるのは次の3点が重なるため。(1) `ActivityTemplateForm.vue` の `FieldRow` が `fieldKey` を保持せず、保存時にも送らない。(2) FE の送信名（`label` / `required` / `options`（文字列配列））と BE の受信名（`fieldLabel` / `isRequired` / `optionsJson`（JSON 文字列））が食い違い、`composables/useActivityApi.ts` は body をそのまま渡すため値が捨てられる。(3) `UpdateTemplateRequest.fields` に `@Valid` がなく、`TemplateFieldInput.fieldKey` の `@NotBlank` が評価されないまま null が `Collectors.toMap` へ届く。

**契約**（マスター裁定 2026-11-22。fieldKey は現行どおり FE が付ける）:

1. 送信名は BE の `TemplateFieldInput` に合わせる: `fieldKey`（必須・最大50字）、`fieldLabel`、`fieldType`、`isRequired`、`optionsJson`（SELECT のとき JSON 配列文字列）、`isAggregatable`、`placeholder`、`unit`、`sortOrder`。`updateTemplate` は `placeholder` と `unit` を無条件に上書きするため、FE の FieldRow は保存済み項目のこの2つも読み込み時に保持して送り返す（送らないと既存値が null で消える）。この `unit` は activity 側の項目の単位であり、指標設定の `unit`（effort 側。下記 (b)）とは別物である。
2. FE の FieldRow は保存済み項目の `fieldKey` を読み込み時に保持し、並べ替え・ラベル変更・必須切替をしても行ごとに同じ値を送る。新規項目の `fieldKey` も FE が付ける。BE は発番しない。
3. BE は `fieldKey` でテンプレートの既存項目と突き合わせる。一致したら同じ行を更新し、activity field ID を変えない。既存に無い `fieldKey` は新規追加として受け入れる（FE が付けた新規キーと区別する必要がないため）。誤送信の検出は次項の照合による。
4. 更新リクエストに `removedFieldKeys: string[]`（省略は空）を設け、削除する既存項目を明示させる。テンプレートの既存項目の `fieldKey` は、すべて `fields` か `removedFieldKeys` のどちらか一方に必ず含まれる。どちらにも無い既存キーがあれば 400 とし、BE は黙って削除も保持もしない。`fields` 自体を省略したときは項目に触れない（現行互換）。その場合 `removedFieldKeys` の指定は 400。
5. 既存項目を削除して作り直すことを禁止する。FE は「更新」と「削除」と「新規追加」を別に送り、編集操作から削除＋同内容の追加を生成しない。管理者が明示的に項目を削除した場合だけ `removedFieldKeys` に入れ、その項目の系列はそこで終わる（同名で追加し直しても別の系列）。

**fieldKey の規則**（新規項目に FE が付けるキー）:

- 書式は `[a-z][a-z0-9_]{0,49}`（50字以内）。FE は `f_` に乱数 12 桁（16 進）を足して生成する（例 `f_3fa85f6457a1`）。ラベルや並び順から作らない（ラベル変更で key が変わる・同名項目で衝突するのを避けるため）。
- テンプレート内で一意とし、既存キー・同じリクエスト内のキーと衝突したら FE が再生成する。
- 削除したキーを同じ名前で追加し直すことを禁止する。活動記録の入力値（`activity_results.field_values`）が fieldKey を鍵にしているため、同じキーを再利用すると過去の記録の値が新しい項目に結び付く。FE は `removedFieldKeys` に入れたキーを同じ保存の新規項目に使わず、削除後の新規項目は必ず新しい乱数キーとする。BE は同一リクエストで `removedFieldKeys` と `fields` に同じキーがあれば 400 とする。過去に削除したキーの履歴は持たない（乱数生成で衝突は事実上起きない）。
- 既存のキー（書式が上記と異なる旧データを含む）はそのまま保持して送り、BE は書式を検査しない。BE が書式を検査するのは、既存に無いキー（新規項目）だけで、違反は 400 とする。

| ケース | 結果 |
|---|---|
| 正常: 既存全項目を fieldKey 付きで `fields` に、新規は FE 付与の新キーで `fields` に | 200。既存項目の field ID・series key・unit・placeholder は不変 |
| 正常: 削除したい項目を `removedFieldKeys` に | 200。その項目だけ削除 |
| `fields[n].fieldKey` が null・省略・空白（既存の @NotBlank を `@Valid` で有効にする） | 400 COMMON_001、fieldErrors の field=`fields[n].fieldKey`（500 にしない） |
| 新規項目（既存に無いキー）の書式違反 | 400 COMMON_001、fieldErrors の field=`fields[n].fieldKey` |
| `fields` 内で fieldKey が重複 | 400 COMMON_001、fieldErrors の field=重複した各項目の `fields[n].fieldKey` |
| 既存キーが `fields` にも `removedFieldKeys` にも無い（FE の保持漏れ・誤ったキーの送信・他の管理者が先に項目を追加した場合を含む） | 400 COMMON_001、fieldErrors の field=`fields`、メッセージに漏れたキー |
| `removedFieldKeys` に既存に無いキー、または同じキーが `fields` にも | 400 COMMON_001、fieldErrors の field=`removedFieldKeys[n]` |
| 既存項目の fieldType 変更 | 既存の ACTIVITY_018（400）のまま |
| 管理者以外 | 既存の認可（403）のまま |

**FE のエラー表示**: `fields[n].fieldKey` のエラーは、利用者が編集できない欄なので該当の行を強調し、フォーム上部に「項目の識別子が正しくありません。画面を読み込み直してください」を出す。`fields` または `removedFieldKeys[n]` のエラー（照合漏れ）は、2人が同時に編集した可能性があるとみなし、フォーム上部に「他の人が先に更新した可能性があります。最新の内容を読み込み直してください」と再読込ボタンを出す。再読込は未保存の入力を捨てるので ConfirmDialog で確認する。文言は `effort.templateSettings.error.*` ではなく activity の名前空間（`activity.template.error.*`）に置く（編集フォームは activity 側の画面のため）。

**series を分断する経路は2つ**ある。(a) activity field ID が変わる（削除→作り直し）ことは、上の契約で禁止する。(b) 指標設定で unit・semantic・型を変えると、[§7 前半](#7-管理者の指標設定と既存型互換)・[データ設計§2](F06.4.1_personal_effort_records_data.md#2-ddl案)のとおり新しい series key になり、旧系列と混ざらない。(b) は禁止せず新系列になる仕様とし、指標設定セクションの UI で警告する。unit・semantic の欄の近くに「単位や意味を変えると、これまでの記録とは別の系列として集計されます」と注記し、保存時に変更があれば ConfirmDialog で確かめる。対象は指標設定（effort 側）の `unit` であり、activity の項目の `unit`（上記 1.）ではない。この警告は PR-4 の成果物とし（先行修正には含めない）、同じセクションの未保存破棄確認と合わせて実装する。

**先行修正の範囲**: ALIC-1・ALIC-2 と同じ先行修正 PR で、活動テンプレート画面の次の不具合も直す。いずれも FE を既存の BE 契約に合わせるだけで、契約は変えない。(1) 一覧: `activity-templates.vue` が `getTemplates('TEAM', teamSlug)` と slug を `scope_id`（BE は Long）へ渡して 400 になる。既存の `useActivityScopeId`（`resolveScopeId('TEAM', slug)`）で数値 ID に解決して渡す。解決で取得に失敗したときはエラー表示と再試行、取得は成功したが該当チームが無いときだけ 404 とする（resolver が取得失敗を null に潰さない契約への修正を含む。本体 §2.3）。(2) 作成: `createTemplate` が `scope_type` / `scope_id` のクエリを送っていない。(3) 複製: `duplicateTemplate` が本文（複製先のスコープ）を送っていない。(4) 画面の日本語直書き（操作列・見出し・confirm・showError・showSuccess・ツールチップ、`ActivityTemplateForm.vue` の「説明」）を、i18n ルールに従い既存の activity の i18n キーへ移す（キー名は本体 §6。`activity.json` を `activity` で包む修正を含む）。同じ画面を触るため先行修正 PR で直す。

新規のエラーコードは設けず、このテンプレート編集の検証エラーはすべて COMMON_001 に統一する。この節は契約だけを定める。既存実装の修正は別 PR で行う。

## 8. 脱退・共有資格喪失のAPI契約

自己脱退/管理者所属解除等の共有資格喪失後は、team Serviceの権威的な加入期間終了状態が旧共有を失効させる。全共有readは閲覧者の現在所属と投稿者の保存grantMembershipIdを検証し、不一致/REVOKEDなら既存の非表示契約（一覧除外、詳細404）を使う。権威照会の障害はEFFORT_004/503。owner GETではTEAM側加入期間の終了状態と照合した実効state=REVOKEDを返し、owner行の非同期失効反映待ちでもVISIBLE/FAILEDとして再試行させない。本人が非所属なら新preview/共有/retryはCOMMON_002/403、再加入済みでも旧加入期間preview/commandはCOMMON_003/409。原本の私的操作は通常のowner認可を維持する。

新規共有/再共有/許可変更previewはteam Serviceから有効なgrantMembershipIdを取得してtokenへ束縛し、共有PUT・team upsert・timeline upsert・owner ackでも一致を確認する。退会だけで保持された既存共有のreadはRETAINED_ACCOUNT_WITHDRAWAL理由かつ保存加入期間ID一致なら許可できるが、新規共有/訂正/retryは現在の共有資格と有効アカウントを必須とする。加入期間IDは内部検証用で、SharedRecordへは返さない。内部batch契約と加入期間を固定した退出eventの適用範囲はデータ設計§8を正本とする。
