## 1. 境界

新規effortrecordドメインだけで原本・定義snapshot・共有projectionを管理する。既存activity/team/user/timelineへの参照はIDとService経由、クロスドメインFKなし。個人側のルーティングはowner_user_id、チーム側はteam_id（チームは親組織0件・複数件があり得るため organization_id で束ねない。2026-11-18 マスター裁定）。現行単一DBでも両者を同じTXへ入れない。同一effortrecordドメインであっても将来異なるシャードになるため、private→team FKも作らない。

definitionは個人所有にせず、標準プリセットまたはチーム定義の不変snapshot識別用で、TEAMはteam側、PRESETは共通参照データとして全シャードへ同じUUID/内容を配布する。原本はdefinition JSON自体を保持するため、definition側へJOINしないで本人閲覧・集計可能。snapshot revisionの作成はactivity Serviceから認可済み定義を取得し、非TX Facadeからeffort definition Serviceへ渡す。activityの更新TXを共有しない。

## 2. DDL案

全新規EntityはUuidV7Entity継承、idは真正UUIDv7/BINARY(16)。created_at/updated_at/deleted_atはUTC DATETIME(6)、新規瞬間型はInstant、recorded_onはLocalDate/DATE。@Versionと `@SQLRestriction("deleted_at IS NULL")` を主要表へ適用する。UuidV7Entityの継承フィールドが既存LocalDateTimeなら共通基底を一括変更せず、追加業務時刻はInstantとして対応を明示する。以下のNOT NULLに暗黙の空値defaultは与えない。

```sql
CREATE TABLE effort_definitions (
  id BINARY(16) NOT NULL,
  source_type VARCHAR(10) NOT NULL,
  source_key VARCHAR(80) NOT NULL,
  team_id BIGINT UNSIGNED NULL,
  team_template_id BIGINT UNSIGNED NULL,
  current_revision INT UNSIGNED NOT NULL,
  retired_at DATETIME(6) NULL,
  version BIGINT NOT NULL DEFAULT 0,
  created_at DATETIME(6) NOT NULL,
  updated_at DATETIME(6) NOT NULL,
  deleted_at DATETIME(6) NULL,
  PRIMARY KEY (id), UNIQUE KEY uq_effort_definition_source (source_type, source_key),
  KEY idx_effort_definition_team (team_id, deleted_at),
  CHECK (source_type IN ('PRESET','TEAM')),
  CHECK (current_revision >= 1 AND version >= 0),
  CHECK ((source_type='PRESET' AND team_id IS NULL AND team_template_id IS NULL)
    OR (source_type='TEAM' AND team_id IS NOT NULL AND team_template_id IS NOT NULL))
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;

CREATE TABLE effort_definition_revisions (
  id BINARY(16) NOT NULL,
  definition_id BINARY(16) NOT NULL,
  revision INT UNSIGNED NOT NULL,
  definition_json JSON NOT NULL,
  definition_hash CHAR(64) NOT NULL,
  created_at DATETIME(6) NOT NULL,
  updated_at DATETIME(6) NOT NULL,
  PRIMARY KEY (id), UNIQUE KEY uq_effort_revision (definition_id, revision),
  CONSTRAINT fk_effort_revision_definition FOREIGN KEY (definition_id) REFERENCES effort_definitions(id),
  CHECK (revision >= 1)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;

CREATE TABLE effort_records (
  id BINARY(16) NOT NULL,
  owner_user_id BIGINT UNSIGNED NOT NULL,
  definition_id BINARY(16) NOT NULL,
  definition_revision INT UNSIGNED NOT NULL,
  definition_snapshot JSON NOT NULL,
  recorded_on DATE NOT NULL,
  record_timezone VARCHAR(64) NOT NULL,
  values_json JSON NOT NULL,
  private_note TEXT NULL,
  purged_at DATETIME(6) NULL,
  version BIGINT NOT NULL DEFAULT 0,
  content_revision BIGINT NOT NULL DEFAULT 1,
  share_definition_snapshot JSON NULL,
  share_mapping_json JSON NULL,
  share_id BINARY(16) NULL,
  share_team_id BIGINT UNSIGNED NULL,
  share_state VARCHAR(12) NULL,
  share_version BIGINT NOT NULL DEFAULT 0,
  grant_membership_id BIGINT UNSIGNED NULL,
  selected_field_keys JSON NULL,
  desired_projection JSON NULL,
  desired_hash CHAR(64) NULL,
  synced_source_version BIGINT NULL,
  last_error_code VARCHAR(32) NULL,
  share_updated_at DATETIME(6) NULL,
  created_at DATETIME(6) NOT NULL,
  updated_at DATETIME(6) NOT NULL,
  deleted_at DATETIME(6) NULL,
  PRIMARY KEY (id), UNIQUE KEY uq_effort_record_share (share_id),
  KEY idx_effort_owner_date (owner_user_id, deleted_at, recorded_on DESC, created_at DESC, id DESC),
  KEY idx_effort_owner_definition (owner_user_id, definition_id, deleted_at, recorded_on),
  KEY idx_effort_sync (share_state, share_updated_at, id),
  CHECK (version >= 0 AND content_revision >= 1 AND share_version >= 0 AND definition_revision >= 1),
  CHECK (share_state IS NULL OR share_state IN ('PENDING','VISIBLE','FAILED','REVOKED','MODERATED')),
  CHECK ((share_id IS NULL AND share_team_id IS NULL AND share_state IS NULL)
    OR (share_id IS NOT NULL AND share_team_id IS NOT NULL AND share_state IS NOT NULL AND grant_membership_id IS NOT NULL))
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;

CREATE TABLE effort_team_shares (
  id BINARY(16) NOT NULL,
  team_id BIGINT UNSIGNED NOT NULL,
  owner_user_id BIGINT UNSIGNED NOT NULL,
  source_record_id BINARY(16) NOT NULL,
  source_version BIGINT NOT NULL,
  grant_membership_id BIGINT UNSIGNED NOT NULL,
  share_version BIGINT NOT NULL,

  PRIMARY KEY (id),
  UNIQUE KEY uq_effort_team_source (team_id, source_record_id),
  KEY idx_effort_team_date (team_id, deleted_at, state, recorded_on DESC, created_at DESC, id DESC),
  KEY idx_effort_team_membership (team_id, grant_membership_id, state),
  KEY idx_effort_team_person (team_id, owner_user_id, deleted_at, state, recorded_on),

CREATE TABLE effort_operation_receipts (
  id BINARY(16) NOT NULL,
  route_kind VARCHAR(10) NOT NULL,
  route_id BIGINT UNSIGNED NOT NULL,
  actor_user_id BIGINT UNSIGNED NOT NULL,
  operation_key CHAR(36) NOT NULL,
  operation_path VARCHAR(255) NOT NULL,
  request_hash CHAR(64) NOT NULL,
  response_status SMALLINT UNSIGNED NULL,
  response_json JSON NULL,
  created_at DATETIME(6) NOT NULL,
  updated_at DATETIME(6) NOT NULL,

  PRIMARY KEY (id),
  UNIQUE KEY uq_effort_receipt (route_kind, route_id, actor_user_id, operation_path, operation_key),
  KEY idx_effort_receipt_expiry (expires_at),

```

チーム側の表（effort_definitionsのTEAM行・effort_team_shares・timeline_effort_sources・TEAM receipt）はorganization_id列を持たず、一意キー・索引はteam_id起点とする（2026-11-18 マスター裁定）。PR-1で適用済みのeffort_definitions.organization_id・effort_records.share_organization_idはPR-2のmigrationでCHECKを再定義して削除し、idx_effort_definition_teamを(team_id, deleted_at)で作り直す（本番データなし）。

source_keyはPRESETなら固定code、TEAMなら `team:{teamId}:template:{templateId}`。definition current_revisionの更新とrevision INSERTは同一definition側TXで、同一hashならrevisionを増やさない。stable field keyはrevision間で保持し、型/単位/semanticの変更は新keyであることを検証する。TEAMのkeyは `f{activity field ID}_{型・semantic・canonical unitのSHA-256先頭10桁}` で決定的に発番する（label変更は同key、activityでの削除→再追加はfield IDが変わるため新key。同じkeyが別の型・単位・semanticを指さない）。したがって activity 側のテンプレート編集は既存項目のfield IDを保つ必要があり、FEが既存項目のfieldKeyを保持して送り、BEがfieldKeyで突き合わせて更新する契約を置く（[API契約§7.1](F06.4.1_personal_effort_records_api.md#71-テンプレート編集の-fieldkey-契約alic-1)）。既存項目の削除→作り直しは系列を分断するため行わない。指標設定はrevisionのdefinition_jsonに保存し、次revisionはkeyからactivity field IDを読み戻して設定を引き継ぐ。SELECTのoption keyはlabelのSHA-256から決定的に導く。retired後もrevisionを物理削除しない。team template IDは既存BIGINTを参照し、UUIDへ置換しない。

原本にはUUID・revisionをFKなしで参照し、作成時に定義JSONを複写。保存後の定義JSONは変更不可。values_jsonはfieldKey→string/nullのobject、private noteは独立列。上限/必須/JSON schema/recorded_on範囲/IANA TZ/allowlist subset/hashはServiceで検証する（MySQL CHECKだけでJSON値の意味を保証しない）。team projection JSONには共有allowlistのfieldだけを置く。所有者private noteをreceiptにも残すため、receiptはprivate原本と同じowner認可・同じ消去対象であり、team mutation receiptはSharedRecordのみ。保持24時間で期限削除バッチ、個人情報の長期保管に使わない。

operation_pathにはHTTP method込みの正規化pathを入れ、route_kind=OWNERはowner user、TEAMはteam IDでルーティングする。TEAM receiptのroute_idはteam ID（親組織は使わない）。Receipt確保・業務更新・応答保存は同一ルーティング先/同一ドメインTXで確定。ネットワークI/O中にTXを保持しない。未完receiptを別TXで先にcommitしないため、プロセス停止でも永久IN_PROGRESSを残さない。

削除はdeleted_atを立てる。同一原本の有効共有は原本1行のshare_idで一意に保持する。取消後別teamへ移すときは新share_idを採番しshare_versionを増加、古いshareのtombstoneはteam側に残す。再度同じteamへ共有する場合は既存source一意行のidを再利用し、本人が新previewで許可したshare_versionでだけ復帰する。share IDの変更とsource一意制約が衝突しないよう、過去teamの既存share IDをServiceから取得してpreview予約IDに使う。管理者MODERATEDはこの復帰を許可しない。

## 3. 同期と状態遷移

```text
private未共有 → preview（未永続・10分有効）
  → owner TX: PENDING + shareVersion増分 + desired_projection/対象version
  → AFTER_COMMIT event
  → 非TX coordinator → team TX: projection upsert
  → 非TX coordinator → timeline Service TX: source UUIDでupsert
  → owner TX: contentRevision/shareVersion一致ならVISIBLE（不一致なら旧ackを破棄）

PENDING → FAILED（業務原本は保存済み）→ 本人明示retry → PENDING
PENDING/VISIBLE/FAILED → 本人取消 → REVOKED
team VISIBLE/PENDING → 管理者非表示 → MODERATED（再試行では復活不可）
```

EffortShareRequestedEventは原本ID、owner ID、share ID、sourceVersion、shareVersion、grantMembershipIdとrouting IDのみを持つ。非TX listener/coordinatorがowner Serviceで現在のdesired projectionを取得し、team Service→timeline Service→owner ackを順番に呼ぶ。各Serviceが自身のTXを完了してから次へ進み、@Transactionalの自己呼出しを使わない。同期失敗は非TX coordinatorがERROR＋監査を記録し、owner側FAILEDを別TXで記録する（contentRevision/shareVersion一致時のみ）。rollback-only TX内でcatchして業務成功と見せない。

AFTER_COMMITは通知規約に合わせ、通常イベントの即時自動リトライをしない。イベント消失/投入拒否/プロセス停止でPENDINGが残る場合は、監視が60秒超のpendingを検知する。本人はGET応答の状態で確認でき、60秒超PENDINGの再試行要求も、owner CASでFAILEDへ移してから同じdesired commandを再実行できる。運用者による再送は専用保守コマンドでshare UUID/versionを指定し、当該commandを再読込して実行する。勝手に古いpayloadを再送しない。イベントは配送の唯一の正本ではなく、owner行のdesired状態が正本。

team upsertはsourceVersion/shareVersionが現在許可と一致することをowner Serviceで直前確認し、古いversionを拒否。team行のMODERATEDは終端であり、owner側のVISIBLE ackが遅れても読取時にteam状態を必ず確認する。私的内容編集でcontentRevisionが増えた瞬間から旧投影はF00非表示。projection→timelineの間に停止しても、再送はshare UUIDを一意sourceにして同じタイムライン投稿を更新する。時刻/並び順createdAtは初回共有のまま、updatedAtだけ更新し新着を乱発しない。

team upsertのTXは、検証済みdesired projectionとcontentRevision/shareVersion/hashを書き込み、team行のstateを**VISIBLEにしてcommit**する（team PENDINGのまま終了しない）。続くtimeline upsertが成功してから、owner ack TXが同じcontentRevision/shareVersion/hashについてowner share_state=VISIBLEとsynced_source_versionを確定する。F00の許可にはteam VISIBLEに加えowner VISIBLEと同期版一致の両方が必要なので、team commitからowner ackまで内容は非表示のままとなる。初回だけでなく既存原本の訂正でも、ownerは先にPENDINGとなり、teamの新しいprojectionをVISIBLEでupsert→timelineの対応版更新→owner ackの同じ順序を使う。旧版team VISIBLE、更新途中の新しいteam VISIBLE、owner FAILEDはいずれも全条件を満たさず非表示。再試行はこの順序を冪等に完了し、正常時にowner/team両方がVISIBLEへ到達する。

タイムラインに新しいsource type `PERSONAL_EFFORT_SHARE` とUUID source参照を追加する。既存createSystemVillagePostのUUID経路はVILLAGE専用であり流用しない。下記のTEAM専用内部Serviceを新規追加し、BIGINT source IDへ変換しない。新規投稿にはshare_with_friends=false、forward sourceなし、外部公開不可、閲覧TEAM固定、全interaction capability=false。通常createPostのparentId、通常PUT、reaction、comment、引用/repost、フレンドチーム転送の各BE入口でsource typeを判定して禁止する。通常投稿は現行機能を維持する。

取消はowner TXでREVOKED＋shareVersion増分を先にcommitし、AFTER_COMMITでteam/timelineを非表示にする。F00はowner許可とcontentRevision/shareVersionを読むため、物理的な削除の完了を待たずstale payloadを返さない。管理者非表示はteam TXを先にcommitして即deny、その後ownerへ状態を通知する。通知が失われてもteam状態を読めば禁止は継続する。つまり、通知（owner への反映）が欠けても、F00 は読み取り時にteamのMODERATEDを見て即deny（待ち時間なし）し、MODERATEDは終端なので本人のretryや編集でも復活しない。teamの削除状態もF00で確認する（親組織の削除・離脱はチーム共有の可否に使わない）。投稿者の退会は下記の既決保持方針に従い本文を維持し、著者表示だけ匿名化する。

F00 resolverはprivate sourceにはowner一致、shared sourceには閲覧者の現在team所属・投稿者の加入期間IDと資格終了理由の確認・team有効・projection state・owner許可（退会purge後は非本文tombstone）・contentRevision/shareVersion・hash一致を確認する。team一覧のSQLで取得したprojectionを最終表示前にbatch判定する。判定は一覧・詳細・個人集約timeline・リンク展開・通知本文preview・フレンドチーム転送・外部公開を含む全経路で同じServiceへ集約する。全体検索（#4647・#4661・#4700）はF00の個別判定ではなく、timeline の検索SQLに `NOT EXISTS timeline_effort_sources` を足して努力由来を常に除外する。件数（count）とページ境界も同じ条件で絞るので、件数から存在が漏れない（[API契約§6](F06.4.1_personal_effort_records_api.md#6-エラー割当)）。キャッシュへ内容を固定保存してこの判定を省略しない。個人の最近activity/監査/通知へprivate値をコピーしない。共有通知の新規配信自体は今回範囲外。

## 4. 障害・競合の検証表

| 注入点 | 必須の観測結果 |
|---|---|
| private保存commit前の例外 | 原本もreceiptも残らず、共有なし |
| private保存後、share要求前の通信切断 | 原本は取得可能。別key再作成を誘導しない |
| event publish/async拒否/停止 | 原本PENDINGが残り、監視と本人表示で検知。未共有としてteamは非表示 |
| team upsert後、timeline失敗 | 原本FAILED、team投影は存在してもowner未確定のため非表示。再試行で同じtimelineへ収束 |
| timeline成功後、owner ack失敗 | team/timelineはowner PENDINGのため非表示。再送upsertで1件に収束 |
| source v2より後にv1イベント到着 | v1はupsert/ack不可。最新値を上書きしない |
| 取消後に遅延create/update到着 | owner許可REVOKEDでdeny、shareVersionの古い作成を拒否 |
| 管理者非表示後に本人retry/編集 | team MODERATED維持。原本だけは更新可能 |
| 別team移行と旧teamイベント競合 | 原本のcurrent share ID/team/versionと不一致なら旧teamは不可視 |
| F00/owner shard/profile照会の障害 | private値を返さずエラー。認可不能を許可へ倒さない |

## 5. ライフサイクルと移行検証

既決の [退会フロー§13.13](../architecture/withdrawal_flow_immediate_anonymization_fix.md) に従う。退会申請時は本人のprivate APIアクセスを停止するが、猶予期間中の原本を不可逆消去しない。共有本文は残し、UserAnonymizedEventでは著者表示だけ「退会者」へ匿名化する。退会だけを理由に既存共有をREVOKEDにしない。AccountPurgedEvent（30日後）でprivate values/note/definition snapshot/共有mapping/receipt responseを消去する。共有許可の判定に必要なowner route/source UUID/contentRevision/shareVersion/grantMembershipId/state/hashだけを非本文tombstoneに残し、共有projectionの本文を維持する。tombstoneの値なしでF00が検証できない状態ならfail closedとする。

purgeリスナーは既存のpurge completion tracking/retry基盤へeffortrecord担当として登録し、owner消去とreceipt消去の完了を冪等に記録する。途中失敗で完了を記録せず、既存purge再試行で収束させる。ユーザーの明示した原本削除/共有取消は退会とは別で即REVOKEDを確定し、tombstoneにも反映する。退会撤回期間中の原本は復帰可能、共有を自動再投稿しない。チーム削除はprivate原本を消さず、チーム側projectionを論理削除する。チーム脱退・所属解除等による共有資格喪失は§8の加入期間終了で共有解除する（2026-11-09裁可）。アカウント退会だけによる本文保持と混同せず、明示退出失効を退会処理で解除しない。

**GDPR個人データエクスポート**: `effort_records` は個人データエクスポート（`PersonalDataCollector` のカテゴリ `effort_records` → `effort_records.json`）の対象。本人の原本のみを出力し（削除済み・purge済みは除く）、項目は本人入力の値・定義名/定義版・recordedOn・recordTimezone・note・作成/更新日時に限る。他人のデータ、内部hash、共有の内部状態、receiptは含めない（実装: `EffortPersonalDataService`、検証: `EffortRecordGdprExportIT`）。

実装時には既存activity/team/user/timelineデータを含むFlyway実MySQLで、無変更保全、同一migration再起動、全表照合順序、UUID version nibble=7、FKがeffort definition内部だけ、制約違反、indexによるEXPLAIN、非TX境界の部分失敗と順逆配送を検証する。migration majorはマージ時最大+1、minorはUTC日時で採番。設計段階では架空のFlyway番号を確定しない。Entity/migration変更時の自動ER再生成とOpenAPI生成は実装PRで行う。

### 5.1 チーム削除と E2E の後始末

実機 E2E は専用のテストチームを作り、終わったらチームごと削除する。ただし `teams` は `deleted_at` による論理削除なので、チームを削除したときに何が起きるかを実コード（2026-11-22 時点）で確かめた結果を次に示す。

**チーム削除で起きること**: `TeamService#deleteTeam` は `teams` 行を論理削除（`softDelete`）し、`PersonalInviteScopeClosedEvent` と `TeamDeletedEvent` を発行するだけである。`TeamDeletedEvent` の購読は、schedule（カレンダー層・予定の保持）、scopefolder（`my_scope_folder_items` の該当 team_id を物理削除）、team の監査、team の加盟の片付け（`TeamOrgLifecycleListener`）の4系統で、effortrecord・activity・timeline は購読していない。`teams` 行を物理削除する経路はない（`TeamPurge*` はユーザー purge 用）。

| 区分 | 対象 | 削除後の状態 |
|---|---|---|
| 消える | `teams`（論理削除。slug 解決・チーム一覧から外れる）、scopefolder の `my_scope_folder_items`（物理）、加盟の PENDING | 即時〜AFTER_COMMIT の後処理 |
| 残る（現状） | `effort_definitions` の TEAM 行・`effort_definition_revisions`、`effort_records`（本人の原本と共有状態の列）、`activity_templates`・`activity_template_fields`・`activity_results`、`timeline_posts`、`memberships` | そのまま残る（チーム削除時の連動なし） |
| PR-3 で増える表（削除時の扱い） | `effort_team_shares`・`timeline_effort_sources`・TEAM の `effort_operation_receipts` | PR-3b で `TeamDeletedEvent` を購読し、`effort_team_shares` を後処理で論理削除する（§5 のチーム削除の記述どおり）。物理削除はしない |

AC-51（E13）が対象とするのはチーム削除だけで、組織削除は扱わない。根拠は2つある。(a) チーム削除では `TeamDeletedEvent` の後処理で `effort_team_shares.deleted_at` を立てる（物理削除はしない）。(b) 親組織の削除・離脱は、チーム共有の可否の判定に使わない（チームは親組織0件・複数件があり得る）。

**残っても他に影響しない理由**: (1) effort・activity・timeline の表は teams への FK を持たない（クロスドメイン FK 禁止。`scope_type`/`scope_id` か `team_id` の ID 参照だけ）ので、論理削除で参照整合が壊れない。(2) 共有の読み取りは F00 と資格 batch がチームの有効性を毎回確認し、削除済みチームは即 deny する（§3）ため、残った共有・投稿は誰にも返らない。(3) `teams` が論理削除されると slug 解決と所属チーム一覧から外れ、URL でも到達できない。(4) 本人の原本・個人グラフは owner 側で完結し、定義 snapshot を原本が保持しているため、チーム側の行が残っていても消えていても本人の閲覧・集計に影響しない。(5) 論理削除後も行が残るので、同じ slug は再利用できない。E2E は毎回一意の slug（例 `e2e-effort-<日時>`）でチームを作る。

**物理的に消す必要がある場合**（E2E データの衛生・容量。通常は論理削除のまま残してよい）は、自分が作った E2E 専用のチーム ID だけを対象にし、既存利用者のデータや作成元不明のデータ、テストユーザー 991783・991784 は含めない。FK の向きから、次の順で消す。

1. `timeline_effort_sources`（対象 team_id。`timeline_posts` への FK を持つので投稿より先）。PR-3 適用後のみ
2. `timeline_posts`（`scope_type='TEAM'` かつ対象 scope_id。子の返信は parent の CASCADE で消える）
3. `effort_team_shares`（対象 team_id）と、TEAM 側の `effort_operation_receipts`（`route_kind='TEAM'`・route_id=対象 team_id）。PR-3 適用後のみ
4. `effort_records` のうち E2E 専用ユーザーの行で `share_team_id` が対象のもの（effort_records は他表への FK を持たない）
5. `effort_definition_revisions`（対象 TEAM 定義の `definition_id`）→ `effort_definitions`（`source_type='TEAM'`・対象 `team_id`）。revisions が definitions への FK を持つので revisions が先
6. `activity_results` とその子（`activity_participants` など。`activity_results.template_id` は RESTRICT なので templates より先）
7. `activity_template_fields`（templates への CASCADE）→ `activity_templates`（対象 scope）
8. `memberships`（対象 scope）→ `teams`（物理削除する場合だけ。論理削除のままでもよい）

削除前に対象の ID・作成元・関連範囲を確認し、削除後に件数を再確認する。

## 6. 版の独立性と更新表

versionは原本行の@Version（CAS用）、contentRevisionは日付/values/private noteの内容版、shareVersionは共有許可・mapping・allowlistの版である。source_version列/API sourceVersionはcontentRevisionを指し、@Versionとは比較しない。ackの状態更新で@Versionが増えても可視性は失われない。projection hashには共有内容と共有定義revisionを含める。

| 操作 | version | contentRevision | shareVersion |
|---|---|---|---|
| 原本作成 | 0 | 1 | 0 |
| 日付/値/note内容更新 | +1 | +1 | 不変（既存mappingで新しいdesiredを作る） |
| 初回共有/再共有/allowlistやmapping変更 | +1 | 不変 | +1 |
| PENDING→VISIBLE ack / FAILED記録 | +1 | 不変 | 不変 |
| 同一desiredのretry | +1 | 不変 | 不変 |
| 本人取消/原本削除 | +1 | 削除では不変 | +1 |
| 管理者非表示 | team version+1、owner通知反映時+1 | 不変 | 不変（team MODERATEDで終端） |

API previewは@Versionで同時編集を検知し、投稿時にもversionを要求する。F00はcontentRevision/shareVersionを比較する。retry/ackで変更されたversionは次回owner GETから取得し、内容版を推測しない。purge後tombstoneでは版を固定し、共有の新規編集や再共有を許可しない。

## 7. TEAMタイムラインへの追加契約

タイムラインドメインへ次の対応表を新規追加する（この表もUuidV7Entity）。timeline_posts.idは既存BIGINTを維持する。値はtimeline_posts.contentへ複写せず、contentは固定の非個人文言キー用識別子のみとし、DTO生成時に許可済みSharedRecordをhydrateする。

```sql
CREATE TABLE timeline_effort_sources (
  id BINARY(16) NOT NULL,
  team_id BIGINT UNSIGNED NOT NULL,
  timeline_post_id BIGINT UNSIGNED NOT NULL,
  share_uuid BINARY(16) NOT NULL,
  grant_membership_id BIGINT UNSIGNED NOT NULL,
  share_version BIGINT NOT NULL,
  content_revision BIGINT NOT NULL,
  is_revoked BOOLEAN NOT NULL DEFAULT FALSE,
  created_at DATETIME(6) NOT NULL,
  updated_at DATETIME(6) NOT NULL,
  PRIMARY KEY (id), UNIQUE KEY uq_timeline_effort_share (share_uuid),
  UNIQUE KEY uq_timeline_effort_post (timeline_post_id),
  KEY idx_timeline_effort_team (team_id, is_revoked),
  CONSTRAINT fk_timeline_effort_post FOREIGN KEY (timeline_post_id) REFERENCES timeline_posts(id),
  CHECK (grant_membership_id >= 1 AND share_version >= 0 AND content_revision >= 1)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;
```

新規内部 `TimelineEffortSourceService.upsertTeamShare(teamId,shareUuid,shareVersion,contentRevision,grantMembershipId)` は認可済みcoordinatorだけが呼ぶ（外部Controller公開なし）。team Serviceで現在の共有state/版と権威加入期間IDと資格の一致を確認し、timeline自身のTXで投稿と対応表を原子的upsertする。同一share UUIDは投稿1件、古い版はno-op、同版再送は同一post ID、撤回済み旧版で復活不可。`revokeTeamShare(teamId,shareUuid,expectedGrantMembershipId,expectedShareVersion,expectedContentRevision)` は、対応表の保存加入期間IDと両版がすべて一致する行だけを同じtimeline TX内でCAS更新し、その更新成功時だけ対応postを論理削除する。不一致はno-opであり、投稿を先に隠さない。将来の再共有は現在有効な加入期間IDで新しい本人許可shareVersionのときのみ復帰し、MODERATEDを解除しない。

upsertは対応表を行lockし、既存grant_membership_idと入力加入期間IDが同じ場合はshareVersion/contentRevisionの単調性を検証する。加入期間IDが異なる置換は、現在資格が入力IDと一致し、team shareがそのIDの新しい本人許可で確定済み、かつ入力shareVersionが保存値より大きい場合だけ認め、加入期間IDと両版を同一更新で保存する。古いm1のupsertは現在資格照合で拒否する。m2で再共有済みの同じshare UUIDへm1失効eventが遅延到着しても、revokeのexpectedGrantMembershipId=m1が保存m2と不一致になるため、m2の対応表も投稿も変更しない。取消/脱退coordinatorは失効対象のteam shareから取得した加入期間IDと両版を渡し、版競合時は現在の対象加入期間がまだ失効対象であることを再確認してから再実行する。

timeline→effortの照会は非TX Facade/read hydratorから行い、timeline TX内で別ドメインRepositoryへアクセスしない。投稿本文、検索index、通知preview、forward payloadに値を保存しない。既存の全timeline取得/検索/転送/公開/親ID/反応経路は対応表存在の判定を含む共通source guardを先に通し、未対応のread pathを残した状態で導線を有効化しない。

### 7.1 purge後tombstoneの具体形

別表を増やさずeffort_records行をtombstoneとして使用する。AccountPurgedEvent処理はvalues_json={}、definition_snapshot={}、private_note=NULL、share_mapping_json=NULL、share_definition_snapshot=NULL、desired_projection=NULL、selected_field_keys=NULL、last_error_code=NULL、purged_at=現在UTCを同一owner TXで確定する。owner_user_id/id/definition_id/版/share routing ID/grant_membership_id/state/desired_hash/synced_source_versionのみ残す。purged行のcreatedAt/recordedOnは公開DTOへ返さず、個人一覧/詳細/集計はpurged_at IS NULLを必須にする。通常Entityの@SQLRestrictionはdeleted_at IS NULL AND purged_at IS NULLとする（原本表だけ）。

purge で消す列と残す列は次のとおり確定する（`effort_records`。個人データを消し、共有の許可検証に要る列だけを残す）。

| 区分 | 列 |
|---|---|
| 消す（空にする） | `values_json`（`{}`）、`definition_snapshot`（`{}`）、`private_note`、`share_mapping_json`、`share_definition_snapshot`、`desired_projection`、`selected_field_keys`、`last_error_code`（いずれも NULL） |
| 立てる | `purged_at`（現在 UTC） |
| 残す | `id`・`owner_user_id`・`definition_id`・`definition_revision`・`version`・`content_revision`・`share_id`・`share_team_id`・`share_state`・`share_version`・`grant_membership_id`・`desired_hash`・`synced_source_version`・`share_updated_at`、NOT NULL の `recorded_on`・`record_timezone`・`created_at`・`updated_at`（公開 DTO へは返さない） |
| 別に消す | owner のレシート（`effort_operation_receipts` の本人分。応答本文を含むため） |

既存の `EffortRecordPurgeService` は `selected_field_keys` と `last_error_code` を消していないので、この表に合わせる改修が要る（PR-3b の退会/匿名化/purge リスナーの成果物。既存の消去列は変えず、この2列を足し、IT で全消去列が NULL・残す列が不変であることを検証する）。

shared F00専用のRepository projection queryは認可済みowner routeとsource UUIDで、上記許可・版・hash列だけをSELECTする。purged_at有無を問わず読める専用native queryとし、JSON本文列をSELECTせず、deleted_atがあれば明示削除としてdenyする。これにより@SQLRestrictionでtombstoneを見失わず、一般APIからpurged行へ到達させない。共有取消のtombstoneはREVOKEDを保持し、purgeでVISIBLEへ戻さない。

### 7.2 努力由来投稿に許す操作と禁止する操作

努力由来の投稿（対応表 `timeline_effort_sources` に行がある投稿）への操作を、BE の各入口で対応表の存在により判定する。禁止は 403 EFFORT_003 に統一する（操作別にコードを分けない）。deletePost の案内は FE が出す。既存の通常投稿の挙動は変えない。

| 操作 | 努力由来投稿 | 備考 |
|---|---|---|
| 閲覧（一覧・詳細・検索・リンク展開） | F00 を通ったときだけ許可 | 通らなければ非表示（詳細は404） |
| like / mitayo / comment / reply / quote / repost | 禁止（EFFORT_003） | 削除側（いいね解除など）も同じ |
| 通常の updatePost（本文更新） | 禁止（EFFORT_003） | 値の訂正は原本の PUT だけ |
| 通常の deletePost | 禁止（EFFORT_003） | 取消 API（本人取消）へ誘導する。投稿だけが消えて共有状態と食い違うことを防ぐ。応答の形は[API契約§6](F06.4.1_personal_effort_records_api.md#6-エラー割当) |
| pin / bookmark | 禁止（EFFORT_003） | 誘導先なし。値が投稿の複製として長期保存されることを防ぐ |
| フレンドチーム転送・外部公開・share_with_friends の変更 | 禁止（EFFORT_003） | 作成時から false 固定 |
| 本人取消（`DELETE /effort-records/me/{id}/team-share`） | 許可 | 許可失効をowner TXで確定し、投稿を非表示にする |
| 原本の訂正（`PUT /effort-records/me/{id}`） | 許可 | 同じ share UUID・同じ投稿を更新 |
| 管理者非表示（`DELETE /teams/{teamId}/effort-records/{shareId}`） | 許可（ADMIN・委任 DEPUTY_ADMIN） | MODERATED |
| 既存の通報・モデレーションによる非表示 | 許可 | 結果を MODERATED へ寄せる（下記） |
| 活動履歴への遷移（「活動履歴で見る」） | 許可 | 操作ではなく画面遷移 |

既存の通報・モデレーションが努力由来の投稿を非表示または削除したときは、タイムライン側の操作から対応表を経由して effort の MODERATED を確定する（管理者非表示と同じ終端状態）。確定の通知が失われても、F00 は投稿の非表示・削除状態を読むため表示は止まり、本人の retry・編集で復活しない。timeline TX 内で effort のRepositoryを呼ばず、AFTER_COMMIT の非 TX coordinator が effort Service を呼ぶ。

## 8. チーム共有資格の権威状態と加入期間ID

origin/main `7a16dea8f6` 時点の tree（2026-11-09 の照合 `dced3a9312e` から DefaultAccessControlService・MembershipService・RoleService・common/visibility に変更なしを `git log` で確認）の DefaultAccessControlService#isMember はmembershipsのuser/scope/left_at IS NULLを直接照会する。TEAMには組織所属継承/委任による救済はない。isRegularMemberOrAboveはSUPPORTERを除き、在籍のないSYSTEM_ADMINも許可しない。今回の共有資格は要件の「所属」に沿いisMemberの直接TEAM所属を使う。SUPPORTERを含む所属ロールの別条件を新規追加せず、新しい資格計算式を複製しない。isRegularMemberOrAboveへの引上げは今回の裁可事項ではない。

共有資格のロール境界は次のとおり固定する。(1) SUPPORTER は、そのチームへ直接所属していれば共有できる（isMember の直接所属で判定し、ロールで除外しない）。(2) そのチームへ所属していない SYSTEM_ADMIN は、一覧・共有・非表示のいずれも回り込めない（SYSTEM_ADMIN だからといって可視性や共有資格をバイパスしない）。(3) 直接所属を保ったままのロール変更（例: MEMBER から ADMIN、ADMIN から MEMBER）では加入期間を失効させず、旧共有を維持する。加入期間が終わる（left_at が付く）場合だけ失効の対象になる。

MembershipService#joinは再加入で新INSERTし、旧membership.idを再活性化しない。この既存BIGINT IDを**grantMembershipId（加入期間ID）**として原本のgrant_membership_id、team shareのgrant_membership_id、previewToken、desired commandへ束縛する。独自epoch表・scope全体cache世代・追加カウンタは作らない。同じuser/teamでも旧ID m1と再加入ID m2は別許可である。

F00は閲覧者の現在所属を確認したうえで、投稿者のgrantMembershipIdをTEAM側のmembership Serviceから照会する。通常は同じuser/teamの現在有効な直接所属IDが保存IDと一致する場合だけ許可する。m1をleft_atで終了した直後から旧共有はdenyであり、ownerシャードの非同期失効を待たない。再加入m2もm1を有効に戻さない。旧preview/command/retry/ackはm1の不一致で拒否し、新previewでm2へ束縛した本人許可だけを受ける。

アカウント退会§13.13に伴う所属整理だけは既決の本文保持を守るため、終了理由をTEAM側で判定可能にする最小列を追加する。クロスドメインFKは追加しない。

```sql
ALTER TABLE memberships
  ADD COLUMN effort_share_disposition VARCHAR(32) NULL,
  ADD CONSTRAINT chk_membership_effort_share_disposition
    CHECK (effort_share_disposition IS NULL OR effort_share_disposition IN
      ('REVOKED','RETAINED_ACCOUNT_WITHDRAWAL'));
```

既存在籍行のNULLは通常のactive membershipとして扱う。既存の終了済みNULL行は共有許可なし（移行前の終了行から本機能の共有は存在しない）。MembershipService#leave :163-210のuser lock→membership悲観lock→left_at設定と同じTEAM側TXで、明示脱退/管理者所属解除はREVOKED、退会処理内部の所属整理はRETAINED_ACCOUNT_WITHDRAWALを確定する。既存AccountPurgedEvent→RolePurgeEventListener→RolePurgeScopeExecutor→RoleService#removeMemberWithoutAdminCheckは通常除名と同じLeaveReason.REMOVEDを使うため、既存leaveReasonだけでこの区分を推測しない。退会内部からの終了窓口へendCause=ACCOUNT_WITHDRAWALを明示伝達し、通常のRoleService所属解除はendCause=EXPLICIT_MEMBERSHIP_ENDとする。ACCOUNT_WITHDRAWALは外部リクエストの任意reasonで指定させず、退会内部経路だけに限定する。role変更だけで直接所属が続く場合は加入期間を失効させない。RoleService経由の所属解除でleft_atを設定する場合は同じMembershipService終了境界でREVOKEDとする。

read専用の例外は、保存grantMembershipIdそのものの所属がRETAINED_ACCOUNT_WITHDRAWALで、user/team一致、REVOKEDではない場合だけ。共有本文維持と著者匿名化を許可するが、新preview/訂正/retryには現在activeな資格と有効アカウントが必要。UserAnonymizedEvent/AccountPurgedEventはREVOKEDをRETAINEDへ変更しない。明示退出と退会整理が競合した場合も同じuser/membership lockを使い、REVOKEDを優先する。退会整理が先にleft_atを設定しても、同じ加入期間を対象とする明示退出の確定はREVOKEDへ上書きできる。逆順では退会整理がREVOKEDを覆さない。撤回は原本アクセスを回復できるが、終了済み旧membershipを再活性化せず、明示退出済み共有を復活させない。

新規内部 `MembershipService.getEffortShareQualificationsBatch([(teamId,userId,grantMembershipId)])` はService経由で既存authorityと加入期間の終了理由を一括取得し、`{teamId,userId,grantMembershipId,isCurrentEligible,disposition}` を返す（public Controllerへ公開なし）。F00/read、owner GET、共有coordinatorが利用する。owner GETは資格終了を実効state=REVOKEDとして返し、owner行の後処理遅延中でも古いVISIBLE/FAILEDのretry導線を出さない。権威照会不能はfail closed/503。cache・検索・集約でも同じread判定を省略しない。退出commit後に認可する応答には旧共有を返さず、長期ストリームへ無期限に値を保持しない。

この資格batchのfreshnessは、既存 `ContentVisibilityChecker#canViewUuidIsolated`（単件、`@Transactional(REQUIRES_NEW, readOnly=false)`）の独立PRIMARY再評価境界に合わせる。単件F00は既存のproxy経由・元read TX終了後の境界へ接続し、ガードを独自再実装しない。一覧用の資格batchは本機能で新実装し、scope/ページ単位のbounded batch内部の資格読取1回を、**PRIMARYへ接続するproxy経由の短い独立新TX（REQUIRES_NEW、readOnly=false、isolation=READ_COMMITTED）で最新committed状態を取得する境界**に置く。既存filterAccessible自体にこの注釈があるとは仮定せず、単件窓口を件数ループして新TXを乱発しない。元read TXを終了してから資格を再評価し、呼出元の既存read TX・REPLICA・先に開いたREPEATABLE READ snapshot・request内の旧membershipメモを使わない。既存TX内でルーティングThreadLocalだけをPRIMARYへ切り替えても接続は替わらないため、その方法を代用しない。F00以外のowner GET・coordinator・preview/共有確認もこの新しい資格batchの同じ境界を使う。退出commit後に開始する再評価が終了済み加入期間を確認した場合は、以前のread結果がactiveでもdenyする。

既存MembershipChangedEvent REMOVED / MembershipEndedEventにはmembershipIdがないため、そのuser/teamだけを根拠に全共有を失効させない。終了TXから専用 `TeamEffortMembershipRevokedEvent(teamId,userId,endedMembershipId)` をAFTER_COMMITで発火し、非TX coordinatorが**grant_membership_id=endedMembershipIdの共有だけ**をteam/owner/timelineで冪等にREVOKEDへ反映する。既存TeamMemberRemovedEventはunfollow専用なので通常脱退の汎用根拠にしない。配送失敗はログ・再送で補う。終了済みmembershipのREVOKED dispositionと未失効team shareをgrant_membership_idで突合する保守再実行も用意し、イベント消失時も失効処理の対象IDを復元できる。再送は保存加入期間IDで対象を限定する。即時denyはDBのmembership終了状態で既に保証する。旧m1の遅延eventは、新m2でpreview済みの共有を失効させない。team/owner/timelineの更新とackは加入期間ID・shareVersion・contentRevisionを対象CASへ含める。

| 競合・障害 | 必須結果 |
|---|---|
| 明示脱退/管理者所属解除→失効event停止 | TEAM membership終了状態で全read即deny、原本/個人グラフ維持 |
| REPLICAは旧activeのまま、または先に開いたRR snapshotがactive→PRIMARYで退出commit→資格再評価 | 既存の独立PRIMARY新TXで最新committed終了状態を取得しdeny。新batchはREAD_COMMITTEDに固定し、旧接続/旧メモへ戻さない。F00/owner GET/coordinator/previewで同条件を検証 |
| m1退出→m2再加入→旧preview/retry/ack | 旧m1を409/deny、新preview必須、自動復活なし |
| m2で新共有後にm1終了event到着 | 新共有を失効させず、m1へ束縛された旧共有だけREVOKED |
| 原本編集/共有送信と資格喪失の競合 | 古い加入期間の送信/ackが残っても最終readでdeny、原本のみ保存 |
| ACCOUNT_WITHDRAWALと明示退出が順逆 | 単独退会は共有本文維持/著者匿名、明示退出があればREVOKED優先 |
