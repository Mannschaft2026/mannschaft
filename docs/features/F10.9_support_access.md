# F10.9: 本人承認制のサポート閲覧（代理ログイン）

> **ステータス**: 🟡 実装中（戦役 Z-B。BE 中核＝DB・API・状態遷移・監査・通知は実装済み。代理ヘッダーの解釈・読取専用の強制・FE は後続）

> **最終更新**: 2026-11-26
> **関連**: [03 ロール・権限モデル §3.6](../security/03_role_authority_model.md)・[F10.3 監査ログ](F10.3_audit_logs.md)

## 1. 概要

運営（SYSTEM_ADMIN）が利用者の不具合を再現・確認するために、**本人の承認がある場合に限り**、本人の視点でその画面を**閲覧のみ**できる仕組み。旧「管理者変身」（`X-Admin-Impersonate-User-Id`・承認なし・書換可・運営者の権限を引き継ぐ）を置き換えて廃止する。

マスター決定（2026-11-26）:

- 運営は**運営専用アカウント**を使う（チーム・組織等に所属しない）。個人アカウントとの併用は禁止。
- 代理される**本人の承認＋記録**で運用する。代理中は**見るだけ**（書換・投稿・削除・送信は不可）。
- 許可の有効期限は**24時間**（延長不可）。本人はいつでも取り消せる。
- 運営は依頼時に**理由（必須）**を入力する。本人へ通知する。閲覧の記録を本人も自分の設定画面で見られる。
- 承認依頼・許可の操作は代理中に行えない（自己許可の抜け道を塞ぐ）。
- 許可時は本人の**再認証（パスワード／パスキー）必須**。メールのワンクリック許可は不可。依頼理由はプレーンテキスト表示。
- 未成年・後見下の利用者は、**本人と保護者の両方**の承認で初めて有効。
- 代理中のダウンロード（署名 URL）・CSV/PDF 等の書き出しはすべて禁止。
- 保存期間: 許可・依頼 3年、閲覧記録 1年（日次バッチで物理削除）。
- 旧代理ログインは新しい仕組みと同時に切り替える。

## 2. 利用者の流れ

1. **運営の依頼**: 対象ユーザー・理由（10〜1000字）・任意の参照（例: FEEDBACK #id）。`PENDING`。依頼自体は72時間で失効。
2. **本人へ通知**: アプリ内通知（高優先度）。未成年・後見下は保護者へも。リンク先は `/settings/support-access`。
3. **本人の判断**: 再認証つきで許可すると `APPROVED`、期限は許可時刻＋24時間に固定。拒否なら `DENIED`。未成年・後見下は本人と保護者の両方が許可して初めて `APPROVED`（期限は最後の許可＋24時間）。
4. **代理閲覧**: 運営が「閲覧を開始」すると開始記録が残り、本人へ通知する。以後の各リクエストは閲覧記録に1行ずつ残る。**開始前・終了後の許可でヘッダーを付けても 403**。
5. **終わり方**: 運営の終了、本人（保護者）の取消（`REVOKED`）、24時間経過（`EXPIRED`）、運営の撤回（`CANCELLED`）、本人の退会申請（`REVOKED`・`WITHDRAWAL`）。いずれも次のリクエストから即座に拒否する（判定は毎回 DB・時刻で行い、キャッシュしない）。

## 3. データモデル

migration: `V274.20261126221600__create_support_access_tables.sql`。パッケージ `com.mannschaft.app.supportaccess`（`admin` とは別ドメイン）。`users` へは FK を張らず ID だけ持つ（原則1）。grants と logs は同一ドメインなので FK あり。ER 図は `docs/architecture/er/` を参照。

### `support_access_grants`（依頼と本人許可）

| カラム | 説明 |
|---|---|
| `id` | UUIDv7（`BINARY(16)`） |
| `operator_user_id` / `target_user_id` | 運営者・本人（`users.id`・FK なし） |
| `status` | `PENDING` / `APPROVED` / `DENIED` / `REVOKED` / `EXPIRED` / `CANCELLED` |
| `request_reason` | 依頼理由（必須・プレーンテキスト） |
| `reference_type` / `reference_id` | 依頼の参照元（任意） |
| `requested_at` / `request_expires_at` | 依頼時刻 / 依頼の失効（+72h） |
| `decided_at` / `deny_comment` | 本人の許可・拒否の時刻 / 拒否コメント |
| `expires_at` | 許可の期限（最後の許可+24h・固定） |
| `revoked_at` / `ended_reason` | 取消時刻 / `USER_REVOKED`・`OPERATOR_CANCELLED`・`EXPIRED`・`WITHDRAWAL`・`OPERATOR_INELIGIBLE` |
| `last_session_started_at` | 直近の閲覧開始 |
| `active_session_started_at` / `active_session_ended_at` | 閲覧開始・終了。NULL（未開始）または終了が開始より後ならヘッダーは 403 |
| `guardian_approval_required` / `guardian_user_id` / `guardian_decided_at` | 保護者の承認（未成年・後見下） |
| `open_flag` | 生成列（`PENDING`/`APPROVED` のとき 1）。`UNIQUE (operator, target, open_flag)` で同じ組合せの**同時1件**を担保。Entity では `insertable=false, updatable=false` |

### `support_access_logs`（閲覧記録）

`grant_id`（FK）・運営者・本人・`event_kind`（`SESSION_START`/`VIEW`/`DENIED`/`SESSION_END`）・`http_method`・`request_path`（**クエリ文字列は保存しない**）・`route_pattern`・`scope_type`/`scope_id`（パスから推定）・`http_status`・`deny_code`・`occurred_at`。

## 4. API

**運営側** `/api/v1/system-admin/support-access`（`SecurityConfig` の ROLE_SYSTEM_ADMIN 規則で保護。自分の依頼だけを扱い、他の運営者の依頼は 404）

| メソッド | パス | 内容 |
|---|---|---|
| POST | `/grants` | 依頼（201）。`{targetUserId, reason, referenceType?, referenceId?}` |
| GET | `/grants?status&targetUserId&cursor&limit` | 自分の依頼一覧（cursor = 直前ページ末尾の `requestedAt`） |
| GET | `/grants/{id}` | 詳細 |
| POST | `/grants/{id}/cancel` | 撤回（`CANCELLED`） |
| POST | `/grants/{id}/sessions` | 閲覧開始（開始記録・本人へ通知）。`{grantId, targetUserId, targetDisplayName, expiresAt}` |
| POST | `/grants/{id}/sessions/end` | 閲覧終了（204） |
| GET | `/grants/{id}/logs?cursor&limit` | 閲覧記録 |

**本人側** `/api/v1/me/support-access`（認証主体のみ。grant の対象本人または保護者以外には 404）

| メソッド | パス | 内容 |
|---|---|---|
| GET | `/grants?status&cursor&limit` | 自分（保護者の場合は子）宛の依頼・許可。運営者は表示名のみ |
| POST | `/grants/{id}/approve` | 許可。本文 `{currentPassword}` または `{passkeyAssertionJson}`（再認証必須）。期限は24時間固定 |
| POST | `/grants/{id}/deny` | 拒否 `{comment?}` |
| POST | `/grants/{id}/revoke` | 取消（いつでも） |
| GET | `/logs?grantId&cursor&limit` | 自分の画面が閲覧された記録（日時・運営者の表示名・パス・スコープ。メールなし） |

パスキーでの再認証は、既存の `POST /api/v1/auth/webauthn/reauthenticate/begin` でチャレンジを取り、署名結果（`credentialId`・`authenticatorData`・`clientDataJson`・`signature`・`signCount`）の JSON を `passkeyAssertionJson` に入れて許可 API へ送る。署名検証だけを共有し、F18 提示モードの再認証フラグ（Valkey）は読み書きしない（用途を分ける）。パスワード照合は1分5回までに制限する。

**代理中のヘッダー**: `X-Support-Access-Grant-Id: <grant の UUID>`。旧 `X-Admin-Impersonate-User-Id` は廃止し、送られたら 400（`SUPPORT_ACCESS_012`）。ヘッダーの解釈（`SupportAccessFilter`）・読取専用の強制は §7。

## 5. エラーコード

| コード | HTTP | 意味 |
|---|---|---|
| `SUPPORT_ACCESS_001` | 404 | grant が無い、または他の運営者・他人のもの（存在を明かさない） |
| `SUPPORT_ACCESS_002` | 403 | 無効（期限切れ・取消・未許可・閲覧未開始/終了・保護者未承認・本人の状態不可） |
| `SUPPORT_ACCESS_003` | 403 | 閲覧のみ違反（書込系メソッド） |
| `SUPPORT_ACCESS_004` | 403 | 代理中は禁止の操作 |
| `SUPPORT_ACCESS_005` | 422 | 対象が不正（運営アカウント・自分・退会手続中・ACTIVE 以外） |
| `SUPPORT_ACCESS_006` | 409 | 同じ組合せの依頼が既に開いている |
| `SUPPORT_ACCESS_007` | 409 | 状態遷移が不正（期限切れの依頼の許可・既許可の再許可 等） |
| `SUPPORT_ACCESS_008` | 400 | 理由が無い・10〜1000字の範囲外 |
| `SUPPORT_ACCESS_009` | 400 | 代理入力・後見ヘッダーとの併用 |
| `SUPPORT_ACCESS_010` | 403 | 運営アカウントがテナントに所属している |
| `SUPPORT_ACCESS_011` | 429 | 依頼が多すぎる（運営者ごとに1日20件） |
| `SUPPORT_ACCESS_012` | 400 | 旧ヘッダーが送られた |
| `SUPPORT_ACCESS_013` | 400 | 許可時の再認証に失敗した、または材料が無い |

旧 `ADMIN_007`/`ADMIN_008`（管理者変身）は廃番にする。

## 6. 状態遷移・業務ルール（BE 中核）

- 依頼（`request`）: 理由→運営者の所属（010）→対象（005）→開いている grant の期限切れはその場で失効（`EXPIRED`）→同時1件（006・DB の一意制約でも担保）→1日20件（011）→保護者の要否判定（`findRequiredGuardianUserId`）。
- 許可（`approve`）: 本人か（承認が要る場合の）保護者のみ。`PENDING` かつ依頼期限内かつ自分が未許可。本人が ACTIVE であること。再認証必須（013）。両者が揃った時点で `APPROVED`・期限＝その時刻+24h。
- 閲覧開始（`startSession`）: 承認済み・期限内・保護者承認済み・運営者が非所属・本人が ACTIVE。**閲覧記録（REQUIRES_NEW）は grant を更新する前に書く**（grant の FK 親行のロックによる自己デッドロックを避ける）。
- 退会: `WithdrawalRequestedEvent` の AFTER_COMMIT で本人の開いている grant を `REVOKED`（`WITHDRAWAL`）にする。取消が遅れても `SupportAccessGrantValidator` が退会手続中の本人を毎リクエスト拒否する。退会30日後の `AccountPurgeService` が `supportaccess` ドメイン（閲覧記録→許可の順）を物理削除する（`GdprPurgeRetryService` にも登録）。
- 失効バッチ（5分ごと）: `PENDING`（依頼72h）・`APPROVED`（許可24h）の期限切れを `EXPIRED` にして監査。保存期間バッチ（日次 03:40）: 閲覧記録1年・終了済み grant 3年を物理削除。
- GDPR エクスポート: カテゴリ `support_access_logs`（本人の閲覧記録。運営者は表示名のみ）を `PersonalDataCollector` が含める。

## 7. 認可・強制の仕組み

- **SupportAccessFilter**（Jwt→ProxyInput の後・`ParentalConsentGateFilter` や各レートリミットより前）: ヘッダーがあるリクエストごとに、元の認証が ROLE_SYSTEM_ADMIN・grant が運営者本人のもの・`SupportAccessGrantValidator` の全検証を通ったときだけ、認証情報を「本人＋本人の roles」で作り直す（**運営者の権限は引き継がない**）。`/ws/**` は対象外。
- **閲覧のみの三層**: (a) フィルター: GET/HEAD 以外は 003、禁止パスは 004。(b) `@SupportAccessDenied`（認証系・決済・書き出しに付与。本人側・運営側の API 全体にも付与）の `HandlerInterceptor`。(c) DB 接続を READ ONLY にする（`SupportAccessContextHolder#isReadOnlyEnforced`）。閲覧記録・監査の `REQUIRES_NEW` だけが `callWithWritableConnection` で書込可能。`@Async` へは `SupportAccessContextTaskDecorator` で文脈を伝播する。
- **監査**: 遷移は `SupportAccessAuditRecorder`（`REQUIRES_NEW`）で `SUPPORT_ACCESS_*`（[F10.3](F10.3_audit_logs.md)）に残す。代理中に書かれる既存の監査は `AuditLogService` が actor を運営者・target を本人に置換し、`metadata.supportAccessGrantId` を足す。
- **通知**: `SupportAccessNotificationListener`（AFTER_COMMIT・`NotificationDeliveryRunner` 経由）。本人へ依頼時・閲覧開始時（保護者へは依頼時）、運営者へ許可・拒否・取消。

> 上記のうちフィルター・三層・READ ONLY 接続・GET 副作用の洗い出しは戦役 Z-B 第2隊、画面（運営側 `/system-admin/support-access`・本人側 `/settings/support-access`・バナー）は第3隊で実装する。

## 8. 運営アカウントの所属判定

`SupportAccessOperatorAffiliationPort` の実装は、現時点ではチーム・組織の所属（`MembershipScopeQueryService`）を判定する。村・サポーター・委員会は戦役 Z-A PR2 の `PlatformAccountAffiliationPolicy` が持つため、PR2 のマージ後にそちらへ委譲して結線する（ポートのインタフェースは変えない）。
