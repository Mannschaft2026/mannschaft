## 1. 概要

運営（SYSTEM_ADMIN）が利用者の不具合を再現・確認するために、**本人の承認がある場合に限り**、本人の視点でその画面を**閲覧のみ**できる仕組み。旧「管理者変身」（`X-Admin-Impersonate-User-Id`・承認なし・書換可・運営者の権限を引き継ぐ）を置き換えて廃止する。

マスター決定（2026-11-26）:

- 運営は**運営専用アカウント**を使う（チーム・組織等に所属しない）。個人アカウントとの併用は禁止。
- 代理される**本人の承認＋記録**で運用する。代理中は**見るだけ**（書換・投稿・削除・送信は不可）。
- 許可の有効期限は**24時間**（延長不可）。本人はいつでも取り消せる。
- 運営は依頼時に**理由（必須）**を入力する。本人へ通知する。閲覧の記録を本人も自分の設定画面で見られる。
- 承認依頼・許可の操作は代理中に行えない（自己許可の抜け道を塞ぐ）。
- 許可時は本人の**再認証（パスワード／パスキー）必須**。メールのワンクリック許可は不可。依頼理由はプレーンテキスト表示。
- 未成年・後見下の利用者は、**本人と保護者の両方**の承認で初めて有効。
- 代理中のダウンロード（署名 URL）・CSV/PDF 等の書き出しはすべて禁止。
- 保存期間: 許可・依頼 3年、閲覧記録 1年（日次バッチで物理削除）。
- 旧代理ログインは新しい仕組みと同時に切り替える。

## 2. 利用者の流れ

1. **運営の依頼**: 対象ユーザー・理由（10〜1000字）・任意の参照（例: FEEDBACK #id）。`PENDING`。依頼自体は72時間で失効。
2. **本人へ通知**: アプリ内通知（高優先度）。未成年・後見下は保護者へも。リンク先は `/settings/support-access`。
3. **本人の判断**: 再認証つきで許可すると `APPROVED`、期限は許可時刻＋24時間に固定。拒否なら `DENIED`。未成年・後見下は本人と保護者の両方が許可して初めて `APPROVED`（期限は最後の許可＋24時間）。
4. **代理閲覧**: 運営が「閲覧を開始」すると開始記録が残り、本人へ通知する。以後の各リクエストは閲覧記録に1行ずつ残る。**開始前・終了後の許可でヘッダーを付けても 403**。
5. **終わり方**: 運営の終了、本人（保護者）の取消（`REVOKED`）、24時間経過（`EXPIRED`）、運営の撤回（`CANCELLED`）、本人の退会申請（`REVOKED`・`WITHDRAWAL`）。いずれも次のリクエストから即座に拒否する（判定は毎回 DB・時刻で行い、キャッシュしない）。

## 4. API

**運営側** `/api/v1/system-admin/support-access`（`SecurityConfig` の ROLE_SYSTEM_ADMIN 規則で保護。自分の依頼だけを扱い、他の運営者の依頼は 404）

| メソッド | パス | 内容 |
|---|---|---|
| POST | `/grants` | 依頼（201）。`{targetUserId, reason, referenceType?, referenceId?}` |
| GET | `/grants?status&targetUserId&cursor&limit` | 自分の依頼一覧（cursor = 直前ページ末尾の `requestedAt`） |
| GET | `/grants/{id}` | 詳細 |
| POST | `/grants/{id}/cancel` | 撤回（`CANCELLED`） |
| POST | `/grants/{id}/sessions` | 閲覧開始（開始記録・本人へ通知）。`{grantId, targetUserId, targetDisplayName, expiresAt}` |
| POST | `/grants/{id}/sessions/end` | 閲覧終了（204） |
| GET | `/grants/{id}/logs?cursor&limit` | 閲覧記録 |

**本人側** `/api/v1/me/support-access`（認証主体のみ。grant の対象本人または保護者以外には 404）

| メソッド | パス | 内容 |
|---|---|---|
| GET | `/grants?status&cursor&limit` | 自分（保護者の場合は子）宛の依頼・許可。運営者は表示名のみ |
| POST | `/grants/{id}/approve` | 許可。本文 `{currentPassword}` または `{passkeyAssertionJson}`（再認証必須）。期限は24時間固定 |
| POST | `/grants/{id}/deny` | 拒否 `{comment?}` |
| POST | `/grants/{id}/revoke` | 取消（いつでも） |
| GET | `/logs?grantId&cursor&limit` | 自分の画面が閲覧された記録（日時・運営者の表示名・パス・スコープ。メールなし） |

パスキーでの再認証は、既存の `POST /api/v1/auth/webauthn/reauthenticate/begin` でチャレンジを取り、署名結果（`credentialId`・`authenticatorData`・`clientDataJson`・`signature`・`signCount`）の JSON を `passkeyAssertionJson` に入れて許可 API へ送る。署名検証だけを共有し、F18 提示モードの再認証フラグ（Valkey）は読み書きしない（用途を分ける）。パスワード照合は1分5回までに制限する。

**代理中のヘッダー**: `X-Support-Access-Grant-Id: <grant の UUID>`。旧 `X-Admin-Impersonate-User-Id` は廃止し、送られたら 400（`SUPPORT_ACCESS_012`）。ヘッダーの解釈（`SupportAccessFilter`）・読取専用の強制は §7。

## 6. 状態遷移・業務ルール（BE 中核）

- **排他**: 遷移（許可・拒否・取消・撤回・開始・終了・失効・退会）はすべて grant 行を `SELECT ... FOR UPDATE`（`SupportAccessGrantRepository#findByIdForUpdate` 等）で読み、ロック後に状態を検証し直してから書く。同時の「開始と取消」「許可と撤回」「本人と保護者の許可」で片方が後勝ちの上書きで消えない。ロックの取得順は「運営者の依頼ロック → grant 行（id 昇順）」に固定。1日20件の上限は `support_access_request_locks`（運営者単位の行ロック・`INSERT ... ON DUPLICATE KEY UPDATE`）で count→insert を直列化する。並行の結合テスト `SupportAccessGrantConcurrencyIT`。
- 依頼（`request`）: 理由→運営者の所属（010）→対象（005）→保護者の要否（下記・fail-closed で 005）→［依頼ロック］→開いている grant の期限切れはその場で失効（`EXPIRED`）→同時1件（006・DB の一意制約でも担保）→1日20件（011）。
- **保護者の要否（fail-closed）**: リンクの有無ではなく本人の年齢・後見の状態で決める。**18歳未満の未成年は、後見の封印段階（自立扱いの年齢）でも一律で**（マスター決定 2026-11-27）、そのほか後見切替の年齢ポリシーで保護者が子に代わって操作できる段階（`switchAllowed`）の本人、または生年月日が読めず承認済みの保護者リンクがある本人は保護者の承認が要る。承認できる保護者（承認済みリンク・後見の権原 ALLOWED・保護者が ACTIVE）がいなければ依頼は 005。保護者に SYSTEM_ADMIN や依頼した運営者本人がいれば利益相反として 005。既存の保護者同意（いずれか1人の承認で子が ACTIVE）に合わせ、**いずれか1人（userId 昇順の先頭）の承認で足りる**。許可の時点で要否と保護者を再評価し、保護者の停止・リンク解除・新たに要るようになった場合は 005（依頼のやり直し）。
- 許可（`approve`）: 本人か（承認が要る場合の）保護者のみ。**後見切替・代理入力の最中は許可・拒否・取消を 015 で拒否**（`ProxyInputContext#isProxy`）。`PENDING` かつ依頼期限内かつ自分が未許可。本人が ACTIVE であること。再認証必須（013。パスキーは UV・UP 必須・sign_count は authenticatorData の値で判定し同期パスキーの 0/0 は許す。F18 提示モードの再認証フラグとは用途を分け、読み書きしない）。両者が揃った時点で `APPROVED`・期限＝その時刻+24h。
- 閲覧開始（`startSession`）: 承認済み・期限内・保護者承認済み・運営者が非所属・本人が ACTIVE。閲覧記録（SESSION_START/END）は grant の遷移と**同じ TX** で書く（grant 行の排他ロックを持ったまま REQUIRES_NEW で子行を書くと FK の親行ロック待ちで自分を待つため）。応答に BE 時刻基準の `remainingSeconds` を含め、FE はこれを基準に残り時間を数える。
- **退会した保護者だけが載る行は、保護者欄を空にする**（マスター決定 2026-11-27。`AccountPurgeService` が保護者の userId を外す現行実装どおり）。
- **代理中のカルテ詳細**（マスター決定 2026-11-27）: `GET /teams/{teamId}/charts/{id}` は代理中も開けるが、写真の署名 URL（`signedUrl`・`signedUrlExpiresAt`）だけを null にして本文は返す（`ChartRecordService#buildChartResponse`。番人の例外表 `credential_get_allowlist.txt`。テスト `ChartRecordServiceTest`）。FE は署名 URL が無いとき「代理閲覧中は写真を表示しません」を出す。
- 退会: `WithdrawalRequestedEvent` の AFTER_COMMIT で本人の開いている grant を `REVOKED`（`WITHDRAWAL`）にする（一時的な失敗はその場で3回まで再試行）。それでも失敗したら失効バッチの照合（`reconcileWithdrawnTargets`: 開いている grant の本人が退会手続中・見つからなければ取消）が取り消す。取消が遅れても `SupportAccessGrantValidator` が退会手続中の本人を毎リクエスト拒否する。`REVOKED` は終端で、退会を撤回しても復活しない。退会30日後の `AccountPurgeService` が `supportaccess` ドメイン（閲覧記録→本人宛の監査 outbox→許可の順）を物理削除し、保護者としてだけ記録された行は保護者の userId を外す（子の記録は残す）。運営者の依頼ロック行も消す（`GdprPurgeRetryService` にも登録）。
- 失効バッチ（5分ごと）: `PENDING`（依頼72h）・`APPROVED`（許可24h）の期限に達したもの（**期限ちょうども含む**。Validator の「`now < expiresAt` のときだけ有効」と境界を揃える）を `EXPIRED` にして監査。保存期間バッチ（日次 03:40）: 閲覧記録1年・終了済み grant 3年・反映済みの監査 outbox 30日を物理削除。
- GDPR エクスポート: カテゴリ `support_access_logs`（本人の閲覧記録）と `support_access_grants`（本人宛・保護者として関わった依頼と許可。依頼理由・運営者の表示名・状態と時刻）を `PersonalDataCollector` が含める（運営者は表示名のみ・メールは含めない）。

## 7. 認可・強制の仕組み

### 7.1 SupportAccessFilter

`JwtAuthenticationFilter` → `ProxyInputContextFilter` → **`SupportAccessFilter`** → 保護者同意ゲート・各レートリミット → 認可（`AuthorizationFilter`）の順（`SecurityConfig`。本人の認証に作り直した後で後段が動く。順序は `SupportAccessEnforcementGuardTest` が固定する）。`@Component` の自動登録は無効（Spring Security のチェーンからだけ動く）。

1. `/ws/**` は対象外（WebSocket は代理にならない。CONNECT は常に運営者本人）。
2. 旧 `X-Admin-Impersonate-User-Id` は経路・認証を問わず 400（012）。
3. `X-Support-Access-Grant-Id` が無ければ素通し。未認証ならヘッダーは無効（通常の認証で拒否される）。
4. 元の認証が ROLE_SYSTEM_ADMIN でなければ 403。grant ID が UUID でなければ 404（001）。代理入力・後見のヘッダー（`X-Proxy-For-User-Id` 等）との併用は 400（009）。
5. `SupportAccessGrantValidator` が**毎リクエスト DB で**検証する（キャッシュしない）。違反は 001（404）・002・010（403）。想定外の失敗は 503（014・fail-closed）。運営者自身の現在の状態（SYSTEM_ADMIN の保持・ACTIVE・退会手続中でない）も毎回確かめる（JWT のロールは発行時点の写しのため。剥奪・凍結・停止は次のリクエストから 002）。
6. 閲覧のみ（第1層）: URI にパーセントエンコード（`%`）を含む要求と禁止パスはメソッドを問わず 004、GET/HEAD 以外は 003。禁止パスは**生の URI と、Spring MVC と同じ規則でデコードした lookup path（`UrlPathHelper`: URL デコード・セミコロン除去）の両方**で判定する（`login%2Dhistory`・`r%65ceipts`・`%61uth`・`ex%70ort` 等のエンコード迂回を塞ぐ）。
7. 認証を「本人 ID ＋ `RoleClaimResolver#resolveRoles(本人)`」で作り直す（**運営者の ROLE_SYSTEM_ADMIN は載せない**。本人が SYSTEM_ADMIN と解決されたら拒否）。ppc は立てない（本人の状態ゲートは検証側で判定済み）。運営者の jti は `details` の `jti` には置かず `supportAccessOperatorJti`（追跡用）に残す。したがって代理中の `SecurityUtils#getCurrentSessionHash()` は **null**（本人のセッションでも運営者のセッションでもない。本人のセッション一覧・監査の session_hash に運営者のセッションを混ぜない）。
8. **閲覧記録（VIEW）を chain の前に書き**（`SupportAccessLogRecorder#recordView`。書けなければ 503）、chain の後に応答状態と最適一致パターンを書き足す。拒否は `recordDenied`（grant が実在すれば DENIED 行＋監査）。
9. `SupportAccessContextHolder` を chain の間だけ設定し、必ず解除する（認証も元へ戻す）。

### 7.2 禁止パス（SUPPORT_ACCESS_004）

`SupportAccessPathPolicy`（大文字小文字・連続スラッシュ・パスパラメータを正規化して判定）。代理中は GET でも次を拒否する。

- 認証・資格情報: `/api/v1/auth/**`・`/api/v1/account/**`（GDPR・退会）・`/users/me/{password,email,oauth,login-history,withdrawal,stripe-connect}`・`/api/api-keys`
- 決済・課金・請求: `/api/v1/billing`・`/me/billing`・`/me/payment-methods`・`/me/receipts`・`/my/receipts`・`/member-payments`・`/payment`、および `billing`・`stripe`・`payment-methods` の語を含むセグメント
- 招待トークン: `*-token(s)`・`invit(e|es|ation|ations)` で終わるセグメント
- 資格情報を返す GET: `qr`・`*-qr`・`qr-*`（会員証・チケット・ポイントカード・備品・順番待ちの QR トークン）、`links`・`file-links`（共有リンクのトークン。公開リンク経由の download 禁止の素通りを塞ぐ）、`*-secret(s)` のセグメント
- 書出し: パスに `download`・`export`・`csv`・`pdf` を含むもの（署名 URL を含む）
- 本人承認・運営: `/api/v1/me/support-access/**`（自己許可の抜け道）・`/api/v1/system-admin/**`・`/actuator`・`/api/internal`
- `SecurityConfig` で SYSTEM_ADMIN 予約の `/api/v1/admin/**`（`age-group-settings`・`stripe`・`reports`・`moderation`・`warning-re-reviews`・`users`・`onboarding/presets`・`form-presets`・`seals`・`action-templates`・`notifications`）。**`/api/v1/admin/**` の一律禁止はしない**（スコープ管理者向けの管理 API は本人の視点として閲覧できる）。差分は番人が検出する。

### 7.3 閲覧のみの三層

- **(a) フィルター**: 上記 §7.1-6。
- **(b) `@SupportAccessDenied` と `SupportAccessHandlerInterceptor`**: 注釈の付いた Controller クラス／メソッドを代理中は 004 で拒否する（`WebMvcConfig` に登録）。download / export / csv / pdf を含むパスの handler 全部（74 箇所）と、本人側・運営側のサポート閲覧 API に付与済み。付与漏れは `SupportAccessEnforcementGuardTest` が検出する（新規の書出し系 handler は注釈が無いと CI が落ちる）。さらに Interceptor は、Spring が選んだルートパターン（`HandlerMapping.BEST_MATCHING_PATTERN_ATTRIBUTE`。パス変数は中立な値に置き換える）とデコード済みの lookup path にも §7.2 の判定を当てる（第1層の二重化）。
  - **資格情報を返す GET**: 応答 DTO（戻り値の型を再帰的にたどる）に `token`・`secret`・`password`・`apiKey`・`signedUrl`・`presigned` を名前に含む文字列フィールドを持つ GET は `@SupportAccessDenied` が**必須**（基準線なし）。番人が検出し、例外は理由付きの許可表 `backend/src/test/resources/support_access_guard/credential_get_allowlist.txt`（現在 0 件）に限る。付与先: 会員証の QR トークン、拠点 QR、共有リンク一覧、ポイントカードの顧客 QR、備品 QR 一覧、順番待ち QR（クラス）、チケット QR・チケット詳細と一覧（qrToken）、サイネージのトークン一覧、iCal 購読トークン、求人の QR トークン（クラス）、プラン変更の支払アクション・エスクローの client secret、LINE 連携設定（webhookSecret）、承継の誓約（署名トークン）、受信 Webhook のトークン一覧、カルテ詳細（写真の署名 URL）。`@SupportAccessReadOnlyPost`（POST だが読むだけの検索系の例外）は未導入（初期は fail-closed。必要になったときに一つずつ追加する）。
- **(c) DB 接続の READ ONLY 化**（最後の砦）: Hibernate のイベントだけでは `@Modifying`（約 300 箇所）・JdbcTemplate・ネイティブ SQL を止められないため、**接続そのもの**を READ ONLY にする。`SupportAccessReadOnlyDataSourcePostProcessor` が `HikariDataSource` の Bean を CGLIB プロキシ（`HikariDataSource` のサブクラスのまま）で包み、`getConnection` の戻り値へ、`SupportAccessContextHolder#isReadOnlyEnforced()` が真のときだけ `setReadOnly(true)` を掛ける。MySQL Connector/J の `readOnlyPropagatesToServer`（既定 true）で `SET SESSION TRANSACTION READ ONLY` がサーバーへ伝わり、書込 SQL は DB が拒否する。返却時は HikariCP が dirty bit で書込可へ戻す（プールへ持ち越さない）。設定に失敗した接続は閉じて例外にする。OSIV は無効（`open-in-view: false`）で、接続は文脈設定後に取得される。**この方式は `readOnlyPropagatesToServer=false` や、プロキシを迂回する別 DataSource（`archiveDataSource` を除く）を作ると崩れる**。
- **書込可能な接続の扱い**: 代理中でも書くのは閲覧記録（`SupportAccessLogRecorder`）と監査（`AuditLogService`・`SupportAccessAuditRecorder`）だけ。`@Transactional(REQUIRES_NEW)` の接続は**メソッド本体の前**（TX 開始時）に取得されるため、本体の中の `callWithWritableConnection` では間に合わない。そこで `@SupportAccessWritable` を付けたクラスの実行を `SupportAccessWritableAspect`（`@Order(HIGHEST_PRECEDENCE)`）が TX の外側で書込可能な区間に包む。付与先は閲覧記録の部品だけ（番人で固定）。監査は `AuditLogService#recordSync` の保存を `callWithWritableConnection` で包む。
- **(d) イベントの扱い**: 代理中に publish されたイベントの受け手でも READ ONLY が効くよう、全スレッドプール（event-pool・withdrawal-pool・purge-pool・page-view-pool・notification-*・ai-analysis-pool・job-pool・M 専用 executor）の `TaskDecorator` を `AsyncConfig#contextPropagatingDecorator`（MDC ＋ `SupportAccessContextTaskDecorator`）に統一した。書込系イベントの受け手は DB 側で拒否される（publish 自体は拒否しない）。同期リスナー・AFTER_COMMIT も同一スレッドの READ ONLY 接続を使う。ダッシュボードの並列集計（`CompletableFuture.supplyAsync`）は共有 ForkJoin プールではなく、同じ `TaskDecorator` を付けた `dashboard-aggregation-pool`（キューなし・飽和時 CallerRuns。入れ子の集計で枯渇しない）を明示して渡す。Executor 未指定の `supplyAsync`/`runAsync` は番人（`SupportAccessEnforcementGuardTest`）が禁止する（基準線なし）。

### 7.4 GET の副作用

GET が副作用（閲覧数・既読・初回作成・履歴・状態遷移）を持つ API を `backend/src/test/resources/support_access_guard/get_side_effect_inventory.txt` に洗い出し、`SKIP`（代理中は副作用だけ行わず結果は返す）・`DENY`（拒否）・`NONE`（到達しない／記録のみ）に分類した。SKIP/DENY の Service は `SupportAccessContextHolder` で判定する。番人（`SupportAccessGuardTest` S14）が、表に載らない新規の候補（Service の `increment*View*`・`markAsRead*`・`record*Viewed*`・`*_VIEWED` と、全クラスの Valkey 書込 `opsFor*().set/setIfAbsent/increment/add`）と、表に残った実在しないファイルを検出する。外部送信（メール・Push・Webhook・S3 署名 URL の発行）は再走査の結果を表の冒頭に記す（いずれも書込 API かその AFTER_COMMIT、または PathPolicy で拒否するパスからだけ発生する）。Spotlight の配信（`GET /api/v1/spotlight/content`）は、代理中に本人の serve-token・serve-cap・ラウンドロビンの位置を消費しない（SKIP）。主な SKIP: 知識ベースの閲覧数、請求の VIEWED 遷移、検索履歴、広告受信設定・確認通知設定・個人時間割設定の既定行の自動作成（既定値で応答）。主な DENY: iCal 購読トークン、請求詳細、領収書 PDF。

### 7.5 旧代理ログインの撤去

`AdminImpersonationFilter` と `FilterRegistrationBean` を削除し、`SecurityConfig` を差し替えた。リクエスト属性 `originalAdminId` の参照（ブログ・個人ブログ・タイムライン・スケジュール出欠の牧場報酬判定、`PrivateSelfAccessGuard`、`RanchAdminController`）は `SupportAccessContextHolder#isActive()` へ移した。`ADMIN_007`/`ADMIN_008` は廃番。牧場の報酬 payload の `originalAdminId` フィールド（配信済みスキーマ）は名称を変えず、代理中は「報酬対象外」として扱う。

### 7.6 監査・通知

- **監査（欠落しない構成）**: 遷移・拒否は、遷移と**同じ TX** で監査 outbox（`support_access_audit_outbox`）へ1行書く。コミット後に `SupportAccessAuditRecorder`（TX を持たない）が行をリースし（`SupportAccessAuditOutboxStore`・REQUIRES_NEW）、`AuditLogService#recordStrict`（`AuditLogStrictWriter`・REQUIRES_NEW・書込可能な接続・**失敗は例外**）で `SUPPORT_ACCESS_*`（[F10.3](F10.3_audit_logs.md)）を書いて確定する。反映に失敗した行は握りつぶさず試行回数と要約を outbox に残し、再試行バッチ `supportaccess-audit-relay`（5分ごと）が間隔を空けて反映する。audit_logs の書込と outbox の確定は別 TX（auth と supportaccess を1つの TX にしない: D-3T）のため少なくとも1回で、重複時は `metadata.auditOutboxId` で同一の事実と分かる。代理中に書かれる既存の監査は `AuditLogService` が actor を運営者・target を本人に置換し、`metadata.supportAccessGrantId` を足す。代理中の `recordSync` は READ ONLY の業務接続に参加せず、`AuditLogStrictWriter` の独立した書込可能な TX で書く（業務 TX が巻き戻っても残る）。
- **通知**: `SupportAccessNotificationListener`（AFTER_COMMIT・`NotificationDeliveryRunner` 経由）。本人へ依頼時・閲覧開始時（保護者へは依頼時）、運営者へ許可・拒否・取消。本人・保護者宛は**安全上必須の通知**（`MandatoryNotificationTypes`）で、通知設定で種別・スコープを OFF にしていても配信する。本人・保護者宛はメール（F09.18 メール outbox・`SUPPORT_ACCESS_NOTICE`・スルー方式）でも送る。依頼理由は HTML エスケープしたプレーンテキストで載せ、リンクは `/settings/support-access` へ遷移するだけ（メールからのワンクリック許可は成立しない）。
- **画面の閲覧のみ**: `useSupportAccessReadOnlyGuard` が、閲覧中は保存系の操作（送信ボタン・フォーム内とダイアログ下部の主ボタン）を無効に見せ（`main.css`）、クリック（キーボードでの押下を含む）とフォームの送信（Enter を含む）を捕捉段階で止める。止めたくない要素には `data-support-access-allow`。

> 画面（運営側 `/system-admin/support-access`・本人側 `/settings/support-access`・バナー `SupportAccessBanner`・`useApi` のヘッダー付与）は戦役 Z-B 第3隊（FE）で実装済み。API の型は `types/generated`（`docs/openapi.json` 由来）を使う。日時はすべて UTC の ISO-8601 Instant（`…Z`）で返り、画面は閲覧者のローカル時刻に直して表示する。

## 8. 運営アカウントの所属判定

`SupportAccessOperatorAffiliationPort` の実装（`SupportAccessOperatorAffiliationAdapter`）は、戦役 Z-A PR2（#4939）の `PlatformAccountAffiliationPolicy#hasAnyTenantAffiliation` へ委譲する。チーム・組織・委員会・村・サポーター（申請を含む）・参加申請・入村申請・個人フォローの所属行を、アカウントの状態を問わず（停止中の運営アカウントも）数える。公式村の作成者としての村長所属は例外として数えない。他人が作った招待・移管の申し出（本人の操作でない所属待ち）は数えない（第三者の操作で運営の業務を止めさせない）。
