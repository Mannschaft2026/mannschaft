# R7 — 大型の負債の提案書（実装しない）

> 親文書: [`../refactor-instructions.md`](../refactor-instructions.md)。先に親文書、[`../decided-facts.md`](../decided-facts.md)、[`../known-doc-drift.md`](../known-doc-drift.md) を読むこと。進め方は親文書 §4-1 の正規フローに従う。
> 足軽のモデル: Sonnet。事実を集める作業が中心である。Sonnet が実際に詰まったときだけ Opus に上げる。
> **このレーンはコードを1行も変えない。** 成果物は `docs/refactoring/proposals/` の文書だけである。PR の scope は `tooling` になる。

## 目的

実装すると凍結ストア・課金・認可・本番の設定に触れる負債について、マスターが「やる・やらない・いつ・誰の戦役で」を決められる材料を作る。

## 最重要の注意

第1版の指示書は、既に決まっていることを「提案」や「質問」にする誤りを多く含んでいた。このレーンは同じ誤りをしやすい。

- 提案を書く前に、[`../decided-facts.md`](../decided-facts.md) と、規約・`docs/security/`・`docs/architecture/`・`docs/features/`・台帳を、その論点の語で検索する
- **方針が既に決まっているもの**は、方針を問い直さない。「決まっている方針をどう実現するか」の計画を書く
- **台帳に行があるもの**は、新しい提案を書かない。その行の持ち主への申し送りを1段落で書く
- 事実と推測を分ける。件数は自分で測る。親文書の数値は起草時点のものである
- 公開リポジトリである。**悪用の手掛かりになる具体**（どの入口が検証されていないか、など）は文書に書かず、マスターへ直接報告する。実証できた不具合を台帳へ起票するときは、台帳の先例の書き方に合わせ、必要なら詳細を省く

## 文書の形式

1件1ファイル。`docs/refactoring/proposals/P<番号>-<名前>.md`。

```markdown
# P<番号> — <題>

## 位置づけ
<提案／決定済みの方針の実現計画／規約違反の是正計画／所管への申し送り のどれか。根拠の文書>

## 現状（事実）
<ファイル・行・件数。測ったコマンドと日付>

## 既に決まっていること
<該当する規約・設計書・台帳の行。出典>

## なぜ負債か
<具体的に何が困るか>

## 影響の範囲
<触るファイル、依存している側、公開 API・DB・凍結物・番人への波及>

## 案
<案ごとの手順、PR の切り方>

## リスクと安全網
<壊れ方と、それを先に検出するテスト。安全網が無いなら、先に作るもの>

## 既存の戦役との関係
<#4022 のどのレーンか。単独でやれるか、所管へ渡すべきか>

## 推奨
<1つに絞る。やらないという推奨も可>

## 判断してほしいこと
<検索して決まっていないと確かめたことだけ>
```

## 手順

1. 対象ごとに事実を集める。読み取りと計測だけを行う
2. 既に決まっていることと、台帳の行を、検索して確かめる。表の記述は起草時点のものである
3. 文書を書く。1 PR に複数の文書をまとめてよい
4. 最後に `docs/refactoring/proposals/README.md` に一覧表（題・位置づけ・推奨・判断待ちの有無）を作る

## やってはならないこと

- 提案のついでの実装
- 計測のための番人の絞り込み実行（親文書 §4-4 の24番）
- 推測を事実のように書くこと
- 決まっている方針を問い直すこと
- 段階と安全網の無い「全部書き直す」案

## 完了条件

1. P1〜P14 のそれぞれについて、文書がある
2. #4022 への申し送りの文書がある
