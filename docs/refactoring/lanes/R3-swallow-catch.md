# R3 — FE 握りつぶし catch 抑止の返済

> 親文書: [`../refactor-instructions.md`](../refactor-instructions.md)。先に親文書を読むこと。
> 推奨モデル: Sonnet。判断が割れた箇所だけ Opus に上げる。
> **横展開型のレーンである。着手前に正本 Issue で対象ファイルを宣言すること**（親文書 §4-4）。

## 目的

`frontend/eslint-suppressions.json` に凍結されている握りつぶし catch（91 ファイル・479 件、ルールは `no-restricted-syntax` のみ）を減らす。障害が利用者にも開発者にも見えない状態を、正しく見える状態に直す。

このレーンは**挙動が変わる**。握りつぶしていた失敗が表に出るようになる。それが目的であり、親文書 §4-2 の8番が認める例外である。

## 先に読むもの

- `frontend/eslint-rules/swallow-catch-rules.mjs`（番人。何を握りつぶしと見なすかの定義）
- `frontend/eslint.config.mjs` の該当部分
- `frontend/FRONTEND_CODING_CONVENTION.md` のエラーハンドリングの節
- 既に返済済みで、同じ種類の処理を持つ画面のコード（手本にする）

## 手順

### ステップ0: 分類表を作る

抑止ファイルから、ファイル別の件数を出す。

```bash
node -e "const s=require('./frontend/eslint-suppressions.json');Object.entries(s).map(([f,r])=>[Object.values(r).reduce((a,x)=>a+x.count,0),f]).sort((a,b)=>b[0]-a[0]).forEach(x=>console.log(x.join('\t')))"
```

件数の少ないファイルから始める。各 catch を次の4種に分ける。

| 種別 | 見分け方 | 直し方 |
|---|---|---|
| ① 利用者の操作の失敗 | 保存・削除・送信などの catch | 既存の手本と同じ方法でエラーを通知する。文言は i18n の6言語に足す |
| ② 画面の初期読み込みの失敗 | 一覧や詳細の取得の catch で、空配列や `null` を入れている | 「空」と「失敗」を区別できる状態を持たせ、失敗を表示する。手本が無ければ質問する |
| ③ 失敗しても業務に影響しない副次処理 | 計測、既読化、プリフェッチなど | 握りつぶす理由が正当な場合に限り、**番人が定める唯一の許可方法**（`frontend/eslint-rules/swallow-catch-rules.mjs` のメッセージが示す、理由コメント付きの行単位の許可）を使う。条件は下の「正当な例外の条件」 |
| ④ 判断できない | 失敗時の正しい振る舞いが仕様書にも手本にも無い | 直さない。質問にまとめる |

### 正当な例外の条件（③だけに適用）

次の**すべて**を満たすときだけ、理由付きの行単位の許可を使ってよい。1つでも欠けたら④（質問）に回す。

1. 失敗しても、利用者が見る表示・保存されるデータ・後続の処理が変わらない
2. 失敗を利用者に知らせる意味が無い（知らせても対処のしようが無い）
3. 失敗が開発者には見える（エラー監視への送信か、警告ログがある）。無ければ足す
4. 理由コメントに、なぜ握りつぶしてよいかを日本語で1文書く。「意図的」「問題なし」だけの理由は不可

PR 本文に、許可を使った箇所の一覧と理由を載せる。許可を使った件数は、抑止を返済した件数とは別に数えて報告する。

### ステップ1: ファイル単位で返済する

1. 1 PR は**最大5ファイル**、かつ同じ機能領域にまとめる
2. catch を直す。`useApi` が既にやっている処理（401 のリフレッシュ、リトライ）を二重に書かない
3. 直した catch ごとに、失敗時の振る舞いを確かめる spec を足すか、既存 spec に足す
4. `npm run lint` を通す。抑止が不要になったら `npm run lint:prune` で**そのファイルの分だけ**が消えることを `git diff frontend/eslint-suppressions.json` で確かめる。無関係なファイルの行が消えていたら、原因を調べる
5. 翻訳を足したら、6言語すべてに**その言語の訳**を入れる。ロケール番人（`frontend/tests/unit/i18n/`）を通す

### ステップ2: 進捗を記録する

PR 本文に「着手時 N 件 → この PR 後 M 件」を書く。

## やってはならないこと

- `eslint-suppressions.json` の抑止を**増やす**こと。「正当な例外の条件」を満たさない catch を `eslint-disable` コメントで黙らせること
- catch を `console.error` だけに書き換えて終わること（握りつぶしと同じ）
- catch を消して例外を素通しにし、画面が白くなる経路を作ること
- `useApi.ts`、`useAuthStore.ts` の変更
- エラー文言の直書き
- 旧い日本語文言を期待値に持つテストを、確かめずに書き換えること。翻訳を足すと落ちる spec があるので、`frontend/app` の同居 spec も走査する
- 1 PR に R4 の構造分割を混ぜること

## Stop And Ask

- ②で、失敗の表示方法の手本が同じ機能領域に無い
- ③か①かで判断が割れる
- 直すと、BE に無い API を FE が呼んでいたことが分かった（握りつぶしで隠れていた未実装）。この場合は直さずに台帳へ起票する

## 完了条件

このレーンは分量が多い。次のどちらかで「一区切り」とする。

- 抑止が0件になった
- ①②③で直せるものを直し切り、残りがすべて④として質問にまとまっている
