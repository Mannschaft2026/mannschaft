# R3 — E2E テストの中の握りつぶし catch の返済

> 親文書: [`../refactor-instructions.md`](../refactor-instructions.md)。先に親文書と [`../decided-facts.md`](../decided-facts.md) を読むこと。進め方は親文書 §4-1 の正規フローに従う。
> 足軽のモデル: Sonnet。
> **横展開型のレーンである。着手前に #4599 のコメントで対象ファイルを宣言すること。**
> このレーンの PR は `frontend/eslint-suppressions.json` を変えるので、scope が `app` になる（決定 P5）。

## 目的

握りつぶし catch の番人が凍結している抑止（`frontend/eslint-suppressions.json`、479 件）を減らす。

**対象は E2E テストである。** 479 件のうち 478 件は `frontend/tests/e2e/` の 90 ファイルにあり、残り1件は `tests/unit/composables/useConflictResolver.spec.ts` にある。画面のコード（`frontend/app/`）には1件も無い。画面側の握りつぶしは、過去の戦役（CMP-260922-2045）で返済が済んでおり、残りは別の台帳行が持っている。このレーンは画面のコードを触らない。

## 現状（2026-11-17 実測）

90 ファイルのうち 78 ファイルは `tests/e2e/real/`（実 BE を踏む実機 E2E）にある。握りつぶしの書き方は、大きく2種類である。

| 種類 | 形 | 件数 | 何が問題か |
|---|---|---|---|
| A. スピナーの消滅待ち | `await page.locator('.pi-spin').waitFor({ state: 'detached', timeout: N }).catch(() => {})` | 完全にこの形の行が 222（待ち時間は 20 秒が 197、30 秒が 15、15 秒が 9、10 秒が 1。うち1行は `page` 以外が対象） | 同じ処理をする共通ヘルパ `waitForSpinnerGone(page, timeout)`（`frontend/tests/e2e/helpers/wait.ts`）が既にあり、18 ファイルが使っている。ヘルパの中の握りつぶしは、理由を書いたうえで番人が認める形になっている。**222 行はその重複である** |
| B. 状態の問い合わせ | `if (await x.isVisible({ timeout: N }).catch(() => false)) { … }` や `if (!(await …)) return` | 約190 | 要素が見えなければ、テストの本体を黙って飛ばして通る。**落ちるべきテストが通ってしまう** |
| C. そのほか | 待ち（`waitForURL` など）の `.catch(() => {})`、後始末の API 呼び出しの握りつぶし、値の取得の握りつぶしなど | 残り | 1件ずつ性格が違う |

## 手順

### 段階1: 種類 A を共通ヘルパへ寄せる（挙動を変えない）

1. 対象は、**種類 A の形に完全に一致する行だけ**である。次の正規表現に一致し、かつ対象が `page` である行に限る
   ```
   ^\s*await\s+page\.locator\('\.pi-spin'\)\.waitFor\(\{\s*state:\s*'detached',\s*timeout:\s*[\d_]+\s*\}\)\.catch\(\(\)\s*=>\s*\{\}\)\s*;?\s*$
   ```
2. 置き換える。待ち時間が 20 秒なら `await waitForSpinnerGone(page)`、それ以外なら `await waitForSpinnerGone(page, <元の値>)`。**待ち時間を変えない**
3. ヘルパを import する。相対パスは、既にヘルパを使っている同じ階層の spec に合わせる
4. 形が少しでも違う行（対象が `page` でない、条件が違う、行が分かれている、前後に処理が付いている）は、段階1では触らない。一覧にして段階3へ回す
5. 1 PR は、同じ機能のまとまりで最大10ファイル
6. `npm run lint` を通し、`npm run lint:prune` を実行する。`git diff frontend/eslint-suppressions.json` で、**自分が触ったファイルの件数だけが減った**ことを確かめる。ほかのファイルの行が動いていたら、原因を調べる
7. 検証（下の「検証」）を通す

### 段階2: 種類 B の棚卸しと、直し方の提案（実装の前に裁可を得る）

種類 B を直すと、テストの合否が変わる。前提のデータが無い環境では、今まで通っていたテストが落ちるようになる。そのため、**先に棚卸しと方針をまとめ、裁可を得てから実装する**。

1. 種類 B の全箇所を、`docs/testing/e2e-conditional-skip-inventory.md` に表にする

   | spec | 行 | 問い合わせている要素 | 見えなかったときの動き（本体を飛ばす／別の経路へ進む／`test.skip`） | 要素が見えるための前提（データ・権限・機能フラグ） | 分類 |
   |---|---|---|---|---|---|

2. 分類する
   - **(i) 必ず見えるはずの要素**: シードやフィクスチャで前提が保証されている。見えなければテストの失敗であるべき
   - **(ii) 環境によって無いことが正しい要素**: 機能フラグや任意のデータに依存する。飛ばすことに意味がある
   - **(iii) 分岐そのものが検証の対象**: 両方の経路を確かめている
   - **(iv) 判断できない**
3. 方針の案を、同じ文書に書く。少なくとも次を含める
   - (i) を `await expect(x).toBeVisible()` に置き換える案。置き換えると落ちるようになる spec の見込み
   - (ii) を、理由を明記した `test.skip(条件, '理由')` に置き換える案（黙って通るのではなく、飛ばしたことが結果に残る）
   - `isVisible()` は、要素が無いときには例外を投げずに `false` を返す。`.catch(() => false)` が実際に握りつぶしているのは、ロケータが複数の要素に一致したときなどの例外である。それを踏まえた直し方
4. 報告に、分類ごとの件数と方針の案を載せて止める。**段階2では spec を変えない**

### 段階3: 種類 C と、段階1で触らなかった行の棚卸し

1件ずつ、何を握りつぶしているかを表にする（同じ文書の別の節でよい）。後始末の失敗のように握りつぶす理由が正当なものは、番人が定める形（`// eslint-disable-next-line no-restricted-syntax -- <日本語の理由>`。実例は `frontend/tests/e2e/helpers/wait.ts`）への置き換えを**提案**として書く。段階3でも spec は変えない。

## やってはならないこと

- 画面のコード（`frontend/app/`）、`useApi.ts`、共通ヘルパ `wait.ts` の変更
- 待ち時間の変更、待ちの削除、アサーションの追加や削除（段階1は置き換えだけ）
- `eslint-suppressions.json` を手で編集すること。抑止を増やすこと
- 握りつぶしの形だけを変えて番人を避けること。番人は1文だけの catch しか検出しないので、`console.error` を1行足せば lint は通るが、握りつぶしは残る（決定 P10）
- 段階2・段階3で spec を変えること
- 対象外の3ファイルに触れること
- R2 が同じ時期に設定を触っている spec に触れること

## Stop And Ask

- 置き換えた spec を実機で実行すると、置き換える前と結果が違う
- `lint:prune` で、自分が触っていないファイルの抑止が動いた
- 着手時の照合で、対象のファイルに未完の台帳行が見つかった

## 完了条件

1. 種類 A の形に完全に一致する行が、対象外のファイルを除いて、すべて共通ヘルパに置き換わっている
2. 抑止の件数が、置き換えた行の数だけ減っている（着手時と完了時の件数を報告する）
3. 種類 B の棚卸し表と方針の案がある
4. 種類 C と、段階1で触らなかった行の棚卸し表がある
5. 置き換えたすべての spec について、置き換えの前後で実機での結果が同じである
